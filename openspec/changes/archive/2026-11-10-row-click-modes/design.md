# Design

## Context

- **Click a task to** (`inline-task-editing` D6): `web/src/app/rowClick.ts`, a device-local stored value (`opentodo.rowClick`, `edit` by default or `open`), read by `TaskListView` in `startInline`. A click on a row's title calls the row's `onOpen(e)`; `startInline` turns it into the inline editor when the choice is `edit`, the pointer is fine, the window is at least 768 px, no panel or split docks and the task is editable; otherwise the task opens (its page, or the side panel or the Inbox's split where they dock). A click on the row's empty area always opens the task.
- **Expanded rows** (`row-expand`): one expanded row per list (`expandedId`), toggled by the row's `onExpand` (the revealed Show details, the touch disclosure, → and ←). Board cards and departing rows cannot expand (`canExpand` in `TaskRow`).
- **Side panel** (`task-side-panel` D2, D4): `useSidePanel` docks the cursor's task (`followTask`) while the panel is open, from 1024 px. **Inbox split** (`inbox-split` D1): `useInboxSplit` docks the cursor's task with the page preference. `TaskListView` read the docked id with `usePanelTaskId()`, so each dock drew the list again.

## Decisions

**D1. Expand the row is a third value of the same choice, decided in the row.** `RowClick` becomes `'edit' | 'open' | 'expand'`, stored as before (`edit` is not stored, so older builds read the new value as their default). The row decides at the click: `clickExpands(e, canExpand)` is true for the `expand` choice, a pointer click (`detail > 0`; Enter's click has `detail` 0 and keeps opening) and a row that can expand; then the row calls its own `onExpand`, else `onOpen` as before. It reads the store at the click (`rowClick()`), not as a prop, so no row draws when the choice changes and the Filter view and saved views, whose rows already have `onExpand`, get it without code of their own. Under `expand` no click starts the inline editor (`startInline` asks for `edit`), F2 still does. Any pointer and any width: unlike editing in place, expanding needs no keyboard. Alternatives: a separate switch "Click expands rows". Rejected: three exclusive meanings of one click are one choice, and two switches could contradict each other. Expanding on selection (j and k expand the row). Rejected: moving the cursor through a long list would open and close details on every row, and the side panel already shows the selected task's details without moving the list.

**D2. A double-click opens the page; its second click does nothing.** `TaskRow` takes an optional `onOpenPage`, wired by every list (`TaskListRow` through the stable `RowActions.openPage`, the Filter view, saved views, Next and Waiting) to `openTaskPage`, so the review screens, Plan and dashboards keep their rows as they are. When `onOpenPage` is set, a click with `detail > 1` is ignored: under Expand the row a double-click would otherwise expand and hide the row, under Open details beside the panel it would dock twice. The first click acts at once (no delay waiting for a possible second click), so a single click stays as fast as before. A double-click on the row's controls (checkbox, chevron, selection box, revealed actions, disclosure, edit bar) is theirs. In the inline title field, a double-click selects a word, unless the field was opened by the first click of this double-click: the row keeps the time of its last click (`opened`) and a double-click within `DOUBLE_CLICK_MS` (500 ms, the longest common system default; the browser does not expose its own) of it still opens the page. Without this, a double-click under the default choice would only ever select a word, because the first click always turns the title into a field. Alternative: open the page on the second click (`detail === 2`). Rejected: the dblclick event is where the browser has already applied its own interval and movement tolerance.

**D3. Details follow the selection: the side panel's behaviour, for everyone who chose it.** No new choice. "Open tasks: In a side panel" already means a task beside every list that follows the cursor while open (`task-side-panel` D4), exactly the Inbox's behaviour that #1116 asks for; a third value ("follow the selection" versus "open on click") would split one panel into two nearly identical modes. This change states it in the docs where people look, pins it with tests in Today, a project, a label and the Inbox, and makes it cheap (D4). Focus stays on the list: the cursor is real focus (`assistive-tech-semantics`), the docked task never takes it, and a click focuses the row's own button. Esc keeps its meaning (`task-side-panel` D4): on the list it clears the cursor and leaves the panel; inside the panel it closes it. Under Expand the row a click selects and expands the row; the selection moves, so an open panel shows the task too, and a closed one stays closed until Enter or Open details, as for any cursor move. The page preference keeps the page, and the Inbox keeps its own split.

**D4. The list reads whether a task is open, not which.** `TaskListView` used the docked id for the click-away (whether to listen), `startInline` (no inline editor while a task is open), the shortcuts' Escape and occurrence keys, the bindings' "a task opened from the panel is selected here" and the Inbox split's "closing the pane clears the cursor". Each now reads `panelTaskId()` when it acts; the render subscribes only to `usePanelHasTask()`, which changes when a task opens or closes, and the two effects that react to a new docked task use `watchPanelTaskId`, a subscription that calls back without a render (and skips a `setSelectedId` to the id already selected, which made React render the list once more to bail out). Measured with 2,000 rows beside the side panel (`sidePanelFollow.perf.test.tsx`): list renders per `j` from 3 to 1 (2 on the first press, when the panel's first task opens), row renders 2, as without the panel. Alternative: memoize the list body so the extra renders are cheap. Rejected: the work is in the list's hooks, not its rows, and the extra renders have no reason to happen.

## Data model

None. The choice stays a device preference in `localStorage`, never synced; nothing is written to tasks or user prefs.

## Interface budget

No new chrome row, task property, sidebar destination, scroll region or shortcut: one more option in an existing select, and a double-click on rows that already open. The settings row's description stays one sentence plus "This device only.".

## Size

No dependency. About 0.3 KB gzip in the first load (entry and static imports 689.7 to 690.0 KB of 694 KB; the entry chunk unchanged at 141.4 KB). The budget in `web/bundle-budget.json` is not raised.
