# Design

## Context

- `performance-10k` (design D8) found: opening the 2,000-task project spends about 1.5 s in style and layout of every row (a passive effect that reads `scrollLeft` forces it before the first frame, but the browser would do it anyway); one completion or pulled edit re-reads the 10,000 tasks of the shared snapshot and re-renders much of the list (about 1.5 s of React work with style and layout); the cursor near the top looked for pinned headers among every element (fixed there).
- A first try of D1 on the development machine (`.row-pad` with `content-visibility: auto`, one desktop run): opening the project 1,520 → 834 ms, a cursor move 230 → 57 ms (p95), a completion 3.1 → 2.6 s; the writes need D2 and D3.
- Trying Dexie's live-query cache (a plain `toArray()` instead of a `filter()` cursor, so Dexie can update the cached result in memory) cut a completion from 4.8 s to 1.5 s, but eleven unit tests saw stale lists after the database was deleted and opened again; it was left out of `performance-10k`.

## Decisions

**D1. Rows off screen cost nothing, and a long list draws its top first.** Two parts, neither of which takes a row out of the document for good:

- **`content-visibility: auto`** on list rows (`.row-offscreen`, not cards): the browser skips layout and paint of rows far from the viewport, while every row stays in the DOM, so keyboard focus, `j`/`k`, find in page, drag and drop and assistive technology work as before. `contain-intrinsic-size: auto 2.25rem` keeps the scrollbar stable and `overflow-clip-margin` keeps focus rings drawn. A dragged or dropped-on row, a row edited in place and an expanded row draw normally, so nothing they show beyond the row is clipped (the row under the cursor keeps the rule, D6).
- **Progressive mounting** (`useRowLimit` in `ListGroups`): a list of more than 150 rows renders its first 150 in the first commit and 150 more in each idle callback, so a 2,000-row project shows its top in one frame and has every row in the document a few frames later. The row the cursor is on is drawn at once even if it lies further down. This is the "windowing" the proposal kept in reserve, without its costs: nothing is ever taken out again, so focus, find in page and drag and drop only ever wait for the first fraction of a second after opening a list.
- **Sibling positions written by the list** (`SiblingAria`): `aria-posinset` and `aria-setsize` of a tree list changed for every row when one row left, which as React props re-rendered all 2,000 rows; the list now writes the same attributes on the rows when the positions change. Rows keep `aria-level`. Screen readers read the same attributes as before.

Not in WebKit (release 0.22.0): its layout check twice found the rows on screen still skipped after the Inbox loaded (the list drawn blank, a tap beside the checkbox landing on the row), which no local run reproduced. `.row-offscreen` falls back to `content-visibility: visible` where `hanging-punctuation` is supported (WebKit alone), so Safari draws every row as before; progressive mounting and the other parts still apply there. To be tried again with a WebKit fix or a reproduction.

Windowing proper (rows outside the viewport removed from the DOM) was not needed and is not done.

**D2. The tasks snapshot applies changes.** `lib/taskSnapshot.ts` keeps every stored task (sorted by id) and listens to Dexie's `storagemutated` event: when the changed primary keys of `tasks` are named one by one (up to 1,000), it reads them with one `bulkGet` and replaces, adds or removes those rows in a copy of the array; anything else (a range, a cleared table, a new database, more keys) reads the table again. Rows a write did not touch keep their objects, so memoised rows and derived lists see no change. The projects and workspace state stay one live query. During a long pull the changes are noted and applied after 2, 4, 8, 16 s, as for the other snapshots. Dexie's own live-query cache was tried instead and dropped: under load, eleven tests saw stale lists.

Two places had relied on the old snapshot arriving late, and are fixed so that they hold whatever the timing: the triage card claims the task it is deciding before the write (it was dropped from the queue by the faster update, so the card skipped a task), and the Calendar's and Upcoming's query filter draws no task until the stored query is read (it drew every task for a moment).

**D3. The tick before the round trip.** `lib/pendingDone.ts`: completing a task (a click or a key in the list) records the wanted state for that row; the row draws it at once and stops as soon as its stored data changes (its field clocks object is new) or after 10 s, so a failed write shows the stored state again and a series that moved on shows its next occurrence.

**D4. Windowing as a last resort**, in a later change, only if D1–D3 leave the list budgets unmet on the CI runner. After D6 the one list budget still over on the CI runner is completing a task (desktop 131–141 ms, phone profile 201–207 ms on runners about 1.4 times slower than the first measurements). What is left is the browser's own work in each frame around the click: with 2,000 rows under `content-visibility: auto`, every frame in which something moves (the hover that shows the row's actions, the press, the tick) recomputes the visibility of all 2,000 rows (about 4–7 ms a frame on a computer, 15–20 ms in the phone profile), and a completion spans two or three such frames. A measured alternative: grouping rows into blocks of 100 with `content-visibility` on the block cut that cost by about a quarter, but it splits the list element that screen readers announce. That is the windowing decision this design leaves to its own change.

**D5. Nothing outside a write's own rows moves.** Measured after D1–D3, a cursor move, a tick and a remote edit still made all 2,000 rows again, and each sync derived the 10,000 tasks again:

- The list keeps each row's element while nothing that row shows changed (`useRowRenderer`): the list-wide inputs are compared once, and each row compares its own answers (cursor, tick, editing, expanded, drop line, departure). React passes the kept elements over without comparing their props.
- Every exchange stored the workspace directory again, which woke every live read of the workspace state: the task snapshot derived its sets again and projects and labels came back as new objects, so every row's project and labels changed. The directory is now written only when it differs, the snapshot derives its sets only when a project's place, its Trash state or the workspaces change, and the project, label, view and membership snapshots keep unchanged rows as the same objects (`keepRows`).
- The sidebar's saved-view and workspace counts are computed after the write's own frame (`useDeferredValue`).
- The command bar folds its 10,000 tasks for matching while it waits for the first keystroke, sorts only the matches it shows, and scrolls its list to the top for the first option instead of laying out the whole page behind it.
- The cursor's scroll looks for sticky headers without walking into rows, and the tab title keeps the heading it found instead of looking it up on every frame.
- Completing a plain task read every task to find its subtree (the Undo plan and the plain completion); it now reads the subtree through the parent_id index, and only a series, whose roll looks at its occurrence records, reads them all. Ten quick ticks had queued about 5 s of these reads (CPU slowed 2x) in front of the next sync.
- A press on a row (the completion circle) cleared drag-and-drop marks by searching the whole page on release; only a drag that lifted marks anything, so only that one clears.
- Quick add re-read its field's scroll after every render, a layout of the whole page; it now does so when its text changes.
- The benchmark opened the saved view straight from the 2,000-row project, which timed taking those rows down (about 130 ms on a computer); it now starts from Today, as opening the project does. Leaving a very long list stays a cost of its own.
- The benchmark's remote edit compared the page's monotonic clock with the sender's wall clock, 0.9 s apart by then; both are wall-clock times now.

**D6. Incremental list updates.** After D1–D5 the CI runner still measured a completion at 117 ms on a computer and 250 ms in the phone profile (budgets 100 and 200), a cursor move in the phone profile at 213 ms (150) and a search keystroke there at 209 ms (200). Traces of the phone profile showed where the time went: after each write the list derived its rows and groups again and every row compared the new progress, blocker, flow and habit maps as a whole; the sidebar counted every saved view and workspace again; and a tick that landed during that work waited for it. Each frame also paid for things no write needed:

- **Only the changed rows and their groups are new.** `keepGroups` (`lib/listGroups.ts`) keeps, from one derivation to the next, every row that shows the same task in the same place, every group whose rows and heading did not change, and the whole list when nothing changed; what is derived from the groups (rows, sibling positions, the time column) is then kept too. A kept row keeps its element when its own answers are the same: its cursor, tick, motion, drop line, progress, blockers, the step it waits for, its habit, read-only state, project and assignee (`sameForRow`), compared only for the maps a write renewed. Sibling positions are written only on rows whose position changed.
- **Counts over every task wait for the writes to stop.** The sidebar's saved-view counts and the workspace counts follow the tasks once they have been unchanged for a second, in an idle moment (`useSettledValue`), instead of once per write.
- **The cursor row keeps `content-visibility: auto`.** It draws nothing outside itself (its marker is inside the row), and taking it out of the rule and back on every cursor move made the browser recompute what it skips for the whole list (about 50 ms of pre-paint a key in the phone profile).
- **Cut titles are measured where they are drawn.** A title in a skipped row is neither measured nor observed until the browser draws it (`contentvisibilityautostatechange`): reading its size laid out that one row, 150 rows a drawing step took about half a second in the phone profile, and observing 2,000 titles cost about 10 ms each frame. Where the browser cannot say what it skips, every title is measured as before. That measuring had also laid out every row once, so each row's height was known; rows never drawn now stand at the average height of the rows drawn first (`RowEstimate`, `--row-estimate`), which keeps End and the scroll bar landing at the end of the list, and a reveal of a skipped row (the cursor) is checked again in the next frames, once its neighbours have their own height.
- **The tab title looks for a heading only when one is added**, instead of scanning the page once a second where the phone bar names it.
- **The command bar's index is prepared before it opens.** In an idle moment a few seconds after the app starts, the bar's task, project and note texts are folded a few milliseconds at a time (`PaletteWarmer`) into a cache keyed by the text, which every later opening and data change reuses; the note index resumes where it stopped instead of reading every note again per step, and typing on compares only the options that matched the shorter text (from two letters on, where a longer text can only match fewer). The bar folds its whole source when it opens (mostly lookups in that cache) instead of in idle moments a quick first key never waited for, keeps each task's note entry per task row, and works out Today's earlier tasks once per data change instead of with every query.
- **The benchmark waits until every row is drawn.** It took a second without a new row as "drawn", and in the phone profile one drawing step held the page for over a second, so the cursor and the completions ran while rows were still being added; it now waits for ten checks in a row with the same count.

**D7. A completion draws its own row.** After D6 the nightly measured completing a task on a computer at 120–143 ms (budget 100) on five nights in a row, every other list budget within its limit. Logging every sample (the p95 of ten is their largest) showed where: the first two completions of each run took 100–150 ms, the next eight 35–60 ms. Every list subscribed to the whole map of running departures, so the click that started one drew the list again in its own frame: its ghost bookkeeping over every row, each of the 2,000 rows comparing its answers, and the layout effects of a list commit, before the tick could paint. Now:

- A row follows its own task's departure (`useDeparture`): starting, ending or turning into a restore draws that task's rows only.
- The list wakes only when a departure ends or Undo turns it into a restore (`useDepartureEnds`), to drop its ghost. A row that leaves the list's data is put back at its place in the lists last drawn (`withGhosts` keeps them), so the list never has to draw when a departure starts.

On the CI runner (one run of five, 2026-11-06) the completion's p95 went to 86 ms on a computer (the later samples 16–39 ms) and 165 ms in the phone profile; the run without the change on the same day measured 136 and 269. Nothing about the rows, their attributes or the list elements changes, so screen readers get the same list (the `a11y-list` check of the benchmark). Windowing (D4) stays unneeded.

## Risks

- Paint containment clips what a row draws outside itself: checked on every row control and the drop line (`ui-check` visual regression covers the row stories).
- A patched snapshot that diverges from storage shows wrong data: the fallback to a full read on anything unexpected, and the equality tests.
