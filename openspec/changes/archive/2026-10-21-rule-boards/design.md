# Design

## Context

See proposal.md for motivation. The pieces this change builds on:

- A dashboard is a view with `kind: 'dashboard'` whose `panels` are the ids of saved **list** views (`openspec/changes/archive/2026-10-10-custom-views`, D3). `web/src/app/DashboardView.tsx` evaluates every panel in one pass (`evaluateViews` in `web/src/lib/views.ts`), renders each as a `section[data-panel-index]` with `TaskRow`s, and owns the `view`-scope shortcuts `dashboard.panels`, `dashboard.down/up`, `dashboard.open`, `dashboard.open-view`, `dashboard.complete`, `dashboard.escape` (`web/src/lib/shortcuts.ts` lines 248–254). Selection for bulk actions is deliberately not offered on dashboards (bulk-actions "Where selection is available").
- The op schema (`internal/sync/ops.go`, `Schema["view"]`) lists twelve view fields with plain kinds; the server stores every entity field-by-field (`fields` table), so a new field needs no SQL migration. REST-only rules live in `internal/httpapi/views.go` (`checkView`, called from the generic collection handlers for create and patch), and `docs/api.md` and `docs/sync.md` document the field table.
- The client stores views in Dexie `views` (`web/src/lib/db.ts`, indexed by `id, position` only), with `VIEW_DEFAULTS` in `web/src/lib/ops.ts` filling fields a row never received. `applyOps` writes any field named in an op onto the row, so a field this build does not know is kept, not dropped.
- Drag and drop is the library-free primitive in `web/src/lib/dnd.ts`: `beginDrag(e, {label, onDrop})` and `data-drop-target` keys; the project board uses keys `section:<id>` (`web/src/app/BoardView.tsx`, `web/src/app/task-list/useListDrag.ts`). `TaskRow` takes `onPointerDown` and sets `data-draggable`.
- Field changes on tasks are planned by pure functions that encode the single-task rules: `planPriority`, `planDue` (keeps the time, un-parks, `null` ends a recurrence), `planLabels` (reads the array just before writing, writes it whole), `planComplete` (recurring roll-forward, subtree), `planReopen` in `web/src/lib/bulk.ts`; `planProjectChange` in `web/src/lib/ops.ts` (clears the section on a project change, moves the subtree, copy-and-tombstone across sharing scopes). `applyBatch` in `web/src/lib/undo.ts` writes one `mutateMany` and stores the inverse with per-field clocks; `undoActions.ts` wraps single-task actions as undoable batches with `source: 'action'`; `showUndoToast` in `web/src/app/bulk/toastStore.ts` shows the toast that `UndoToast.tsx` renders with `Ctrl/⌘+Z`.
- The filter grammar is frozen by `filter-queries`; both parsers (`web/src/lib/filter/parse.ts`, `internal/filter`) run the examples of `docs/filters.md`. The four Eisenhower queries were checked against `internal/filter.Parse` while drafting this change and parse.
- Interface budget (docs/interface-guide.md): two rows of chrome above a list's first item, seven task properties, six sidebar destinations, three scroll regions, every shortcut registered without conflict (`conflicts()` in `web/src/lib/shortcuts.test.ts` compares entries that can meet; `view`-scope entries meet only in views that host the other scope).

## Goals / Non-Goals

**Goals:**
- One additive field, one rule planner, one drop handler; everything else is reuse of the bulk planners, the undo store, the dnd primitive and the dashboard component.
- A rule is data the user can read back in one line ("Priority 1, due today") and that the server can validate without knowing task semantics.
- The Eisenhower board is nothing special once created: four views and a dashboard, editable like any other.

**Non-Goals:**
- No change to the grammar, the project board, the panel layout (grid of panels, two columns from `md`, three from `2xl`), the sidebar, or the selection model (ticking stays off on boards).
- No rule evaluation on the server, in the CLI, in MCP or the assistant. No automatic (timed, on-save) rules.
- No inverse "leave" rule on the source column (D3).

## Decisions

**D1. The rule lives on the list view, not on the dashboard.** `view.on_drop` is a field of the saved filter shown in the column. The rule says "what makes a task belong to this filter", so it belongs with the filter and holds wherever the filter is a column. Alternative: a per-dashboard map from panel id to rule. Rejected: the schema has no map kind (`panels` is a string list), a map would be one register fighting over six rules, and the case it serves (one filter with different rules on two boards) is served by saving a second filter.

**D2. Shape and kind.** `on_drop` is `null` or an object:

```
{ add_labels?: string[], remove_labels?: string[], priority?: 1|2|3|4,
  due?: 'today'|'tomorrow'|'next-week'|'clear', start?: 'someday'|'clear',
  section?: { project_id: string, section_id: string | null }, state?: 'complete'|'reopen' }
```

A new kind `kRule` in `internal/sync/ops.go`, beside `kDue` (the other structured value): `null`, or a JSON object whose keys are exactly from this set, with `priority` 1–4, the enumerations as listed, at most 32 ids per label list (each at most `MaxIDLen`), a `section` object with a non-empty `project_id`, and no unknown key. Sync checks shape only (like every kind: it never checks that ids exist); REST additionally checks that labels exist and are not deleted, that the section exists, is not deleted and belongs to `project_id`, and that the view is a list view, the way `checkView` already resolves `panels`. Whole-object LWW, like `due` and `panels`. Alternative: a JSON string in a `kString` (precedent: `field.options`, `user_prefs.sidebar_destinations`). Rejected: the API and export would show an escaped string for a value scripts will want to write, and the server could not validate it without decoding it anyway. Alternative: one view field per rule kind (`drop_priority`, `drop_due`, …). Rejected: seven fields that must be edited together and would converge separately, producing rules nobody set.

Unknown keys: the server refuses them (a new key is a schema addition, server first, like a new field); a client that meets a key it does not know keeps it in the row (`applyOps` writes what it receives) and ignores it when planning. `on_drop` is not a content field (ids and enumerations only), so `internal/e2ee.ContentFields` and `CONTENT_FIELDS` are unchanged; the template's view names and queries are content and are encrypted as every view's are.

**D3. No source rule.** A drop runs the destination's rule only. Reasons: the destination rule is the full meaning of "this task is now in this column"; a "leave" rule would have to be a second rule per column, and two columns' rules could contradict each other (source removes a label the destination adds), with the loser decided by patch order; and with exclusive filters (the Eisenhower matrix, any set of columns that partition on the fields the rules set) the task leaves the source by matching the destination. When filters overlap, a task honestly shows in both columns. Alternative considered: compute the inverse of the source rule automatically. Rejected: "add label" inverts to "remove label", but "due today" has no inverse worth guessing.

**D4. The planner is pure and reuses the bulk planners.** `web/src/lib/rules.ts` exports `planRule(task, all, rule, ctx): Change[]` which, in this order, calls `planLabels` for each id in `remove_labels` then `add_labels` (ids of deleted labels skipped), `planPriority`, `planDue` (`clear` → `null`, which also ends a recurrence as the bulk Date → No date does), the start change (`someday` → `parkTask`'s patch: start someday, due null, evening false; `clear` → `{start: null}`), `planProjectChange` for `section` (a different project moves the subtree and clears the section unless the rule's section is of the new project; a shared project goes through the copy-and-tombstone path with `cross`), and `planComplete`/`planReopen` for `state`; the per-task patches are merged with `mergeChanges`. A change the task already has produces no patch, so an empty plan means "already matched". `describeRule(rule, labels, projects, sections): string` gives the one-line wording used by the panel's accessible description, the Arrange row and the toast ("Priority 1, due today"; "Adds errand, removes waiting"; "Section Doing of Home"; "Completes"). Unit tests pin both against the spec scenarios.

**D5. Drop and keyboard move share one action.** `dropOnPanel(taskId, view, ctx)` in `web/src/lib/undoActions.ts` reads the task and its subtree (`readTicked`), runs `planRule`, and applies through `applyBatch(…, {source: 'action', label})`; the label is `t('Moved to {column}: {changes}')`. `DashboardView` calls it from the dnd `onDrop` for target keys `panel:<viewId>` and from the new shortcuts `dashboard.move-prev` / `dashboard.move-next` (`Shift+←` / `Shift+→`, scope `view`, views `['dashboard']`, section `filter`), which move to the nearest panel in that direction whose view has a rule and then set the selection to the task in that panel. Panels whose view has no rule carry no `data-drop-target`, so the dnd primitive never lights them. The `conflicts()` test covers the registration: `board.move-*` (scope `board`) and `month.focus` (views `['month']`) cannot meet a `['dashboard']` entry. Cards get `onPointerDown={(e) => beginDrag(e, {label: task.title, onDrop})}` as the project board does; a card dropped on its own panel changes nothing.

**D6. The held card is interface state.** After a drop, `DashboardView` compares the task against the destination's compiled predicate (`compileView` in `web/src/lib/views.ts`, today module-private and used by `evaluateViews`, exported for this). If it does not match, the task id goes into a `held: Map<panelId, taskId>` React state; the panel renders that task first with a `Badge` "Not matching" and the toast text gets `t('It does not match the column’s filter.')` appended. The entry is dropped when the component unmounts (leaving the board), when the task next changes (the row's `_clock` differs), or when it starts matching. Nothing is written or synced for it.

**D7. Rule editor in Arrange.** The existing Arrange list (`ol[aria-label="Arrange panels"]`) gets a **Rule** button per row that opens a `Dialog` with one control per rule kind: labels via the existing `LabelPicker` in two groups (add, remove), a priority `select` (Keep, 1–4), a due `select` (Keep, Today, Tomorrow, Next week, No date), a start `select` (Keep, Someday, Clear), section via the project `Combobox` (`ProjectPickerField`) followed by its sections, and a state `select` (Keep, Complete, Reopen); a "No rule" button clears it. Save writes `setOnDrop(viewId, rule | null)` in `web/src/lib/views.ts`, one `mutate('view', id, {on_drop})`. Outside Arrange, a panel with a rule shows an `Icon name="zap"` beside its count with the wording as `Tooltip` and `aria-describedby`; `zap` is one icon vendored from Lucide into `web/src/ui/icons/lucide.ts` and `names.json` (about 0.2 KB, used by this screen so `usage.test.ts` needs no reservation). Alternative: edit the rule from the saved filter's own header. Rejected for now: the drop happens on the board, so that is where the rule is discovered and changed; the field is still reachable through the API.

**D8. Templates are data.** `web/src/lib/boardTemplates.ts` exports `BOARD_TEMPLATES: BoardTemplate[]` with `{id, name, description, columns: {name, query, color, on_drop}[]}`; the only entry is `eisenhower` with the four columns of the spec. `createBoardFromTemplate(template, name)` in `web/src/lib/views.ts` builds one `mutateMany` batch: four `view` rows (`kind: 'list'`, `pinned: false`, positions after the last view, `on_drop` set) and one `view` row (`kind: 'dashboard'`, `pinned: true`, `panels` the four ids), then navigates to the board. The client parses each query with `parse` before writing (as `createView` does with `checkQuery`), and a Go test posts the same four queries to `/api/v1/views` so the two parsers are proven on them. **New board** in `ViewsView.tsx` opens a `Dialog` listing "Empty board" and the templates as radio rows with their descriptions, then the existing `NamePrompt` (prefilled with the template's name).

**D9. Older clients.** A client without this change never offers a drop on a board, keeps `on_drop` in the row when it syncs the view, and its edits of other fields are per-field ops, so the rule survives them (spec "Older client receives a rule"). The server must be upgraded before clients (an old server rejects the unknown field in `Apply`), which is the order the single-binary deployment already has.

## Data model

- Server `Schema["view"]` gains `"on_drop": kRule`; `docs/sync.md` view rows gain the field; `docs/api.md` "View fields" gains a row. No migration (field store), no rename, no removal.
- Client `View.on_drop: OnDropRule | null`, default `null` in `VIEW_DEFAULTS`; `VIEW_FIELDS` in `types.ts` lists `on_drop` among the view fields the export and import carry. No Dexie version bump (no index).
- Writes: the rule (one view field), the template (five view creates in one batch), and a drop's task field ops. All through `mutate`/`mutateMany`.

## Size and resources

No dependency. Web bundle about +7 KB gzipped: the planner and wording (~1.5 KB), the rule editor dialog (~3 KB), the template and chooser (~1 KB), drag wiring and the held card (~1 KB). Go binary about +15 KB for `kRule` validation and the REST checks. Runtime memory, image size and database size unchanged (one small JSON value per view that has a rule). A drop costs one predicate evaluation against one task.

## Interface budget

- Rows of chrome above a board's first panel: the page header, plus the Arrange list only while Arrange is on (as today): 1–2 of 2.
- Task properties visible by default: cards keep `TaskRow` unchanged; the "Not matching" badge appears only on a held card.
- Primary sidebar destinations: unchanged (the Eisenhower board is a pinned view in the Filters group).
- Vertical scroll regions: the content column only (1 of 3); the Rule dialog scrolls inside itself when open, as every dialog does.
- Shortcuts: `dashboard.move-prev` (`Shift+←`) and `dashboard.move-next` (`Shift+→`) registered in `web/src/lib/shortcuts.ts` with scope `view`, views `['dashboard']`; `conflicts()` must stay empty.

## Risks / Trade-offs

- [Overlapping filters leave a dropped task in both columns] → documented; the exclusive Eisenhower template shows the intended pattern, and the held-card marker plus the toast make a non-matching result visible rather than silent.
- [A rule that completes tasks is a destructive drop] → the toast's Undo restores it in one step, the rule's wording is on the panel, and completing is not part of any template.
- [A `section` rule on a shared project copies and tombstones the task] → it is the single-task move's behaviour (`planProjectChange` with `cross`), undone by the same inverse (bulk-actions "Undo a cross-scope move"); the wording names the project.
- [Two parsers must accept the template queries] → the template is tested on both sides with the literal strings, like the `docs/filters.md` examples.
- [The whole-object rule loses a concurrent edit] → a rule is a few choices set once; newer edit wins, as for `panels`.
- [Drag on touch inside a scrolling panel] → the dnd primitive's long-press threshold already distinguishes a scroll from a drag on the project board; panels stack on phones so the drop target is below or above, reachable by scrolling while dragging as `dnd.ts` supports.

## Migration Plan

Additive. Deploy the server (it accepts and stores `on_drop`), then the web bundle ships with it in the same binary. Rollback: reverting the binary leaves `on_drop` values in the field store, which an older server would reject only for new ops of that field; existing rows are unaffected and older clients ignore the field. Docs screenshots: a new `docs/images/eisenhower-light.webp` / `-dark.webp` from `scripts/docs-screenshots.mjs`.

## Implementation notes

- **Pin model (sidebar-favourites).** Since sidebar-favourites, a saved filter is a favourite by its `pinned` flag, and a pinned view that `user_prefs.favourites` does not name lists after the named entries, by position; `reorderView` orders among all saved views. `createBoardFromTemplate` follows `createView` (new saved filters land in Favourites by the flag alone): the four filters are written with `pinned: false` (listed in the Filters group, not in Favourites) and the board with `pinned: true`, all five with consecutive positions after the last view (filters in matrix order, then the board), in one `mutateMany`. No `favourites` entry is written, so the board shows in Favourites after the entries the user ordered until they move it; `pin()`/`unpin()` work on it as on any filter.
- **Logical today.** The drop and the keyboard move resolve `due: today|tomorrow|next-week` against the board's `ctx.today`, which `useViewData` takes from `useToday()` (the logical today of day-boundary); `dropOnPanel` falls back to `logicalToday()`, never to `todayISO()`. "Next week" is `dateOfPick('next-week')`, the first day of the following week per the user's week start.
- **Filter grammar.** The four Eisenhower queries were re-checked against `internal/filter` and the web parser as they are after task-origin and time-tracking added terms (`origin`, `tracked`): `TestViewsAcceptEisenhowerQueries` posts them (201 each) and `boardTemplates.test.ts` parses them.
- **Planner order.** `planRule` applies labels, priority, due, start and state first and the project/section move last (D4 listed section before state): the move is then planned from the task with the rule's other changes on it, so a move across sharing scopes copies a task that already carries them. A completion rule on a completed task, or a reopen rule on an open one, plans nothing (the bulk `planComplete` would otherwise toggle). No-op fields are dropped against the rows read just before planning, so an empty plan means "already matched".
- **Wording.** `ruleParts` returns lower-case phrases (the toast: "Moved to {column}: priority 1, due today"); `describeRule` gives the sentence-case line for the panel description, the Arrange row and the editor's summary. A deleted label is left out of the wording; the editor shows it as a "Removed label" chip that can be taken out.
- **`dropOnPanel(taskId, view, {filter, names, now?, today?})`** returns `{entry, label, taskId, matches, changed, row}`: `taskId` is the copy's id after a cross-scope move, `row` the task after the batch (its clocks let the board tell a later change apart). Matching is computed with the exported `compileView` on the task as the batch leaves it. Nothing to change shows a toast "{task} already matches {column}" without Undo.
- **Board screen.** Drops and held cards live in `web/src/app/useBoardDrop.ts` (one held card per panel, keyed by the panel's view id; dropped when the board unmounts, when the task's clocks change, or when the panel's own results include it). The dashboard's selection is now a task id within a panel, so a card moved by `Shift+←/→` stays selected in the destination. The panel's rule wording is an `sr-only` element referenced by `aria-describedby` ("On drop: …") and the bolt's tooltip.
- **Rule editor.** `LabelPicker` is bound to one task, so the editor uses the design-system `Combobox` directly for the two label lists; the project is `ProjectPickerField` without the Inbox ("Keep" is the none option), the section a select of that project's live sections. The choices (priority, date, start) come before the label fields so the dialog's first focus does not open the label list. File: `web/src/app/RuleEditor.tsx`.
- **New board.** The chooser is `web/src/app/NewBoardDialog.tsx`; the template's chooser title is "Eisenhower matrix" and its default board name "Eisenhower" (`BoardTemplate.title` and `.name`). The command palette's "New dashboard" still creates an empty board directly. Template colours come from the app's label palette.
- **Server.** `kRule` is checked in `internal/sync/rule.go` (`ParseRule`, also used by REST). Every view representation (list, get, create, patch, export) carries `on_drop`, `null` when unset, through the read-side annotation in `annotateProjects`; create writes no `on_drop` op of its own, so views made through the client still write the same twelve fields.
- **Icon.** `zap` was already in `web/src/ui/icons/site-icons.json` (a website-only icon); now that the app vendors it, it is dropped from that file as `scripts/site-bundle.test.mjs` requires. The path is identical, so the site's sprite does not change.
- **Not regenerated here.** Visual baselines (`make ui-baselines` needs Docker): the new stories "Screens/Board of filters" (Eisenhower, Rule editor) have none yet, and the `foundations-icons--all` baselines are stale because `zap` was added; both come from CI's ui-check report. The stories were rendered once in the bundled Chromium. The docs screenshots `eisenhower-light/dark.webp` were generated with `node scripts/docs-screenshots.mjs eisenhower`; no other image was regenerated.
