# Proposal

## Why

An assistant planning someone's week can only write `due` today: `docs/api.md` promises an `agent` token `deadline`, `start`, `evening` and `blocked_by`, but no tool in the agent registry accepts them, so the agent REST routes refuse each with `403 insufficient_scope` and the MCP tools, the in-app assistant and `ot` have no way to set a deadline, defer a task, park it in Someday, mark it for the evening or make it wait for another task (issue #198). The new `location` field (`task-locations`) is in the same position: its proposal left the CLI and the MCP tools for a follow-up. Every missed planned day becomes "overdue", which is the opposite of what the Open Loops method teaches. At the same time there is no way to keep one shared project (a client's, a partner's) away from the other members' assistants, which the roadmap lists as a future idea.

## What Changes

- **Planning fields in every agent write path.** `create_tasks` items and `update_tasks` updates accept `deadline` (`YYYY-MM-DD` or null), `start` (`YYYY-MM-DD`, `"someday"` or null), `evening` (boolean), `blocked_by` (a list of task ids) and `location` (the `task-locations` object, or null), validated exactly as the sync and REST paths validate them (a calendar date that exists; at most 50 distinct blockers of the same sharing scope that are not the task itself and close no cycle; the location shape and ranges), with every refusal naming the item and the field and changing nothing. The agent REST routes (`POST /api/v1/tasks`, `PATCH /api/v1/tasks/{id}`) route the same five fields to those tools, so the `docs/api.md` table becomes true, and gain `location`. No new tool: `update_tasks` already takes up to 50 updates, so "park these five in Someday" is one call.
- **Planning fields in every agent read.** Task results of the read tools, the write tools, the `opentodo://` resources, the agent REST responses and the in-app assistant's reads carry `deadline`, `start`, `evening`, `blocked_by`, a derived `blocked` (true while any blocker is open) and `location` (its `name` and `address` inside the untrusted-text marking, its coordinates and `place_id` outside; `null` and `encrypted: true` for an encrypted account). `list_tasks` and the views resources gain a `blocked` filter and the views `someday` and `anytime`, so an assistant can walk the Open Loops places (Next, Later, Waiting, Someday) the way the app does.
- **`ot add` and `ot edit`** gain `--deadline <date|none>`, `--start <date|someday|none>`, `--evening` / `--evening=false`, repeatable `--blocked-by <ref>` (edit replaces the list; `--blocked-by none` clears it) and `--location <saved location name or id | "lat,lon" | none>`; `ot list` gains `--someday`, `--anytime` and `--blocked`, prints a `BY` column (the deadline) when a listed task has one, and the `task` JSON schema lists the five fields. The skill file and `ot schema` describe them.
- **The in-app assistant** knows the vocabulary (do-on date versus deadline versus start versus Someday versus evening versus waiting for) in its fixed instructions, the built-in skills use it (plan-week sets start dates and deadlines instead of forcing a do-on date on every task; weekly-review uses `blocked_by` for Waiting and `start` for Later; triage-inbox may park or defer), and the proposal review shows each planning change in plain words ("Deadline 6 Nov", "Starts 3 Nov", "Someday", "This evening", "Waits for “Order parts”", "At Mum's") like it shows due dates today.
- **Encrypted accounts.** `deadline`, `start`, `evening` and `blocked_by` are plaintext by design and work for every account. `location` is a content field: for an encrypted account it is offered as ciphertext only, plaintext is refused with `encryption_enabled`, and reads carry no location members, exactly as `origin` is handled today.
- **Keep a project away from AI assistants.** The owner of a project, or an admin of a shared one, can switch on **Keep away from AI assistants** for that project (in the share dialog and the command palette). While it is on, the project, its sub-projects and everything in them (tasks, sections, comments, attachments, time entries, field definitions and values, counts) are left out of every read and write of every assistant surface for every member: the MCP tools, resources and prompts whatever the token, the agent REST routes, the in-app assistant, and so `ot` and `ot mcp` with an `agent` token. A write that names an excluded entity is `not_found`, indistinguishable from a deleted one. The switch is server state like membership (never an op, never synced, needs a connection to change, shown from a cached copy offline), is audited as `project.agent_access`, and does not touch ordinary REST, CalDAV, the export, webhooks or sync, which are not assistants.

Out of scope: a tool that creates or edits reminders (the "Related" note of issue #198; relative and deadline reminders already follow the dates these tools write); new write tools (`defer_tasks`, `set_deadline`) or a bulk `plan_tasks`; quick-add phrases for start and deadline in `ot add --natural` beyond what the grammar already parses; `location` on CalDAV; a per-member exclusion (one member hiding a shared project from their own assistant only); excluding a label or a saved view; hiding an excluded project from the device relay of `mcp-device-relay` (that change inherits the exclusion through the registry when it is built); any change to the sync protocol or the op schema. ROADMAP.md: closes the "Keep a shared project away from AI assistants" future idea and completes the agent surface of `deadlines`, `someday-and-evening`, `task-dependencies` and `task-locations`; no new environment variable; no op-log format change (**not BREAKING**).

## Capabilities

### New Capabilities
- `agent-project-exclusion`: the per-project "Keep away from AI assistants" switch: who may set it, its routes, what it hides from which surfaces, inheritance by sub-projects, offline display, audit and demo behaviour.

### Modified Capabilities
- `mcp-server`: added requirements for the planning fields and the location in write tools, in tool results and resources, and the new views and filter of `list_tasks`; the encrypted-account rule for `location`.
- `account-access`: "Agent content routes" lists the five fields an `agent` token may now send on the task routes.
- `cli-client`: "Add and edit tasks" gains the planning flags; added requirements for the list filters, the `BY` column and the schema.
- `in-app-assistant`: added requirement for planning changes in proposals and the review wording; the assistant's reads respect the exclusion.
- `assistant-skills`: added requirement that the built-in skills use the planning fields and never see an excluded project.
- `audit-log`: added requirement for the `project.agent_access` events.

`http-api` needs no delta: its task representation and write-through already cover the five fields for every token; the agent-token restriction lives in `account-access`. `task-locations` (open, archived before this change is applied) needs no delta: its "Task location" and "Location validation" requirements are reused as written.

## Impact

- Server: `internal/agenttools` (write_tasks.go, data.go, read.go, write_helpers.go, skills.go, a new exclusion check in the snapshot loader and a new store for the switch), `internal/httpapi/agent_rest.go`, `internal/mcp` (resources, views), `internal/assistant` (system prompt, loop context), `internal/audit` (one event name), `internal/store/migrations` (one additive table `project_agent_exclusions`), the `/api/v1/me` payload and two new routes under `/api/v1/projects/{id}/agent-access`.
- CLI: `internal/cli/cmd_tasks.go`, `schema/task.json`, the embedded `SKILL.md`, `ot schema` output.
- Web: `web/src/lib/assistant.ts` (review wording), `web/src/app/ShareDialog.tsx`, the command palette registry, a Dexie cache of excluded project ids next to memberships, translations.
- Docs: `docs/api.md`, `docs/mcp.md`, `docs/cli.md`, `docs/ai-limits.md`, `docs/assistant.md`, `docs/sharing.md`, `docs/account-security.md` (audit names).
- No new dependency. Binary and bundle growth are a few KB (measured in the tasks). Closes issue #198.
