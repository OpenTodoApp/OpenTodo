# Proposal

## Why

`rule-boards` gave a board column a rule that runs when a card is dropped on it, and that is the only rule the app has: everything else that repeats ("when I add the label waiting, move it to the Waiting section", "every Sunday evening, bring what slipped to Monday", "when a task in Client A is completed, tell the webhook") is still done by hand or by an external script against the API. The rule vocabulary, its planner, its editor and its validation already exist; what is missing is a place to keep a rule, something other than a drop to start it, and a server-side engine that runs it when no device is open. Rules on a timer or on other triggers were set aside on ROADMAP.md ("rules fired by a drop on a board column shipped in `rule-boards`; rules on a timer or other triggers stay set aside"); this change builds them, and becomes the home where scheduled assistant routines can later plug in.

## What Changes

- **Rules as a synced entity.** A new entity `rule` in the user's personal scope: a name, an on/off switch, one **trigger**, an optional **condition**, a set of **actions**, a position and the usual timestamps. It syncs field by field, works offline (a rule saved on the train is on the server when the device syncs, and the engine starts running it then) and converges by last-writer-wins; the trigger, the condition and the actions are each one whole value, like a column's `on_drop`.
- **Triggers.** Task created; task completed; task reopened; label added (which label); label removed (which label); assigned to me; moved to a project (which project, optionally which section); due date reached (the task's due time, 09:00 for a date-only due, in the user's time zone); became overdue (the user's day start on the day after the due date); and a **schedule**: every day, or on chosen weekdays, at a time in the user's time zone. A scheduled rule acts on every open task that matches its condition at that moment.
- **Conditions are structural, not query text.** A condition is a small set of predicates on fields the server can read for every account, encrypted ones included: project (one of, including sub-projects, or none), section, labels (any of, all of, none of), priority, due (none, set, today, overdue, within N days), deadline (none, set, within N days), start (Someday, deferred, none), evening, blocked, assignee (me, nobody, anyone), origin kind, habit, estimate and tracked time. The same predicates are evaluated on the device (so the editor can say "12 open tasks match now") and on the server (so the engine agrees), pinned by shared test vectors. Free text, custom field values and dates relative to a week are not predicates in this version.
- **Actions** are the on-drop vocabulary (add labels, remove labels, priority, due to today, tomorrow, next week, in N days or clear, start to Someday or clear, project and section, complete or reopen) plus: deadline (in N days from today, or clear), assignee (me, or clear), add a comment (a fixed text), send an in-app notification, and send to one of the user's webhooks (a new `rule.fired` event with the task and the rule). A rule's actions on a task are one batch of ordinary field operations, attributed to the rule in history and activity, undoable from the task's history like any other change.
- **The engine runs on the server's jobs leader**, next to the digest and the issue pollers: a post-commit observer turns committed batches into durable rule events, a worker evaluates them against the author's enabled rules and writes through `ApplyStrict` with device `rule:<rule-id>`, and a scheduler pass fires due-reached, overdue and scheduled rules against a per-rule watermark so a restart or a missed minute never fires twice or skips a firing. Every run is **idempotent** per (rule, task, occurrence), **loop-protected** (a rule never reacts to its own writes, and a chain of rules stops after three links), **rate limited** per account (runs per minute and per day) with a runaway rule paused and its owner notified, and recorded in a **run log** per rule (what fired, on which task, what changed, or why nothing did) kept for 30 days.
- **Kill switches.** The owner's `automations.enabled` (default on, `OPENTODO_AUTOMATIONS=off` as an optional override) stops every rule on the server; each user can pause all their rules at once; each rule has its own switch. Nothing runs on the demo instance.
- **Encrypted accounts.** Triggers, conditions and the structural actions work, because they read and write only ids, dates and enumerations; a rule's name is encrypted like a view's name. The server cannot write readable text into an encrypted account, so the **add a comment** action is refused for encrypted accounts, and a rule's in-app notification names the task by id, resolved to its title on the device.
- **Rules page and editor.** A Rules page (`/rules`, in the sidebar's More group, with "Go to Rules" and "New rule" in the command palette) lists the user's rules with their switch, a one-line summary ("When a task gets the label waiting → move to Waiting, priority 3"), when each last ran and how often, and opens a run history. The editor is one dialog: trigger, condition rows, the action controls of the board rule editor extended with the new actions, and a live "n open tasks match now" line. **Convert to a rule** on a board column (Arrange → Rule) and on a saved filter's menu starts the editor from that column's rule and the structural part of its query, naming any term it could not carry over.
- **API, CLI and MCP.** `/api/v1/rules` follows the collection conventions with validation of every id and enumeration; `GET /api/v1/rules/{id}/runs` lists the run log; `POST /api/v1/rules/{id}/test` dry-runs a rule against one task and returns the planned changes. `ot rules list|enable|disable|runs` and the read-only MCP resource `opentodo://rules`. Rules travel in the export and the own-format import.
- **Scheduled assistant routines are not built** but the hook is left: the actions object is a closed set the engine dispatches on, and a later change (`scheduled-assistant-routines`) can add an `assistant` action that hands the matching tasks and a prompt to the in-app assistant's loop. This change adds no model call and no assistant dependency.
- No new dependency. No new mandatory environment variable (`OPENTODO_AUTOMATIONS` is optional). The op log gains one additive entity; nothing is renamed or removed. Not **BREAKING**.

Out of scope: rules on shared projects (a rule is personal and acts as its author; a rule whose project action names a shared project is refused, see design D2); conditions on free text, custom field values or week-relative dates; an action that runs the assistant (`scheduled-assistant-routines`, later); rules that create tasks (templates and recurrence cover the daily cases); rules edited by the assistant or MCP write tools; the browser extension and CalDAV; a source rule when a task stops matching; retroactive runs over existing tasks (a scheduled rule or `test` covers it); e-mail as an action (webhooks can send mail).

Advances ROADMAP.md: the set-aside "rules (rules fired by a drop on a board column shipped in `rule-boards`; rules on a timer or other triggers stay set aside)" item ships; "scheduled assistant routines" stays set aside with its hook named here.

## Capabilities

### New Capabilities

- `automation-rules`: the rule entity and its validation, triggers, conditions and their shared evaluation, actions and their planning, the server engine (events, scheduler, idempotency, loops, limits, pauses, run log), the owner and user switches, the Rules page, the editor, converting a column rule, the REST routes, the CLI commands, export and import, and demo behaviour.

### Modified Capabilities

- `custom-views`: a new requirement "Convert a column rule into an automation rule" (added, so the "Dashboards" and "On-drop rule" requirements that `rule-boards` modifies and adds are not touched).
- `trash-and-history`: a new requirement "Rule writes are labelled in history" (device `rule:<id>` → "Rule (<name>)").
- `activity-log`: a new requirement "Rule operations form their own events" (like public link operations).
- `webhooks`: a new requirement "Rule events" (`rule.fired` as a subscribable event with the rule id in the payload, delivered like every event).
- `end-to-end-encryption`: a new requirement "Rules for encrypted accounts" (what works, what is refused; added rather than a change to "Encrypted and plaintext fields", which other open changes modify).
- `mcp-server`: a new requirement "Rules resource" (`opentodo://rules`, read-only).

## Impact

- Server: a new package `internal/rules` (the entity's value kinds and their validation, the condition matcher pinned by vectors, the action planner, the event observer, the durable queue, the scheduler, the worker, limits and the run log); `internal/sync/ops.go` (`Schema["rule"]`, three new kinds); a migration for `rule_events`, `rule_runs` and `rule_state` (watermarks, pauses) tables; `internal/httpapi/rules.go` (collection routes, runs, test, the owner setting) registered through the policy wrapper with `.demoDenied()` and a deny-list entry; `internal/tenant` (wiring and `StartJobs`); `internal/webhook` (the `rule.fired` event and `source: "rule"`); `internal/notify` (a `RuleSink` with "rule fired" and "rule paused" notifications); `internal/activity` and the history route (device labels and own events); `internal/e2ee.ContentFields` (`rule.name`, `rule.actions` is structural except the comment text, see design D6); `internal/settings` (`automations.enabled`); `internal/config` (`OPENTODO_AUTOMATIONS`); `internal/importer` (export and own-format import of rules); `internal/cli/cmd_rules.go`; `internal/agenttools/resources.go` (`opentodo://rules`).
- Web: `web/src/lib/types.ts` (`Rule`, `RuleTrigger`, `RuleCondition`, `RuleActions`), `web/src/lib/ops.ts` (`RULE_DEFAULTS`), a Dexie table `rules`, `web/src/lib/rules/` (the condition matcher and its vectors, the extended action planner shared with `on_drop`, the one-line wording, the query-to-condition converter), `web/src/app/rules/` (the Rules page, the editor dialog, the run history panel), `web/src/app/RuleEditor.tsx` (the new action controls), `web/src/app/DashboardView.tsx` and the saved filter menu (Convert to a rule), the sidebar's More group, palette commands, locale catalogues, stories and baselines.
- Docs: a new `docs/automations.md` and help page; `docs/api.md` (rules routes, the owner setting), `docs/sync.md` (the entity), `docs/webhooks.md` (`rule.fired`), `docs/e2ee.md` (what rules can do), `docs/saved-views.md` (Convert to a rule), `docs/cli.md`, `docs/mcp.md` (the resource), `docs/self-hosting/configuration.md` (`OPENTODO_AUTOMATIONS`), ROADMAP.md and CHANGELOG.md.
- Size: binary about +300 KB (engine, matcher, planner, routes); the web app's main bundle about +4 KB gzipped (types, the matcher used by the editor's live count, the More entry and palette commands) plus a lazy Rules chunk of about 10 KB gzipped; runtime memory on the server: per-account counters and one worker goroutine per tenant, the queue and the log in SQLite; database: one row per rule event until processed, at most 100 kept runs per rule, pruned after 30 days.
- API: `GET|POST /api/v1/rules`, `GET|PATCH|DELETE /api/v1/rules/{id}`, `GET /api/v1/rules/{id}/runs`, `POST /api/v1/rules/{id}/test`, `PUT /api/v1/me/rules/paused`, `GET|PUT /api/v1/settings/automations`; the `rule.fired` webhook event; `rules` in the export.
