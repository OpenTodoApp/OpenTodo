# Proposal

## Why

One account holds one undivided list of projects, labels and views, so a person who uses OpenTodo for work and for home either mixes both in one sidebar or runs two servers (issue #175: "organizations for example to separate Personal and Work ... but keep on the same instance"). Sharing is also person by person: a household of five or a team of eight re-adds the same people to every project, and nothing says who belongs together. Workspaces give an account separate rooms on one server, each with its own members and groups, so a project can be shared with "Family" in one step and so a work mention never offers a relative. This is the "groups" item the roadmap set aside and the first item of the "Next: ten more" list.

## What Changes

- **Workspaces.** An account has one or more workspaces: a *default workspace* that every existing account gets with everything it has today, plus workspaces the user creates ("Work", "Family"). A workspace has a name, an optional icon and colour, an owner, members with the roles `owner`, `admin` and `member`, and groups. Workspaces, their membership and their groups are server-side data like project membership (never an op); their names and member lists reach every device through the sync exchange and are cached for offline use.
- **Everything a user organises belongs to one workspace.** Projects, labels, saved views and dashboards, favourites, and tasks without a project each carry an additive `workspace_id` (absent or null means the default workspace). A task with a project belongs to its project's workspace. Older clients ignore the field and keep showing one undivided list, so an upgrade changes nothing for them. No op is rewritten, no id changes.
- **A current workspace per device.** The sidebar's header becomes the workspace control: the current workspace's name, opening a switcher that lists the user's workspaces with their Inbox and Today counts, "New workspace" and "Manage workspaces". Inbox, Today, Upcoming, Calendar, the method views, Completed, Trash, Updates, Filter, the sidebar groups, counts, search, quick add and the palette all show the current workspace only. The palette can switch workspaces by name and opens a result from another workspace by switching to it. The choice is remembered per device, never synced, and a new device opens the default workspace.
- **A closed directory per created workspace.** In a workspace the user created, a project can be shared only with members and groups of that workspace, mentions and assignee pickers list only them, and people are added to the workspace by email (existing accounts) or with a workspace invite link that can create an account under the server's sign-up rules. The default workspace keeps today's behaviour: any account on the server can be added to a project in it, so nothing a user shares today changes.
- **Groups.** A workspace's owner and admins create groups ("Family", "Design"), with any members of the workspace. The share dialog offers groups beside people: a project is shared with a group as one grant with one role. Adding someone to a group gives them every project the group is on; removing them takes those away, with their devices purging the projects as when a member is removed today. Effective membership is recomputed on the server from direct grants and group grants, the higher role winning, and is delivered to devices exactly like membership today, so nothing about the op log, convergence or the role checks changes.
- **Moving between workspaces.** A project's owner can move it to another of their workspaces; its sections, custom fields and tasks follow (they belong to the project), and its labels are re-matched by name in the target workspace. A task without a project can be moved between workspaces from its project picker, which lists every workspace's projects grouped by workspace and "No project" per workspace. A shared project whose workspace a member does not belong to is shown to that member in their default workspace, so a move never hides a project from anyone.
- **Everywhere else.** The export lists workspaces and carries `workspace_id` on projects, labels, views and tasks, and the own-format import restores them, mapping workspaces the importing account does not have to its default workspace with a note. The CLI gains `ot workspaces`, `--workspace <name or id>` and a profile default, and shows a workspace column where projects are listed. The MCP server gains `list_workspaces`, a `workspace` filter on `list_projects`, `list_tasks` and `search_tasks`, a `workspace_id` on `create_project`, and the workspace on every project in results. CalDAV lists the calendars of every workspace, with the workspace name before a project's name outside the default workspace. Webhook payloads carry the project's workspace id. Public links, calendar feeds, reminders, time tracking, the assistant and attachments are unchanged.
- **Encryption.** Workspaces are a partition inside one encrypted account: the account key covers every workspace, content stays encrypted, and workspace names and member lists are plaintext server data like project membership today. An encrypted account can create workspaces and move things between them, but cannot add members or groups to a workspace (409 `encryption_enabled`), exactly as it cannot share a project; it can be a member of others' workspaces and of their shared projects as today.
- **Limits and the demo.** At most 20 workspaces per account, 200 members and 50 groups per workspace, 100 members per group, with host-mode operators able to lower them per tenant. Workspace membership, group and invite routes are refused on the demo instance like project sharing.
- **No BREAKING change.** No op field is renamed or removed, no mandatory environment variable is added, and the sync exchange only gains optional response fields. One additive migration creates the workspace tables and the default workspace of each account.

Out of scope, each a possible follow-up: a workspace that shares every project with every member automatically (a "team workspace"), a combined Today or Upcoming across workspaces, a `workspace:` term in the filter grammar, workspace-level roles that grant rights on every project, per-workspace settings (theme, day start, language), group mentions (`@Family`), workspace invite links that bypass the server's sign-up policy, workspaces in display mode routes, end-to-end encryption of workspace names, and moving a shared project between two different owners' workspaces.

ROADMAP.md: adds the first row of a new "Next: ten more" table ("Workspaces and groups", change `workspaces`) and strikes "groups" from the set-aside list.

## Capabilities

### New Capabilities
- `workspaces`: the workspace entity and its default instance per account, the per-device current workspace and the switcher, what belongs to a workspace and how it is partitioned on the device, workspace membership and roles, groups and group grants with their effect on project membership, workspace invite links, moving projects and tasks between workspaces, limits, the settings page, and the demo and host-mode rules.

### Modified Capabilities
- `project-sharing`: "Project membership and roles" (grants to groups, the closed directory of a created workspace), "Membership routes" (grant and group grant routes, `via` in member lists), "Memberships in a fixed number of queries" (effective membership stays materialised, the response adds workspaces and groups in a fixed number of queries).
- `project-organization`: "Project fields" (additive `workspace_id`) and "Inbox is the default container" (one Inbox per workspace).
- `task-management`: "Task fields" (additive `workspace_id` for tasks without a project).
- `labels`: "Label entity" (a label belongs to a workspace; uniqueness per workspace).
- `custom-views`: "Saved view entity" (a view belongs to a workspace).
- `app-shell`: "Sidebar structure" (the header row is the workspace control; groups and counts are those of the current workspace).
- `offline-first-sync`: "Sync exchange" (the response also carries the caller's workspaces, their members and groups).
- `http-api`: "Export" (workspaces in the export document).
- `data-import`: "Own export completeness" (workspaces restored or mapped).
- `cli-client`: "Configuration file and profiles" (a profile's default workspace and `--workspace`).
- `mcp-server`: a new requirement "Workspaces in tools" (added, so the "Read-only tools" requirement that `mcp-projects` and `time-tracking` already modify is not touched).
- `caldav-sync`: "Discovery and calendar collections" (calendars of every workspace, named with the workspace).
- `end-to-end-encryption`: "Consequences for server-side reads and integrations" (workspace membership refused like sharing).
- `demo-mode`: "Restricted features" (workspace membership, groups and invites refused).

## Impact

- **Server.** `internal/sync`: `workspace_id` in the `Schema` for `project`, `label`, `view` and `task`; a new `workspaces.go` (workspaces, members, groups, grants, effective membership recomputation, the sync response additions); `scope.go` `CanWrite` gains the `workspace_id` rule for shared projects. `internal/store/migrations/0040_workspaces.sql` (tables `workspaces`, `workspace_members`, `workspace_invites`, `groups`, `group_members`, `project_grants`; `project_members` becomes the materialised effective membership with a `via_group_id` column; one default workspace per user). `internal/httpapi`: `workspaces.go` (routes under `/api/v1/workspaces`), `members.go` (grant routes), the export, the demo deny list. `internal/audit`: workspace and group events (ids only). `internal/caldav`: calendar names. `internal/webhook`: `workspace_id` in payloads. `internal/importer`: workspaces in the own format. `internal/agenttools` and `internal/mcp`: `list_workspaces` and the `workspace` arguments. `internal/cli`: `ot workspaces`, `--workspace`, the profile field. `internal/host`: per-tenant limits for workspaces, members per workspace and groups.
- **Web.** `web/src/lib`: `types.ts` and `ops.ts` (the field and defaults), `db.ts` (v23: `workspaces`, `workspaceMembers`, `groups` tables and a `workspace_id` index on projects, labels, views and tasks), a new `workspaces.ts` (current workspace, partition helpers, counts), `sync.ts` (the new response fields), `collections.ts`, `favourites.ts`, `search` and the palette registry, `e2ee.ts` (nothing new to encrypt). `web/src/app`: the sidebar header control and switcher, the Workspaces settings page (members, groups, invites), the share dialog's Groups section, the project picker grouped by workspace, "Move to workspace", stories and baselines for each.
- **CLI, docs, site.** `docs/workspaces.md` (new), `docs/sharing.md`, `docs/api.md`, `docs/cli.md`, `docs/mcp.md`, `docs/caldav.md`, `docs/import-export.md`, `docs/e2ee.md`, `docs/self-hosting/host-mode.md`; the agent skill file; translations in the five catalogues.
- **Dependencies and size.** No new dependency on either side. Estimated: server binary +180 KB, main web bundle +5 KB gzipped (the switcher and the partition helpers; the settings page is in the existing settings chunk), one more Dexie version. Runtime memory: the sync response grows by the workspace directory (bounded by the member limit), read in three additional fixed queries.
- **Compatibility.** Older clients and the CLI ignore `workspace_id` and see one undivided account, as today. Devices that have not yet received a workspace show its projects in the default workspace until it arrives. REST and MCP writes without a `workspace_id` go to the default workspace, so every existing script keeps working.
