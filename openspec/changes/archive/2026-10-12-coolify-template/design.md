# Design: Coolify one-click service template

All Coolify references are to `coollabsio/coolify` at `main` 068f02e (2026-10-12) and to `coollabsio/coolify-docs` `content/docs/contribute/service.mdx` (2026-10-07).

## D1 Conventions taken from Coolify

| Convention | Source |
| --- | --- |
| Header comments `documentation`, `slogan`, `category`, `tags`, `logo`, `port`, in that order (322 of 386 templates). The generator reads each `# key: value` line, appends `?utm_source=coolify.io` to `documentation`, and also knows `ignore`, `minversion`, `env_file`, `amd_only`, `arm_only` | `app/Console/Commands/Generate/Services.php` |
| `port` is required ("Caddy proxy cannot automatically determine every service port") | coolify-docs `contribute/service.mdx`; `tests/Feature/ServiceTemplatePortCoverageTest.php` |
| Domain via `SERVICE_URL_<NAME>_<PORT>`. Coolify then fills `SERVICE_URL_<NAME>` (`https://host`), `SERVICE_FQDN_<NAME>` (host) and the `_<PORT>` variants (with `:port`) from the **first** domain assigned to the service | `bootstrap/helpers/services.php` `updateCompose()` |
| `${VAR:-default}` creates an optional variable in the UI, `${VAR:?}` a required one. A nested `${A:-${SERVICE_URL_X}}` creates `A` and leaves the magic variable to Coolify (precedent: `templates/compose/supabase.yaml`) | `bootstrap/helpers/parsers.php` (service parser), coolify-docs |

| Logo at `public/svgs/<name>.svg`, referenced as `svgs/<name>.svg`. SVG preferred. (The docs page says `svgs/`; every recently merged service, e.g. Linkwarden #11561 and Lidarr #11576, adds it under `public/svgs/`) | `git log -- public/svgs` |

## D2 Image tag `0.2`, not `0.2.0`

The template follows the `0.2` release line, so patch releases arrive on the next Deploy without editing the template. Coolify's written rule says to pin a specific version. `uptime-kuma.yaml` (`louislam/uptime-kuma:2`) shows that maintainers accept a release line, but a reviewer may still ask for `0.2.0`. The check accepts `X.Y` or `X.Y.Z` of the latest release in `CHANGELOG.md`, so switching to `0.2.0` is a one-line change. When `0.3` is released, the check fails until the template (and the upstream copy) is bumped.

## D3 Which variables the template references

Coolify passes a UI variable to a Compose service only when the compose file references it. The template references the variables that have no equivalent in the app's Settings, or that matter on a public Coolify host:

- `OPENTODO_BASE_URL=${OPENTODO_BASE_URL:-${SERVICE_URL_OPENTODO}}`: the generated URL, unless the operator sets one. This matters when the service has two domains, because Coolify passes only the first.
- `OPENTODO_ALLOW_SIGNUP` (`false`), `OPENTODO_TRUSTED_PROXIES` (empty; `cloudflare` behind Cloudflare's proxy), `OPENTODO_PUSH` (`on`), `OPENTODO_SESSION_DAYS` (`90`), `OPENTODO_TRASH_RETENTION_DAYS` (`30`), `OPENTODO_IMPORT_MAX_MB` (`20`), `OPENTODO_LOG_LEVEL` (`info`).
- Email to task, which can only be configured through the environment: `OPENTODO_EMAIL_ADDRESS`, `OPENTODO_EMAIL_IMAP_HOST`, `OPENTODO_EMAIL_IMAP_USER`, `OPENTODO_EMAIL_IMAP_PASSWORD`, all empty (empty means off; partial settings stop the container with a clear message).

Left out: OIDC, backup and webhook presets, MCP and CalDAV toggles (all of them are set in Settings after the first start), and demo mode. They remain available through Coolify's "Edit Compose File", as documented. The defaults written into the template are the application's own defaults, so the UI shows real values and an empty value behaves like an unset one.

Only two inline comments (on `OPENTODO_BASE_URL` and `OPENTODO_TRUSTED_PROXIES`), to stay well under the PR check's limit on added comment lines.

## D4 Health check timing

- One-click service and Compose resources run `docker compose up -d --force-recreate` (`app/Actions/Service/StartService.php`; the Compose build pack in `app/Jobs/ApplicationDeploymentJob.php`): the old container stops before the new one starts, so there is no overlap and no rolling update. The template's health check (`interval: 5s`, `timeout: 5s`, `retries: 10`, `start_period: 10s`) only drives Coolify's status display, and it reports healthy within about 5 s.
- The Dockerfile and Docker Image build packs do roll (`rolling_update()`). For a Dockerfile build, Coolify reads `--interval`, `--timeout`, `--start-period` and `--retries` from the Dockerfile's `HEALTHCHECK` (`Application::parseHealthcheckFromDockerfile()`). It waits `start-period` (5 s), then polls `docker inspect` up to `retries` (3) times, sleeping `interval` (30 s) between polls. Docker Engine 25+ probes every 5 s during the start period by default, so the first probe lands at about 5 s, racing Coolify's first poll. If the probe loses the race, the update waits another 30 s. Measured locally: the `0.2` image is healthy after 5 s. With `--start-interval=2s` the probes run at 2 s and 4 s, so Coolify's first poll already sees "healthy" (measured: healthy after 2.1 s). Engines older than 25 ignore the flag and probe for the first time after `interval`, as before. `--start-interval` must come after `--interval` in the instruction: Coolify's regex `--interval=` would otherwise match inside `--start-interval=`.

## D5 Version from source builds

Coolify passes `SOURCE_COMMIT` as a build argument when the application's "Source commit availability" is set to "Available during build" (default: runtime only; `include_source_commit_in_build`). The Dockerfile declares `ARG SOURCE_COMMIT`, and when `VERSION` is still `dev` it builds `dev+<first 7 characters>`. Release builds pass `VERSION` and are unaffected. The default stays `dev`, so builds stay reproducible and the build cache keeps working.

## D6 The check script

`scripts/coolify-template-check.mjs`, plain Node with no dependencies. It parses the small YAML subset the template uses with a strict line parser, and fails if it meets anything it does not understand. It checks:

- the header fields and their order;
- `services.opentodo` only, with no `build:`, `container_name`, `ports` or `restart`;
- an image `ghcr.io/pixari/opentodo:<X.Y[.Z]>` of the latest release;
- `SERVICE_URL_OPENTODO_8080`, `port: 8080`, and `OPENTODO_BASE_URL` taken from `SERVICE_URL_OPENTODO`;
- every `OPENTODO_*` written with `${NAME:-…}` and present in `internal/config/*.go`, with no `:?` (nothing required);
- the `/data` volume and `test: ["CMD", "/opentodo", "healthcheck"]`;
- the upstream copies byte-identical to `deploy/coolify/opentodo.yaml` and `opentodo.svg`;
- a logo that is a square `viewBox` SVG under 4 KB, with no external references and no scripts;
- a final newline and at most 10 comment lines.

With Docker it runs `docker compose -f … config` (Coolify's magic variables set to sample values). `--smoke` pulls the image, starts it with the environment the template produces, waits for `/healthz` and runs `/opentodo healthcheck` in the container. CI runs both; `make check` runs the static part and the `config` step when Docker is present.

## Size

No dependency. Image size unchanged; the Dockerfile change is one shell conditional and one health check flag.
