# Design

## Context

See proposal.md for motivation. Today each settings panel under `web/src/app/` renders `SettingsSection` (title, description, rows) and `SettingRow` (label, description, status, control) from `web/src/ui/patterns/SettingsSection.tsx`, and writes its English copy inline as `t('…')` or `t.rich('…', {…})` in the JSX. The inventory in the spec was taken from those props: 42 cards (29 over 90 characters), about 90 rows (14 over), three option descriptions in `MODE_DESCRIPTION` of `web/src/app/method/MethodModeChooser.tsx` (two over 60) and fifteen notices over 90, the longest being the demo note in `SettingsView.tsx` at 353 characters.

Constraints that shape the approach:

- Localization: English is the source text; `scripts/i18n/extract.mjs` collects the first argument of `t()`, `t.rich()` and `msg()` into `web/src/locales/messages.json`, and `scripts/i18n-check.mjs` (`make i18n-check`) fails on a shipped catalog (`de.json`, `fr.json`, `es.json`, `it.json`, `pt.json`) that misses or still holds a message, or whose placeholders differ. Every sentence that changes therefore changes five catalog entries, by hand (localization "Shipped languages and their catalogs").
- The card anatomy: `settingsAnatomy.test.tsx` fails on a `<HelpLink>` or `<HelpHeading>` in a panel and on an `actions=`/`helpId=` prop of a card, because the page header carries the one Help action (design-system "Settings section and row patterns", UX-AUDIT G4). Contextual help opens through `openHelp(screen, trigger)` in `web/src/lib/helpRequest.ts`; the Shell renders the panel on top and returns focus to `trigger` on close. `MethodModeChooser` already opens help from inside a card with a `data-help-screen` button ("Learn the method").
- Screen ids: `web/scripts/docs/check.mjs` reads `data-help-screen="…"`, `openHelp('…')` and `help="…"` from the sources and fails when a guide page declares none; pages declare them in `screens:` front matter as `id#anchor`. Guide pages must stay under 600 words (`MAX_GUIDE_WORDS`); the four settings pages are at 485, 540, 402 and 468 words.
- The untranslated-string check in `scripts/ui-check.mjs` flags a `description=` prop on `SettingsSection`/`SettingRow` whose value is a bare literal phrase; a value routed through `t()` or an identifier passes.
- Docs screenshots: `scripts/docs-screenshots.mjs` shots `settings`, `settings-security`, `settings-passkeys`, `settings-notifications`, `members`, `assistant-settings` and `import` show settings cards; the `loop` shot drives the How you work card to switch modes and waits on `[data-method-mode]`.

## Goals / Non-Goals

**Goals:**
- One place that holds every settings sentence, so the rule can be checked by a test rather than by review, and the inventory in the spec is the file.
- No visual change beyond shorter text: same primitives, same ids (`*-heading` ids, `data-setting-row`, `data-testid`s), same test hooks, so the settings tests, stories, the search index and the screenshot script need only text changes.
- The moved sentences land in Help in the section the card already links to, and every such screen id is checked by the docs check.

**Non-Goals:**
- No change to `SettingRow`'s layout, to the section list, to `settingsSections.ts` (section descriptions are already one line) or to `settingsIndex.ts` (search descriptions are already short; the table may feed it later, not here).
- No translation of the guide; Help stays English with the existing note (localization "Help stays English, and says so").
- No change to dialogs: `ConfirmDialog` consequences keep their full text, as the spec says.

## Decisions

**D1. One copy table, `web/src/app/settingsCopy.ts`, keyed by the card's heading id.** Each entry is `{ title, description, learnMore?, rows?, options?, notices? }` where every text is a `msg('…')` literal (so the extractor sees it and the catalogs carry it), `learnMore` is a Help screen id, `rows` maps a row key to `{ label, description? }`, `options` maps a choice to `{ label, description }`, and `notices` maps a key to a one-line message. A description that depends on state (owner or admin on Users, on or off on the MCP switches, single sign-on on or off on Linked accounts, with or without the version on About, the Sidebar card under Open Loops first) is a record of named variants, each checked. Two helpers read it: `cardCopy(id)` returns `{ title: t(…), description: t(…), learnMore, headingId: \`${id}-heading\` }` to spread into `SettingsSection`, and `rowCopy(id, row)` returns `{ label, description, id }` for `SettingRow`. A rich description (the Trash link on Projects, `{header}` on API tokens, `{name}` on Linked accounts) is rendered by the panel with `t.rich(SETTINGS_COPY.projects.description, { a: … })`; the entry is still the one literal. Alternative: keep the copy inline and lint the JSX with the TypeScript parser. Rejected: the composed and conditional descriptions (`BackupsPanel`, `CalendarSettings`, `UsersPanel`, `SsoPanel`) cannot be measured from the JSX, and a reviewer cannot see the whole copy in one place. Alternative: a JSON file. Rejected: `msg()` in TypeScript is what the extractor and the editor already understand; JSON would need a second extractor.

**D2. The lint is a vitest file beside the table, `web/src/app/settingsCopy.test.ts`, in two parts.** (a) Over the table: every `title`/`label` has at most 4 words (a hyphenated word counts once, "Calendar apps (CalDAV)" counts three), every card, row and notice description at most 90 characters, every option description at most 60, measured on the source message with placeholders counted as written; a failure names the entry and "112 of 90". (b) Over the sources, in the style of `settingsAnatomy.test.tsx` (`import.meta.glob` of `web/src/app/**/*.tsx`, `web/src/ui/patterns/Settings.stories.tsx` and `web/src/app/**/*.stories.tsx` as raw text): a `description=` prop of `<SettingsSection` or `<SettingRow` must be a spread of `cardCopy`/`rowCopy` or an expression that mentions `SETTINGS_COPY`; a literal or a `t('…')` fails naming the file and line. (c) Over the catalogs: for every message of the table, each shipped catalog's entry is at most 120 characters (a third longer than the English limit; German and Portuguese run about 20 to 30 % longer), naming the entry and "140 of 120". The test runs in `npm test` and so in `make check`. It does not replace `make i18n-check`: completeness, staleness, placeholders and plural categories stay there, and the two can both fail on one bad entry (a missing Italian entry fails the catalog check only; a 140-character German entry fails the copy lint only). Alternative: extend `scripts/i18n-check.mjs` with the length rule. Rejected: that script checks catalogs against sources without knowing which message is a settings description; the table knows.

**D3. Learn more as a prop of the primitive, rendered inside the description line.** `SettingsSection` gains `learnMore?: string` (a screen id). When set, the description paragraph ends with a `<button type="button" data-help-screen={learnMore} aria-label={t('Learn more: {topic}', { topic: title })} onClick={(e) => openHelp(learnMore, e.currentTarget)}>` in the metadata size and the accent colour, in the same paragraph so it wraps with the text and is never a header action. Focus order: heading, Learn more, the rows' controls. On close, the Shell returns focus to the trigger as it does for every help request. `settingsAnatomy.test.tsx` keeps its ban on `<HelpLink>`/`<HelpHeading>` in panels and on `helpId=`; a new assertion checks that `learnMore` is the only way a card reaches Help. Alternative: a "?" icon button in the header. Rejected by the anatomy rule and UX-AUDIT G4 (nine help links per page was the problem). Alternative: make the whole description a link. Rejected: a sentence is not a link target, and a card without more to say needs no link.

**D4. The docs check learns the table.** `web/scripts/docs/check.mjs` gains one pattern, `learnMore: '…'`, read from `settingsCopy.ts`, so a Learn more id no page declares fails `make docs-check` like a `data-help-screen` does. The ids reuse the existing ones where a page already declares them (`settings/session`, `settings/password`, `settings/two-factor`, `settings/security` for passkeys, `settings/linked-accounts`, `settings/encryption`, `settings/sessions` for Recent activity, `settings/appearance`, `settings/start-view`, `settings/date-time`, `settings/calendar`, `settings/keyboard`, `settings/notifications`, `settings/quick-add`, `settings/voice`, `settings/capture`, `settings/email`, `settings/caldav`, `settings/calendar-feeds`, `settings/webhooks`, `settings/tokens`, `settings/assistant`, `settings/assistants`, `settings/data`, `settings/projects`, `settings/users`, `settings/members`, `settings/access` for the two-factor policy, `settings/sso`, `settings/project-invites`, `settings/backups`, `settings/attachments`, `settings/outgoing-email`) and adds the missing ones to the page that holds the moved text: `settings/how-you-work` → `docs/method/overview.md#how-prominent-it-is`, `settings/sidebar` → `docs/settings-you.md#appearance`, `settings/language` → `docs/language.md`, `settings/digest` → `docs/statistics.md#weekly-digest-by-email`, `settings/audit` → `docs/settings-server.md#server`, `settings/server-archive` → `docs/self-hosting/host-mode.md#owners-take-their-data-away` (an admin page, which opens on the website as the documentation capability says), `settings/demo` → `docs/getting-started.md#try-the-demo` for the demo note's Learn more.

**D5. Where the moved sentences go, under the 600-word limit.** A card with a feature page sends its text to the section its screen id names (two-factor, account-security for passkeys and recent sign-ins, e2ee, push-notifications, quick-add, capture, email, caldav, calendar-feeds, webhooks, mcp, assistant-settings, backups, attachments, self-hosting/outgoing-email, self-hosting/sso, invite-people, statistics, language, method/overview). Only the cards without one write into `docs/settings-*.md`: Session, How you work's one-liner, Appearance and Sidebar (settings-you, +60 words at most), Start view, Calendar, Keyboard (settings-app, which is at 540 and gets its Notifications paragraph shortened by the same amount it grows, staying under 600), Your data and Projects (settings-data), Users, Members, Two-factor policy, Project invite links, Download your data and Audit log (settings-server, +80 words at most). The `docs-check` word count is the gate; `make docs` regenerates `web/src/generated/help.json`.

**D6. Notices.** The demo note becomes one `Notice` line from `SETTINGS_COPY.demo.notices.restricted`, "Demo instance: {features} are disabled here.", with `features` from `joinList` as now and a Learn more button to `settings/demo` as its `action`; `DEMO_RESTRICTED_FEATURES` and the per-section `demo` lists in `settingsSections.ts` are unchanged, so the demo tests only change their expected sentence. The other fourteen notices become entries under their card's `notices` and keep their tone (`warning` for unencrypted transport, the plain-http address and blocked notifications). The owner-only pointers ("Ask the server owner to turn it on.") are already one line and move into the table unchanged.

**D7. Options.** `MODE_DESCRIPTION` in `MethodModeChooser.tsx` reads `SETTINGS_COPY['how-you-work'].options`; the Mode, Density, Date format, Time format and First day of the week options have labels only today and get no description. Theme tiles have no description. The "Learn the method" link stays as it is (it already opens `method/overview`); the card's own Learn more points at the same section, so the card does not get two links: the How you work card sets no `learnMore` and keeps "Learn the method" as its line's link.

**D8. Translations.** The five catalogs are rewritten by hand for every changed message (about 140 entries each), following `docs/translating.md`; the glossary terms (Inbox, Loop home, Places, app password) stay as the catalogs have them. `node scripts/i18n/extract.mjs --write` refreshes `messages.json` first so `make i18n-check` lists exactly what is missing and what is stale.

## Data model

No change. Nothing is read or written for any of this; the copy is static text. No op field added, renamed or removed.

## Size and resources

No dependency. About 10.5 KB raw of English description text leaves the panels and about 6 KB comes back in the table; the helpers and the Learn more rendering add about 0.3 KB. The main chunk shrinks by roughly 1.5 KB gzipped; each of the five catalog chunks (130 KB raw today) shrinks by roughly 1 KB gzipped. The lazy Help chunk (`help.json`) grows by the moved sentences, about 4 KB raw, loaded only when Help opens. Container image, binary and runtime memory unchanged.

## Interface budget

- Rows of chrome above the first item: the page header and, on the demo, one notice line (2 of 2); today the six-line demo note is one row that costs the height of three cards.
- Task properties visible by default: not a task screen.
- Primary sidebar destinations: unchanged.
- Vertical scroll regions: the section list column and the content column (2 of 3), as today; the Help panel is the shell's panel slot.
- Shortcuts: none added. `?` is named in the Keyboard card as today; `web/src/lib/shortcuts.ts` is untouched.
- Three-column settings layout unchanged (`SettingsView.tsx` grid and `SETTINGS_TWO_COLUMN_QUERY` untouched); fewer lines per card is the only visible change.

## Risks / Trade-offs

- [A one-liner loses a nuance a user needed on the card, for example "API tokens keep working" on Password] → the Learn more link is on every card whose text was cut, the moved sentence is in the guide section it opens, and the spec's inventory is reviewed line by line against the old text before the catalogs are written.
- [German and Portuguese lines wrap to two lines at 42 rem] → the limit for translations is 120 characters, which fits one line of the metadata size at the form width; the settings-section story at phone width is checked in German through the workbench's language switch.
- [Stories, tests and the screenshot script match the old sentences] → tests find cards by heading ids and `data-testid`s, which do not change; the few assertions on sentence text (`accountSettings.test.tsx`, `settingsView.test.tsx`, the demo tests, `methodLink.test.tsx`) are updated with the table as their source of expected strings, so a later copy change does not break them twice.
- [The table becomes a second place to look when editing a panel] → each panel keeps a one-line comment naming its table key, and the lint fails on an inline literal, so there is only one place.
- [Catalog entries written in a hurry drift from the source meaning] → the entries are reviewed by a speaker of each language as `docs/translating.md` requires; the copy lint only bounds their length.
- [The docs check's word limit blocks a page] → D5 budgets each page; if a page still exceeds 600 words, the longest card explanation moves to its feature page and the card's Learn more is repointed, without a spec change.

## Migration Plan

Pure UI and docs. Ships with the web bundle; no data migration, nothing to roll back beyond reverting the commit. `make docs-screenshots` regenerates the settings shots (`settings`, `settings-security`, `settings-passkeys`, `settings-notifications`, `members`, `assistant-settings`, `import`), whose wait selectors (headings and `data-method-mode`) still match.

## Implementation notes

- **The table lives in `web/src/lib/settingsCopy.ts`, not `web/src/app/`.** The lint must also cover `web/src/ui/patterns/Settings.stories.tsx`, and `src/ui` may not import `src/app` (eslint web-layering rule). In `src/lib` the stories, the panels and the docs check all read it. Keys are the cards' heading ids without `-heading` (`mfa`, `security`, `linked`, `e2ee`, `email-digest`, `voice-settings`, `attachments-settings`, `server-archive`, …), so `cardCopy(id)` returns `headingId: \`${id}-heading\`` and every heading id, `data-testid` and anchor stays as it was. Helpers: `cardCopy(id, { variant, values })`, `rowCopy(id, row, …)`, `noticeCopy(id, key, …)`, `optionCopy(id, option)`, and `copyEntries()` for the lint. A rich entry is passed to `t.rich(SETTINGS_COPY…)` by the panel. Row labels moved into the table too (titles and labels are linted for 4 words); dynamic labels (the passkey count, the sidebar destinations) stay in their panels.
- **The source lint** (D2 b) fails on a `description=` of `<SettingsSection>`/`<SettingRow>` that is a string literal or contains a `t('…')`/`t.rich('…')` of its own literal; an identifier (a prop passed down, as in Focus's number rows) passes, as in `ui-check.mjs`. It walks each opening tag with a small brace-aware scanner rather than the TypeScript parser, like `settingsAnatomy.test.tsx`.
- **Labels over 4 words were shortened**, which the inventory did not list: Sign out here, Week starts on, Feedback and problems, Start work automatically, Allow AI assistants, Assistants may make changes, Changes to my tasks, Small changes without review, Dictate tasks, Email me the digest, Invite new people, and On this server (CalDAV and calendar feeds). The switches keep their accessible names where the new visible label is contained in them (WCAG 2.5.3); the Focus and digest switches take the row label. Docs that quote these labels were updated (settings guides, sharing, invite people, quick add, offline and sync, install app, MCP, CLI, API, assistant settings, README); `settingsIndex.ts` keeps its search labels, which are not card text.
- **Learn more ids.** Existing screen ids were reused wherever a page already declared the right section: the Sidebar card uses `settings/appearance`, Download your data and the Audit log use `settings/server` (`docs/self-hosting/host-mode.md` is an admin page, and only user pages may declare screens), and the demo note uses the existing `demo` id (`getting-started.md#try-the-demo`, already opened by the demo banner). New ids: `settings/language` (`docs/language.md`) and `settings/digest` (`docs/statistics.md#weekly-digest-by-email`). How you work keeps "Learn the method" and sets no `learnMore` (D7). The Focus card's last-row "How Focus works" button (focus-mode, because cards could not carry a help link) became the card's Learn more to `settings/focus`, and `settingsAnatomy.test.tsx` now fails on any `openHelp(`/`data-help-screen` in a panel, so Learn more is the only way a card reaches Help.
- **Moved text.** Cards whose screen id resolves to a `docs/settings-*.md` section (CalDAV, webhooks, tokens, AI assistants, users, policies, backups, outgoing email, audit, server archive, email to task) received their moved sentences there; feature pages that are admin or developer pages (`caldav.md`, `webhooks.md`, `mcp.md`, `email.md`) are not in the in-app Help, so the user-facing section got the text. Word counts after the change: settings-you 541, settings-app 588 (its Notifications paragraph and the Date and time preview sentence were shortened by what Email to task gained), settings-data 560, settings-server 579, account-security 594, getting-started 598.
- **The demo note** is a `Notice` with one line from `SETTINGS_COPY.demo.notices.restricted` (variants `one`/`other` for "is"/"are", since a plural message would be measured as one long source) and a Learn more button as its action. The "first card within two lines at 1200 px" check is structural (happy-dom has no layout): `settingsSections.test.tsx` asserts the note holds only that line and the profile card follows it directly.
- **Shell-level test (2.4).** The Webhooks add form is a dialog, so the test renders `WebhooksView` with its draft in state next to the Shell's help slot (`HelpPanel` for the current help request), types an address, activates the card's Learn more, and checks that the guide opens, the address is kept, and closing returns focus to the link.
- **EmptyState legacy slots.** lean-chrome left `icon`/`body`/`control` on `EmptyState` "for settings only", but they are also used outside Settings (the labels page, the review's project walk, archived projects, the task panel's History and Activity tabs), and this change's tasks do not cover empty states. They stay; follow-up: move the settings panels' empty states (webhooks, tokens, passkeys, linked accounts, members, users, recent activity) and those other callers to the `title`/`action`/`secondary` contract and delete the slots, together with the line in `docs/interface-guide.md` that calls them settings-only.
- **Not regenerated here.** UI baselines (the new `UI/Patterns/Settings/Learn More` story and every settings story whose text changed) need the Docker-based `make ui-baselines`; this session has no Docker daemon, so they come from CI's `ui-check-report` artifact. Docs screenshots (`settings`, `settings-security`, `settings-passkeys`, `settings-notifications`, `members`, `assistant-settings`, `import`) are stale in their card text and were not regenerated (`make docs-screenshots` fails on unrelated shots in this environment). The German and Portuguese phone check (4.9) was not done by eye; the lint bounds every translation at 120 characters.
- **Main merged.** The Community row in About (discord-community) was on `main` only; `main` was merged into this branch first so the rule applies to it.
