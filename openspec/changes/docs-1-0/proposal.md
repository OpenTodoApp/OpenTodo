# Proposal

## Why

OpenTodo's documentation is already one source in `docs/` that builds the website and the in-app Help, with checks for links, images, capability coverage and API routes (`documentation`, `internal/httpapi/api_docs_test.go`). What a 1.0 user, operator or contributor still can't rely on:

- **Self-hosters.** Self-hosting is spread over 25 platform pages. Nothing walks an operator from install to upgrade, backup drill, monitoring and hardening, and the `OPENTODO_*` variables are documented wherever each feature lives, not in one reference. The research's audience is people leaving subscriptions to self-host (research §1, §3); for them the operator path is the product.
- **API clients.** Every route is in `docs/api.md`, but the error codes are not checked against the codes the server sends, and no example request in the doc is ever run.
- **Contributors.** `CONTRIBUTING.md` is 65 lines. A newcomer can't find how to add an importer, a language or a shared Go/TS contract without reading `AGENTS.md`, which is written for agents.
- **Everyone.** There is no public roadmap page. ROADMAP.md is a long table read on GitHub, and nothing tells a visitor what is planned, in progress or shipped.
- **Coverage.** No check proves that every screen of the app has a guide. The 0.17–0.21 milestones add many screens and settings, and a 1.0 user guide with holes is a trust problem.

## What Changes

- **Every screen has a guide.** The app's screen ids become one list: the routes of `web/src/app`, the Settings sections, and the dialogs with a Help action. The docs check fails when a screen id is declared by no page's `screens:` front matter.
- **A self-hosting handbook.** `docs/self-hosting/README.md` is one ordered path: install, first run, reverse proxy and TLS, backups with a restore drill, upgrading (linking to the upgrade policy of `stability-contract`), monitoring (health endpoint, logs, the nightly alerts), hardening, and sizing (the numbers of `performance-10k`). The 25 platform pages hang off its install step.
- **One configuration reference.** `docs/self-hosting/configuration.md` lists every `OPENTODO_*` variable the server reads, with its default, example and the page that explains it. A test fails when `internal/config` (or any package) reads a variable that the reference does not list, or the reference lists one nobody reads.
- **API reference you can trust.**
  - Every error code the server can send, as listed in `web/src/lib/i18n/server-error-codes.json`, is documented in `docs/api.md` with its HTTP status, and a test checks both ways.
  - Every fenced `http` example in `docs/api.md` marked `<!-- run -->` is executed against a test server in `go test`, and its documented status must match.
- **A contributor guide.** `CONTRIBUTING.md` stays the entry point, and `docs/contributing/` gains seven how-tos:
  - first contribution in 30 minutes;
  - architecture tour;
  - the OpenSpec workflow;
  - tests and checks;
  - adding a language (the kit from `more-languages`);
  - adding an importer (the steps `migration-everywhere` follows);
  - adding a shared Go/TS contract.

  Each page is checked for broken links like the rest.
- **A public roadmap page.** `docs/roadmap.md` is generated at docs build from ROADMAP.md's milestone tables. Each change gets a status computed from the repository:
  - **Planned**: a proposal with no task done;
  - **In progress**: some tasks done;
  - **Shipped in x.y**: archived, with the version from CHANGELOG.md.

  It is served on the docs website and in Help under "About". The docs check fails when the page is stale.
- **User guide list extended** with the five new switch guides (OmniFocus, Vikunja, Notion, Super Productivity, Tududi).
- **Screenshots refreshed for 1.0.** Every screenshot is regenerated by `make docs-screenshots` from the release candidate, and `docs/README.md` states the version they show.

No behaviour change in the app beyond the Help "About" entry. No op field, no route, no environment variable. Not **BREAKING**.

## Out of scope

- **Translating the docs.** The app speaks six (seven with Dutch) languages, but the docs stay English for 1.0. A later change can add translated Help pages with the contributor kit.
- **A docs hosting change.** The website stays the static bundle served under `/docs/`.
- **Video tutorials.**
- **Rewriting existing guides.** This change fills gaps and adds checks; it does not restyle pages that pass them.
- **Versioned docs for several releases side by side.** Each server's Help shows its own version, as today.

## Roadmap

1.0 "Trust", row `docs-1-0`. It depends on `stability-contract` (the upgrade policy it links), `performance-10k` (the sizing numbers) and `migration-everywhere` (the five switch guides). Those archive first.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `documentation`: "User guide" lists the five new switch guides and the self-hosting handbook. New requirements:
  - "Every screen has a guide";
  - "Self-hosting handbook";
  - "Configuration reference is complete";
  - "API error codes and examples are checked";
  - "Contributor guide";
  - "Public roadmap page".

## Impact

- **Data model, sync, op schema, E2EE, API, CLI, MCP:** none.
- **Code:**
  - checks in `scripts/` (docs build and repo checks);
  - `internal/httpapi/api_docs_test.go` (error codes and examples);
  - a new `internal/config` test (environment reference);
  - the screen-id list exported from `web/src/app`;
  - a Help "About" entry.
- **Docs:** new pages under `docs/self-hosting/` and `docs/contributing/`, plus `docs/roadmap.md`, generated by the docs build.
- **Size:** the in-app help grows by the roadmap page, about 6 KB gzip, loaded only when Help opens. No binary change beyond the embedded help.
