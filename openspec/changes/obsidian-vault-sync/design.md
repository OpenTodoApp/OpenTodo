# Design

## Context

`internal/vault` is about 4,200 lines of engine (line grammar, layout, merge, render, plan, exchange, state, store, front matter) plus TaskNotes support, behind `ot vault init|sync|status|watch`. Its state file `.opentodo/state.json` (version 2) holds the device id `vault:<id>`, the cursor, the clock offset, the base (the account as of the last sync, per field, with the clock that wrote it), per-file hashes and the printed map. `obsidian-plugin` gives the plugin a connection, a `full` token, the shared envelope code, the task-line grammar in TypeScript and a per-device install id. Obsidian on mobile offers the vault's `DataAdapter` (which also reads dot folders), file events (`modify`, `create`, `delete`, `rename`) and `requestUrl`; it does not run plugins in the background.

## Goals / Non-Goals

**Goals:** the same folder, rules and results as `ot vault`, on Obsidian desktop and mobile; one implementation's behaviour pinned to the other by vectors; no double syncing of a replicated folder.

**Non-Goals:** background sync, the live stream, TaskNotes, a new file format.

## Decisions

**D1. Port the engine to TypeScript, pinned by shared vectors.** Alternatives: (a) compile `internal/vault` to WebAssembly with Go's `js/wasm` target; (b) TinyGo; (c) a server-side vault renderer; (d) a TypeScript port. (a) costs a 2–3 MB runtime in a plugin people install on phones, a memory footprint Obsidian mobile users notice, and a JavaScript/Go bridge for files and requests; Obsidian's reviewers also discourage large opaque binaries. (b) does not support the reflection `encoding/json` needs here. (c) cannot work for encrypted accounts (the server holds ciphertext) and would move the merge off the device, against local-first. (d) doubles the code but keeps the plugin small and readable; the drift risk is handled the way the repository already handles it for recurrence, quick add and the filter parser: shared vectors. Chosen: (d), with the fixture vault (`internal/vault/testdata/vault`, parse and print byte for byte) and new sync vectors.

**D2. Sync vectors.** `internal/vault/testdata/sync/<case>.json`: `{state, files, serverOps, serverTime}` in, `{pushed, files, conflicts, report, state}` out, generated by a Go test from the engine's existing scenarios (`go test ./internal/vault -run TestSyncVectors -update`), committed, and run by `obsidian/src/vault/engine.test.ts` against an in-memory adapter and transport. Cases cover every scenario of `markdown-vault` "Merge and conflict rules", "Task lines", "Completion and recurrence in files", "Labels, sections, subtasks and notes", "What the file does not round-trip", "Vault limits" and "Encrypted accounts in the vault" (with a fixed test key). A change to either engine that changes an output fails the other's test until the vectors are regenerated and both agree.

**D3. Same state file, two new optional members.** The plugin reads and writes `.opentodo/state.json` version 2 through the `DataAdapter`, atomically (write `state.json.tmp`, then rename). It adds `owner: {kind: "cli" | "obsidian", install: <random id per installation>, label: <host name or "Obsidian on iPhone">}` and `lease_until`. `ot` writes the same. A state with `tasknotes` set is refused by the plugin with "This folder has a TaskNotes folder linked; keep syncing it with `ot vault`", and the member is preserved if the user later takes over with `ot`.

**D4. One syncing device per folder, with a lease.** The hazard: a folder replicated by Obsidian Sync, iCloud or git, with `ot vault watch` on a laptop and the plugin on a phone, has two engines that each see the other's writes as file edits and push them again, and two states racing through the file-sync service. Options: (a) let it be and document "only one"; (b) per-device state outside the folder; (c) ownership in the replicated state. (b) makes each device a separate vault device over the same files — exactly the race. Chosen: (c). Before a sync, the engine reads the state: if `owner` names another installation and `lease_until` is in the future, it refuses (`vault_owned`, naming the owner's label and when the lease ends); if the lease has expired, it still refuses unless the user takes over, because the owner may only be asleep. A sync by the owner renews the lease to now + 5 minutes (`watch` and the plugin renew it on every cycle, so a live owner always holds it). Edits made on a non-owning device reach OpenTodo through the file-sync service and the owner's next sync, which is the correct single path.

**D5. Taking over is a fresh, conflict-safe first sync.** "Take over syncing here" (plugin) or `--take-over` (`ot`) writes a new device id `vault:<id>`, a new owner, an empty cursor and an empty base, then runs the first sync in adopt mode with the server as the base: every line with a known `🆔` is compared to the server's values; a field that differs keeps the server's value and the file's line goes to `<file>.conflict.md`, as "Merge and conflict rules" already does for both-sides changes; a line without `🆔` creates a task. Nothing in the files is lost and nothing is pushed twice. Alternative rejected: continue with the old owner's cursor and base — the replicated state may be stale by an unknown number of syncs.

**D6. When the plugin syncs.** On load (after the workspace is ready); after a file under the folder has been stable for one second following a `modify`, `create`, `delete` or `rename` (two-second debounce, as `watch`); every 30 seconds while Obsidian is visible (`document.visibilityState`), the same fallback interval as `watch` without the stream; on the command "Sync vault with OpenTodo now". Failures back off (30 s, 1, 2, 5 minutes) and are shown in the settings tab and, on desktop, the status bar; the folder and the state stay consistent because the engine writes files and state only after a successful exchange, as in Go. Obsidian's own editor buffer is respected: files are written through `vault.process` so an open editor picks the change up instead of overwriting it.

**D7. Encrypted accounts and plaintext.** As `markdown-vault` "Encrypted accounts in the vault": content decrypted on the device with the unlocked key, every pushed content value encrypted, a value that does not decrypt written as the placeholder and never pushed. Locked: the sync is skipped with "Unlock OpenTodo to sync the vault", nothing is sent. Enabling sync on an encrypted account shows once, in the confirmation, that the folder (and anything that replicates it) will hold the content in plaintext.

**D8. Send-line and the synced folder.** Lines inside the synced folder are vault lines: "Send line to OpenTodo" refuses them ("This line is already synced by the vault") so a task is never created twice.

**D9. Mobile limits.** The same limits as `markdown-vault` "Vault limits" (1 MB or 5,000 lines per file, 20,000 tasks, 64 KB notes). The base for 20,000 tasks is a few MB of JSON; the plugin parses and writes it once per sync, so syncs skip unchanged files by hash first (as Go does) and the state is written only when something changed.

## Data model impact

None on the server. State file: two optional members (D3).

## Progressive disclosure

Off until the user turns it on in the plugin's settings; nothing changes in OpenTodo. `ot vault` users see the ownership message only when a second device is involved.

## Interface budget

No OpenTodo screen changes.

## Size

Plugin `main.js` +~100 KB minified for the engine; the budget becomes 400 KB. No server, binary or web change beyond the state members in `internal/vault`.

## Risks

- **Two engines.** Mitigated by D2; each requirement's scenarios become vector cases, and a new vault feature must add vectors before either engine can ship it.
- **File-sync services that rewrite files late** (iCloud downloads on demand). A file iCloud has not downloaded yet is absent, with a `.<name>.icloud` placeholder beside it; read as "file removed", it would trash its tasks. The engine treats a file with such a placeholder as not present yet: it skips it with a report and changes nothing for its tasks. This needs a vector of its own and a manual run on iOS with iCloud.
- **A lost owner** (a laptop that died): the user takes over, which is safe by D5.
