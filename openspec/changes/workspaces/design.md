# Design

## Context

See proposal.md for the motivation. Relevant current state:

- Every op and every materialised field belongs to exactly one sync scope (`internal/sync/scope.go`): the user's personal scope (`user:<id>`: Inbox, unshared projects, labels, views, preferences) or a shared project's scope (`project:<id>`). `loadAccess` reads `project_members` once per request; `Memberships` reads two fixed queries per sync; `scopeUsers` fans wake-ups and webhooks out to a project's members. Membership is authorization data changed only through REST routes (`members.go`), never an op.
- The client keeps one Dexie database per account (`web/src/lib/db.ts`, v22) and renders every view from it; the sync response's `memberships` replace the local `memberships` table on each exchange.
- The sidebar (quiet-sidebar and sidebar-favourites, both archiving before this change) has a header row with the app name and the search button, pinned primary destinations, one scroller of groups, and a one-row footer. `app-shell` "Sidebar structure" limits `first` mode to six primary destinations.
- Preferences that must survive the partition already exist as single-string `user_prefs` values: `favourites` (kind:id entries) and `sidebar_destinations`. Both are lists of ids, so a per-workspace reading needs no new field.
- Project invite links (`internal/auth/projectinvites.go`, `project_invites` table) and account invitations already implement single-use hashed secrets, previews, acceptance, email sending and rate limits; the workspace links reuse that code.
- End-to-end encryption is per account: one key covers every content field of the account's personal scope; sharing a project is refused for encrypted accounts (`end-to-end-encryption` "Consequences").
- Host mode serves one tenant per data directory with per-tenant limits (`internal/host`); a tenant is an instance, and this change keeps it so.
- Open changes that modify requirements this change also touches: `quiet-sidebar` and `sidebar-favourites` ("Sidebar structure" in `app-shell`; the delta here is written against `quiet-sidebar`'s text, which is the later of the two and includes the Favourites group and the one-row footer), `mcp-projects` and `time-tracking` ("Read-only tools" in `mcp-server`; this change adds a new requirement instead of modifying it), `inbox-means-unplaced` (`project-organization`, `cli-client` and `mcp-server` deltas that do not overlap the requirements modified here). All of them are expected to archive before this change is applied; task 11.1 re-reads the four affected requirements at apply time and adjusts the delta text to the archived wording.

## Goals / Non-Goals

**Goals:**
- A partition every user understands in one sentence: "a workspace is a separate room with its own projects, labels, views and people".
- No change to the sync protocol's guarantees: one cursor per device, per-field last-writer-wins, membership never in the op log, a fixed number of queries per exchange.
- Groups that make sharing with a household or a team one action, without a new permission model: effective membership is exactly today's `project_members`.
- An upgrade that changes nothing for a single user on an older client, the CLI or a script.

**Non-Goals:**
- A workspace whose members automatically see every project in it (a team workspace). This design keeps a project private to its owner until shared; the closed directory and groups make sharing cheap instead. A team workspace can be added later as a flag on the workspace without changing the data model.
- Per-workspace preferences (theme, language, day start) and a combined Today across workspaces.
- Encrypting workspace names: they are membership metadata, treated like project member lists.
- Routing by workspace in the URL. The current workspace is device state (D5), so every existing link keeps working.

## Decisions

**D1. A workspace is a server-side directory, not a sync scope.** Data keeps living in the personal scope and in project scopes; a workspace adds an `id` to projects, labels, views and project-less tasks (`workspace_id`), and a server-side membership directory (`workspaces`, `workspace_members`, `groups`, `group_members`). The server never partitions ops by workspace: a device receives its personal scope and its project scopes as today and partitions on the device. Alternative: a third scope kind `workspace:<id>` whose members all read and write it. Rejected: it changes who can see what (every member sees every project), needs a per-workspace role table for ops, breaks "an encrypted account cannot share" into a new case, and would require moving existing ops between scopes at migration time. Alternative: a client-only partition with no server knowledge. Rejected: the closed directory, groups, invites, CalDAV naming and the CLI all need the server to know the workspaces.

**D2. Additive fields, default by absence.** `workspace_id: kNullableString` on `project`, `label`, `view` and `task` in `internal/sync/ops.go` `Schema`, `web/src/lib/types.ts` and the defaults in `web/src/lib/ops.ts` (`null`). Null or absent means the default workspace, so no op is rewritten at upgrade, older clients write nothing new and see everything in one list, and REST or MCP writes without the field land where they always did. The field is an id, not user text, so it is not an `e2ee` content field. Tasks carry it only for the Inbox case: a task with a project follows the project (one source of truth for placement, no fan-out write when a project moves). Sub-projects follow their parent at read time; a `parent_id` into another workspace reads as a missing parent, the rule `project-organization` already has for missing parents.

**D3. Effective membership is materialised.** New table `project_grants(project_id, subject_kind 'user'|'group', subject_id, role, added_by, created_at)` holds what people did. `project_members` keeps its primary key `(project_id, user_id)` and gains `via TEXT NOT NULL DEFAULT ''` (comma-separated group ids, empty for a direct grant) and keeps `role` as the effective (highest) role. `recomputeProject(tx, projectID)` rewrites the project's `project_members` rows from the grants and the current group memberships inside the same transaction as any grant, group or workspace-membership change, and emits the same `MemberChange` effects (backfill flags for new members, unassignment ops and purge for removed ones, audience for wake-ups) as `members.go` does today. Every reader (`loadAccess`, `Memberships`, `scopeUsers`, `canBeAssigned`, CalDAV, webhooks, public links, the assistant's member provider) is untouched. Alternative: evaluate groups at read time with a join. Rejected: it touches every reader, makes "fixed number of queries" harder to keep, and makes the op check depend on two tables. Cost: a group change on a group that is on N projects rewrites N member lists in one transaction; bounded by 50 groups × 200 members per workspace.

**D4. The default workspace stays open; created workspaces are closed.** Each account's default workspace (`workspaces.kind = 'default'`, id derived with `ids.Name("workspace", userID)` so it is stable and needs no lookup table) has no member list and accepts no members. Projects in it share by exact email across the server, as today. A created workspace is a directory: `addMember` and invite acceptance on a project check that the target is in `workspace_members` of the project's workspace (409 `not_in_workspace`), and group grants are limited to the workspace's groups (404 for others). A member of a shared project who is not in its workspace sees it in their default workspace (client rule in `workspaces.ts`: `workspaceOf(project) = project.workspace_id ∈ myWorkspaces ? it : default`). This keeps every existing share valid and lets an owner move a legacy shared project into a workspace without first inviting everyone. Alternative: migrate every existing share by adding its members to the owner's default workspace. Rejected: it would make Bob a member of Alice's "Personal", which is the opposite of what the feature promises.

**D5. The current workspace is device state.** Stored in the `meta` table (`currentWorkspace`), read by one hook, never synced, never in the URL. Views, counts, search, quick add and the palette's local sections read `currentWorkspaceId()` through one helper, `inWorkspace(entity)`, in `web/src/lib/workspaces.ts`, so the partition is one function. Opening an entity of another workspace (addresses, notifications, palette hits) calls `switchTo(workspaceOf(entity))` first and shows a toast. Alternative: `/w/<id>/...` route prefixes. Rejected: every saved link, notification, display route and docs screenshot would change, and the phone tab bar would need the prefix too. The cost is that two tabs on one device share the current workspace; a change in one tab is picked up by the other through the existing cross-tab meta listener.

**D6. Where the switcher lives.** The sidebar's header row (app name) becomes the workspace control. It is not a destination, so `first` mode keeps six; no chrome row is added above any list (the header row already exists); the footer stays one row. On phones the control is the drawer's header. No default shortcut: `g w` is Week and the shortcut registry's `g` sequences are nearly full, so switching is a palette command per workspace ("Switch to workspace: Work") and the control is keyboard-reachable; a key can be assigned later without a spec change. The "other workspace has updates" dot reuses `StatusDot` and the unread computation of `activity-feed`, grouped by workspace.

**D7. Labels and views are per workspace by field, favourites by reading.** Labels get `workspace_id` so names can repeat across workspaces (uniqueness check and `@` completion filtered by `inWorkspace`). A task moved across workspaces keeps its label ids; the hide-unknown-id rule already in `labels` makes the chips disappear without a write. "Move to workspace" on a project re-matches labels by name as one `mutateMany` batch so the common case (same vocabulary everywhere) just works, with Undo. Favourites (`user_prefs.favourites`) and promoted destinations stay one string: the sidebar filters entries by the current workspace at read time and keeps the stored value whole, so pinning in two workspaces never fights over one field.

**D8. Workspaces reach devices through the sync response.** `/api/v1/sync` adds `workspaces: [{id, name, icon, color, default, role, ownerId, members: [{userId, name, role}], groups: [{id, name, members: [userId]}]}]`, read with three queries (workspaces of the user, members of those workspaces, groups with members of those workspaces), ordered deterministically, replacing Dexie tables `workspaces`, `workspaceMembers`, `groups` (v23; plus a `workspace_id` index on `projects`, `labels`, `views`, `tasks`). Members carry names only (no emails) because the directory is shown to every member; project member lists keep their emails as today. The wake-up channel stays content-free; membership changes call the existing notifier for the affected users. Alternative: a separate `GET /api/v1/workspaces` the client polls. Rejected: devices would be stale offline and the exchange already carries memberships for the same reason.

**D9. Routes and policies.** All workspace routes are registered through `routes.handle` with `signedIn.fullTokens()` (writes also `.demoDenied()` with the matching `demo.go` entries); the invite preview is `public("workspace invite preview")` and acceptance `signedIn`; link creation is `.credential()`-free but rate limited like project links. Errors reuse existing codes (`user_not_found`, `forbidden`, `not_found`, `owner_must_transfer`, `already_member`, `invitation_invalid`, `rate_limited`, `insufficient_scope`, `encryption_enabled`, `demo_restricted`) and add `not_in_workspace`, `default_workspace`, `workspace_not_empty`, `group_exists`, `limit_reached`. Audit events (ids only): `workspace.created`, `workspace.renamed`, `workspace.deleted`, `workspace.transferred`, `workspace.member_added`, `workspace.member_role_changed`, `workspace.member_removed`, `workspace.group_created`, `workspace.group_deleted`, `workspace.group_member_added`, `workspace.group_member_removed`, `project.grant_added`, `project.grant_changed`, `project.grant_removed`, `workspace_invite.created`, `workspace_invite.accepted`, `workspace_invite.revoked`.

**D10. Account lifecycle.** Deleting an account (user-administration) removes its workspace memberships and grants through `ON DELETE CASCADE` plus `recomputeProject` for the affected projects, deletes its default workspace, and transfers each owned workspace to its oldest admin, or deletes it when it has no projects and no other members, or otherwise hands it to the server owner (named in the audit event). Deactivation changes nothing in the directory, as for project membership today.

**D11. Data model impact.** Additive migration `0040_workspaces.sql`: `workspaces(id, kind, owner_id, name, icon, color, created_at, deleted_at)`, `workspace_members(workspace_id, user_id, role, added_by, created_at)`, `workspace_invites` (the shape of `project_invites`), `groups(id, workspace_id, name, created_at, deleted_at)`, `group_members(group_id, user_id, created_at)`, `project_grants` as in D3, `ALTER TABLE project_members ADD COLUMN via TEXT NOT NULL DEFAULT ''`, one `workspaces` row of kind `default` per existing user, and one `project_grants` row of kind `user` per existing `project_members` row. No op is rewritten; `scope_fields` is untouched. Rollback: an older binary ignores the new tables and column and reads `project_members` as before, because the materialised rows stay in the same shape.

**D12. Query cost and size.** Per sync exchange: +3 queries (D8), independent of the number of workspaces. Per op: no new query; `CanWrite` only adds a field rule (`workspace_id` on a shared project is owner-only). Per membership change: one recomputation per affected project. Server binary: about +180 KB (routes, recompute, invites, CLI commands, MCP tool). Web: about +5 KB gzipped in the main bundle (the control, the switcher, `workspaces.ts`, the partition hook); the settings page lives in the existing lazily loaded settings chunk. No new dependency on either side. Runtime memory: the directory in the sync response is bounded by the limits (20 × 200 members, 20 × 50 groups) and is not kept in server memory between requests.

**D13. Interface budget.** Sidebar: the header row changes content, no new row; primary destinations unchanged. Lists: no new chrome row above the first item; the Inbox, Today and every view keep their headers. Task row and panel: unchanged (no workspace chip; the project chip already names the project, and a project's workspace is in its tooltip path). Project picker: entries grouped by workspace with the current workspace first, "No project" per workspace, inside the existing Combobox. Settings → Workspaces: one new settings page under Account with the standard `SettingsSection`/`SettingRow` pattern at the form width, one Help action, members and groups as rows, a danger zone card last; at 360 px rows wrap and every control is 44 px. Share dialog: a "Groups" section under People, same picker. Scroll regions: none added (the switcher is a popover). Shortcuts: none added to the registry; two palette commands per account plus one per workspace.

**D14. CLI, MCP, CalDAV, webhooks.** `ot workspaces` (list, `--json` with the versioned schema), `--workspace` and `OPENTODO_WORKSPACE` resolved once per command to an id (name match ignoring case, exit 2 with the list otherwise), a `workspace` column in `ot projects`, `ot projects move --workspace`. The agent tool registry adds `list_workspaces` and the `workspace` argument, so MCP and the in-app assistant get them together; `update_project.workspace_id` is planned only for the owner, the server refuses the rest. CalDAV paths do not change (a calendar's path is its project id), only display names outside the default workspace, so a client sees a rename, never a removal. Webhook payloads add `workspace_id` to project and task events; subscriptions keep their project filter.

**D15. Tests that pin the partition.** A shared fixture `internal/sync/testdata/workspaces_fixture.json` lists entities with `workspace_id`, parent and project links, and the expected workspace of each; `internal/sync/workspaces_test.go` and `web/src/lib/workspaces.test.ts` both read it so the Go side (CalDAV, MCP, CLI, export) and the device agree on where every entity belongs. Convergence: the random-history test gains `workspace_id` on the four entities.

## Risks / Trade-offs

- [A person expects "Work" to be shared with their team automatically] → the empty Work workspace explains that projects are private until shared and offers "Share with a group" as the first action; a team workspace is a recorded follow-up.
- [Legacy shares look odd: Bob sees Alice's "Trip" in his Personal workspace] → the project header shows "Shared by Alice" as today; nothing changes for Bob until Alice invites him to Family, after which the project moves to Family on his devices automatically.
- [Two Inboxes confuse quick capture: a task lands in the wrong workspace] → the quick-add field's placeholder names the workspace ("Add to Work…"), and the task's toast offers "Move to Personal".
- [Group recomputation on a large group is slow] → bounded by the limits; done in one transaction with one `DELETE` and one `INSERT ... SELECT` per project, measured in a benchmark test at the limits (task 2.6).
- [Older client writes a label with a name that already exists in another workspace] → labels are per workspace by id; the client's duplicate check runs within a workspace, and an older client (no partition) still refuses duplicates account-wide, which is stricter, not wrong.
- [Switching tabs or devices shows a different workspace than expected] → per-device choice, named in the header and in the quick-add placeholder; the palette crosses workspaces so nothing is unreachable.
- [Export and import grow a new section that other importers do not understand] → `workspaces` is optional in the format; version stays 1 because readers ignore unknown keys, and the docs say so.
- [Deleting a workspace with projects loses data] → refused while it has projects or members; "Move to workspace" and "Delete project" are the only ways out, both undoable or in the Trash.

## Migration Plan

1. Ship the migration and the server: default workspaces and grants are created at startup; nothing visible changes until a client that knows workspaces connects. Older clients keep working.
2. Ship the web app: the header becomes the control; with one workspace it reads "OpenTodo · Personal" and the switcher invites creating one.
3. Upgrade note in the CHANGELOG: new tables, no new variable, `project_members` gains a column; back up first as for every release; older servers ignore the new tables and column.
4. Rollback: run the previous binary; the new tables are ignored, effective membership is still in `project_members` in its old shape, and `workspace_id` values are unknown fields the old server never sees (devices from before the change do not write them; devices from after it would be refused with `invalid_op`, so downgrade only together with the web app, as the sync protocol already requires).

## Open Questions

- The name of the default workspace: "Personal" is proposed; "My workspace" avoids implying work versus home. Changeable at apply time without touching the specs (the specs say "Personal until renamed").
- Whether the workspace control should show the account's avatar beside the workspace name on a desktop, where the footer already shows the account. Visual only; decided in the workbench.
- Group mentions (`@Family`) and a `workspace:` filter term are the two follow-ups most likely to be asked for first; both are additive.
