# Design

## Context

- **The iPhone app today.** `mobile/ios` is a SwiftUI shell around a `WKWebView` that loads the user's server (`ios-shell`), published by `ios-distribution`. It does three native things: a widget, a share extension, and reminders scheduled on the device. All three get their data through a JavaScript bridge (`web/src/lib/shell.ts`). `mobile/android` is the same design in Kotlin.
- **What testers reported.** Lists, navigation, sheets and the keyboard feel like a website. The widget and push notifications were unreliable. They asked whether the app is made for iPad.
- **The shared code.** `web/src/lib` holds 392 non-test modules.
  - 114 of them use the Dexie database (`db.ts`).
  - About 93 name a browser global, nearly always behind a `typeof` guard. The ones on the sync path are in `sync.ts`, `http.ts` and `dates.ts`, plus `crypto.ts` through `crypto.subtle`.
  - The pure parts have no browser dependency: `hlc`, `recurrence`, `nlp/*`, `inbox`, `flow`, `closedList`, `filter/*`, `e2eeEnvelope`, `i18n/*` and `liveTasks`. They are already pinned by the shared vectors the Go ports check against.
  - `obsidian/` already bundles a subset of this code. It has a path filter that runs its CI only when its own files or the shared files it uses change. This design follows the same precedent.
- **The owner's setup.** The owner does not use Xcode. Every Apple build, signing step and upload already runs on GitHub's Mac runners (`ios-testflight.yml`).

## Goals / Non-goals

**Goals**
- An app that behaves like a native app because it is drawn with native views.
- One implementation of sync, ops, encryption and parsing: the shared TypeScript.
- A web developer's loop and the web CI exactly as fast as today.
- A trial installable next to the current app, so the decision to switch is made on evidence.

**Non-goals**
- Feature parity with the web app. The app is for the phone moments: capture, today, triage and checking off. Deep configuration stays on the web.
- A shared UI layer between web and app. Screens are written for each platform.

## Decisions

### D1. React Native with Expo, not Swift and Kotlin, not a better shell

| Option | Native feel | Cost | Shares the protocol code | Android |
|---|---|---|---|---|
| Polish the web-view shell | No: it is still a web page | Low | Yes | Yes |
| Capacitor or Ionic | No: also a web view | Low | Yes | Yes |
| Flutter | Close, but drawn by its own engine, not UIKit | High | No (Dart) | Yes |
| SwiftUI plus Kotlin | Best | Two full apps plus a port of the sync engine | No | Separate app |
| **React Native (New Architecture) with Expo** | **Native views: UINavigationController, UITabBarController, UIKit lists and sheets** | **Medium** | **Yes, it imports `web/src/lib`** | **Same code** |

React Native renders with platform views, so the tab bar, navigation, sheets and menus are the system's own. On iOS 26 the system tab bar comes with the current look for free. The protocol stays one implementation, guarded by the vectors that already exist. Expo provides the native-project generation (D9) that makes "no Xcode" workable.

Swift remains for what must be Swift: the widget, the share extension, App Intents and Live Activities. Those are app extensions that `native-app-handover` keeps from today's `mobile/ios`.

### D2. Same repo, behind a declared boundary

The app lives in `mobile/app/` (rejected: a separate repo).
- **Why the same repo.** The op schema is generated (`web/src/generated/opSchema.ts`) and checked by `go test`, and the shared vectors live here. One pull request that changes the protocol must fail if the app breaks. A separate repo would need the shared code published as a package and kept in step by hand.
- **The boundary.**
  - The app resolves `@shared/*` to `web/src/lib/*` through Metro's `watchFolders` and a TypeScript path.
  - `mobile/app/shared-modules.json` lists every shared module the app reaches. It is generated by `node mobile/app/scripts/shared-modules.mjs`, which walks the import graph from the app's entry with the TypeScript compiler `web/` already has.
  - The repo check fails when the list is stale, which takes about a second and needs no app install.
  - A lint rule in the app refuses imports from `web/src/app`, `web/src/ui` and any module that imports `dexie-react-hooks`, `react-dom`, `prosemirror-*` or `maplibre-gl`.

### D3. A platform port instead of browser globals

`web/src/lib/platform.ts` exports one `Platform` object, installed once at start-up. Its members:

```ts
interface Platform {
  visibility: { visible(): boolean; onChange(fn: (visible: boolean) => void): () => void }
  network:    { online(): boolean;  onOnline(fn: () => void): () => void }
  leader:     { request<T>(name: string, fn: () => Promise<T>, signal?: AbortSignal): Promise<T> } | null // Web Locks, or null: lead at once
  broadcast:  (name: string) => { post(m: unknown): void; on(fn: (m: unknown) => void): () => void; close(): void } | null
  prefs:      { get(k: string): string | null; set(k: string, v: string): void; remove(k: string): void }
  timeZone:   { current(): string; onChange(fn: () => void): () => void }
}
```

- **On the web.** The web implementation is exactly today's code: `document.visibilityState`, `navigator.onLine`, `navigator.locks`, `BroadcastChannel`, `localStorage`, and the time-zone watcher in `dates.ts`.
- **In the app.**
  - Visibility comes from `AppState`, and the network from `@react-native-community/netinfo`.
  - The leader is `null`, so the one process leads at once. Broadcast is `null`.
  - `prefs` is MMKV, and the time zone comes from `expo-localization`.
- **What uses it.** `sync.ts`, `http.ts` and `dates.ts` use the port and no longer touch globals. A repo check lists every browser global in a module of `shared-modules.json` and fails on a new one, so the boundary cannot erode.
- **Cost on the web.** It moves code and adds no behaviour. The first-load gzip budget is near its limit, so the port must stay within it. The design target is under 150 bytes, which `make bundle-budget` reports.

Cryptography stays `crypto.subtle`. In the app it is provided by `react-native-quick-crypto`, a native implementation of the Web Crypto subset `crypto.ts` uses (AES-GCM, PBKDF2, HKDF, random values). The shared envelope vectors (`e2eeEnvelope`) run on the iOS simulator every night, so the native implementation is checked against the browser's.

### D4. Local storage: Dexie on SQLite, chosen by measurement

The data layer calls Dexie in 114 modules, and rewriting them is not on the table. Dexie runs on any IndexedDB implementation it is handed (`new Dexie(name, { indexedDB, IDBKeyRange })`). Two candidates give it one on the phone:

- **A. A memory-resident IndexedDB with SQLite persistence.**
  - It uses `fake-indexeddb`, already a dev dependency of `web/`.
  - At start-up its object stores load from one SQLite file (`op-sqlite`).
  - Each committed IndexedDB transaction writes its changed records to SQLite in one SQLite transaction before the commit resolves.
  - Reads are memory-speed. Memory is about the size of the data: roughly 30 MB at the 10,000-task fixture.
- **B. `indexeddbshim` over SQLite.** IndexedDB semantics are implemented on SQL tables. It uses less memory, but every read is a SQL query through a compatibility layer.

The first task is a measured spike on the iOS simulator with the `perfseed` 10,000-task account. Three numbers decide: cold start to Today drawn, opening Inbox, and applying a 500-op pull page, against the budgets in the `performance-budgets` delta.
- The candidate that meets them with less code wins.
- If both meet them, A is chosen for its read speed and simpler failure modes: a crash loses nothing that was committed, because SQLite holds it.
- If neither meets them, the fallback is a SQLite adapter for the subset of Dexie's API the shared modules use (`get`, `bulkGet`, `put`, `bulkPut`, `where().equals()`, `toArray`, `transaction`). It sits behind `db.ts`'s existing `Table` types and has its own tests against the same suite.

The decision and the numbers are recorded in this design before `native-app-everyday` starts. The database is per account and per server, like the web app's, and is deleted at sign-out.

### D5. Sign-in through the system browser, with an authorization code and PKCE

A native sign-in form would mean reimplementing password, second factor, passkeys and single sign-on. Native passkeys would also need an associated domain, which no self-hosted server can give our app. Instead:

1. The app opens `https://<server>/app/sign-in?code_challenge=…&state=…` in `ASWebAuthenticationSession` (iOS) or a Custom Tab (Android). This is the system sheet that shares the browser's cookies and passkeys.
2. If the user is already signed in there, the page only asks to confirm "Sign in to the OpenTodo app on this device?", showing the device name the app sent. Otherwise the server's normal sign-in runs first. Every existing method works because it is the same page.
3. On confirm, the server redirects to `opentodo://signed-in?code=…&state=…`. The code is single-use, expires after 60 seconds and is bound to the challenge.
4. The app posts the code and verifier to `POST /api/v1/app/token`.
   - It receives an access token (1 hour) and a refresh token. The refresh token rotates on every use; reuse revokes the grant (RFC 6819 §5.2.2.3).
   - Tokens are stored in the Keychain or Keystore, never in MMKV.
5. The grant appears in the user's sessions as "OpenTodo app · iPhone", with its last use. Revoking it there, or "Sign out everywhere", ends it at the next request.

The server side reuses `internal/mcpoauth`: its code table, PKCE check and grants. It adds a built-in public client, `opentodo-app`, that is not listed with MCP clients and does not depend on the owner's MCP switch, plus the `app` scope. The `app` scope acts as a `full` token on the routes, so credential and administration routes stay refused, and the app links to the web for them.

Both new routes are declared policies:
- `/app/sign-in` is `signedIn`: it redirects to sign-in when there is no session.
- `/api/v1/app/token` is `public("app code exchange")` with a rate limit, mirroring the MCP token endpoint.

A demo instance denies `/api/v1/app/token` (`.demoDenied()`).

A custom URL scheme can be claimed by another app. PKCE makes an intercepted code useless without the verifier, which never leaves the app (RFC 8252 §8.1). The `state` value prevents injection.

### D6. Sync lifecycle on a phone

The shared engine runs unchanged: outbox, pull pages, live stream, hybrid clock.
- **Foreground and background.** On `AppState` active, the app pulls at once and reopens the stream. In the background it closes the stream after the outbox drains, within iOS's background grace period.
- **Background refresh** (`BGAppRefreshTask`) comes with the widget in `native-app-handover`.
- **Device id.** The app's device id is generated on first launch, like a browser's, so ops carry it and convergence is unchanged.

### D7. The UI stack, fixed here so every screen uses the same parts

Each dependency is a native-view library, not a JavaScript imitation:

- `react-native-screens` and `@react-navigation/native-stack`: UINavigationController, edge-swipe back, large titles, and sheets with detents.
- `react-native-bottom-tabs`: UITabBarController and the Material bottom navigation, with the platform's own look.
- `react-native-gesture-handler` and `react-native-reanimated`: swipe actions and drag at 60/120 fps on the UI thread.
- `@legendapp/list` or `@shopify/flash-list`: recycled lists. The `everyday` spike picks one with the 2,000-row scroll test.
- `@expo/ui`: SwiftUI and Jetpack Compose pickers, menus and date pickers where a native control exists.
- `expo-haptics`, `expo-localization`, `expo-secure-store`, `react-native-mmkv`, `op-sqlite`, `react-native-quick-crypto` and `@react-native-community/netinfo`.

Every dependency is pinned exactly, its version at least two weeks old when added, and listed with its reason in `mobile/app/DEPENDENCIES.md`. Adding one needs a line there, and the repo check compares the file with `package.json`.

### D8. No committed native projects; generation in CI

The app uses Expo's continuous native generation: `npx expo prebuild` writes `ios/` and `android/` from `app.config.ts` and config plugins, in CI and on demand. Nothing in them is edited by hand, and both are git-ignored.
- The owner never opens Xcode, and no hand-edited `.pbxproj` merges ever happen. This is the same reason `mobile/ios` uses XcodeGen today.
- The widget and share extension join through a config plugin in `native-app-handover`.

### D9. CI that leaves the web app alone

`scripts/ci-changes.sh` gains one answer, `app`. It is true when the changed files touch `mobile/app/`, a module in `mobile/app/shared-modules.json`, `web/src/generated/opSchema.ts`, the i18n catalogs the app loads, or the workflow and filter themselves.

| Job | Runner | Runs when | Time target |
|---|---|---|---|
| `app-check`: type-check, lint, unit tests (Jest with the shared vectors), the boundary check | Linux | `app` | ≤ 3 min |
| `app-ios`: prebuild, simulator build, simulator tests (Maestro flows: sign in against a CI server, Today, complete) | macOS | a `mobile/app/` change on a pull request; nightly; release | ≤ 25 min |
| `app-android`: prebuild, debug build, unit tests | Linux | a `mobile/app/` change on a pull request; nightly; release | ≤ 15 min |
| `app-perf`: the `perfseed` account on the simulator, D4's three numbers | macOS | nightly | n/a |
| TestFlight preview | macOS | `workflow_dispatch` and release tags | n/a |

Further rules:
- A web-only pull request, one that touches no shared module the app imports, runs no app job. A change to a shared module runs only `app-check`, never a Mac build.
- `app-check` has its own `node_modules` cache keyed on `mobile/app/package-lock.json`. The web jobs never install the app's dependencies, and `make check` does not run the app. `make app` does, and `make check APP=1` adds it.
- Dependabot groups the app's updates weekly in one pull request, so its lockfile does not churn the queue.
- The boundary and `DEPENDENCIES.md` checks run in the existing repo-check job. They are text checks, about a second, and need no install.

### D10. Distribution of the trial

The trial ships as a separate App Store Connect app, "OpenTodo Preview" (bundle id `app.open-todo.preview`), so it installs next to the current app and testers can compare them side by side.
- `ios-testflight.yml` gains an input `app: shell | native`. The native path prebuilds and archives `mobile/app` and uploads with the same `release` environment key.
- CI never submits for review.
- The owner creates the app record once, because Apple's API cannot. The workflow registers the bundle id (`ios-register-ids.yml`).

### D11. Server compatibility

On the server screen, the app reads `GET /api/v1/version`.
- A server without the app sign-in routes gets "This server needs OpenTodo 1.5 or later for the app" and a link to the update guide. No half-working fallback to a web view.
- The app's version follows the repo's version. Its minimum server version is a constant checked in its unit tests against `internal/version`.

## Data model

- No new synced field and no op change.
- **Server:**
  - a migration adds the `app` scope to the grants' check;
  - the built-in client is a seeded row;
  - app grants join the sessions query.

## Size and memory

- **Server:** binary under +20 KB (two handlers and a page template). The container image is unchanged.
- **Web app:** the platform port moves existing code. It targets ≤ 150 B on the entry chunk and is reported by `make bundle-budget`.
- **App:**
  - The download is about 25–35 MB (React Native with Hermes).
  - The resident memory at 10,000 tasks is measured by `app-perf`, with a target under 180 MB including candidate A's store.
  - Neither is part of the server or web budgets.

## Risks / Trade-offs

| Risk | Mitigation |
|---|---|
| **Two UIs to maintain.** | The app's scope is deliberately small (non-goals), and the protocol code is one implementation. A feature reaches the app only when its spec says so. |
| **React Native upgrades.** | Expo SDK upgrades once or twice a year as a pull request of their own. `app-ios` and `app-android` catch breakage before a release. |
| **The storage spike fails both candidates.** | The fallback is the Dexie-subset SQLite adapter. It is more code, but bounded by the API surface the shared modules use, which the boundary check lists. |
| **The Mac build loop is slow without a local simulator.** | Most work happens in `app-check` (Linux) and on Expo's dev client against a server. The Mac runs are for integration. Screens are checked through simulator screenshots uploaded as artifacts. |
| **App Store review of a second app.** | The preview goes to TestFlight only and is never submitted. When `native-app-handover` switches, the native app ships under the existing record and the preview record is retired. |

## Migration Plan

1. The platform port lands first on its own, with the web app unchanged and all web tests green.
2. The storage spike. Its decision is recorded here.
3. App sign-in on the server, with its tests.
4. `mobile/app` with sync and Today, plus the CI lanes.
5. The preview in TestFlight.

Each step is reversible on its own, and nothing user-facing changes for web users at any point.
