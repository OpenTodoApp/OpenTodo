# Design

## Context

Ciphertext travels through the op log as an ordinary string (`end-to-end-encryption`, "Transport through the unchanged operation log"):

```
"enc:v1:" + base64url(nonce(12) || AES-256-GCM(utf8(plaintext)) || tag(16))
aad = utf8(entity + "\0" + entityId + "\0" + field)
```

Each field converges by last-writer-wins on the operation's timestamp (`ts`, Unix milliseconds from a hybrid logical clock; ties by device id). The timestamp, device, sequence number and actor are op metadata the server stores and serves. Nothing authenticates them.

Writers of ciphertext today:

| Writer | Path | Who sets the op's `ts` |
| --- | --- | --- |
| Web app (`e2eeSync.prepareOutgoing`, at upload) | sync push | the device (HLC); the server clamps it for clients without the `clock_skew` feature |
| Obsidian plugin (`Keyring.seal`, `sealValue`) | sync push | the plugin |
| `ot vault` (`keyCrypter.Seal`) | sync push | `ot` |
| `ot mcp --decrypt`, `ot notes` (`crypt.Seal`) | MCP tools and REST, then `ApplyStrict` | the server's clock |
| Device relay (`relay.ts`, encrypt requests) | the server writes the envelopes it gets back | the server's clock |
| Routine device runs and proposals (`rules/deviceRun.ts`, `deviceProposal.ts`) | device commit, then the server applies | the server |

Readers: the web app (sync, history, activity, task and note pages, notification bell), `ot` (`internal/e2ee/crypt`), the Obsidian plugin (bundles `crypto.ts` and `e2eeEnvelope.ts`), `ot vault`, the device relay. The shared vectors `web/src/lib/e2ee.vectors.json` are generated by `internal/e2ee/vectors_test.go` and checked by `crypto.test.ts` and `internal/e2ee/crypt`.

## Threat model

**Adversary.** The server for an encrypted account: its operator, its disk and backups, or an attacker who controls the process. It holds every ciphertext it ever stored (op log, superseded operations until a purge, backups). It can drop, reorder, delay and replay operations, rewrite their metadata (`ts`, device, `seq`, actor), invent new operations around any ciphertext it holds, and answer each device differently. It does not have the account key and cannot run the device's code (tampered JavaScript is `signed-web-app`'s concern).

**Goals.**

- **G1, no rollback of a held value.** A device never replaces a content value it holds with a ciphertext written before that value.
- **G2, no replay under a new clock.** A ciphertext authenticates only with the operation timestamp it was written for. Last-writer-wins then orders every replayed ciphertext where it was written, on every device and on the server.
- **G3, no downgrade.** Stripping the version (serving a `v1` ciphertext of the same field) does not get around G1 once the device holds the field as `v2`.
- **G4, an older key record is noticed, not obeyed.** A device never adopts a key record older than the one it cached when the server serves it unchanged, and it never stops working over one. The record's version and creation time are not authenticated, so a hostile server can relabel an older record with current numbers: that is not defended in this change (see D6).
- **G5, no data loss on detection.** What the device refuses is never applied and never re-written over a value someone else wrote.

**Not goals** (documented as limits):

- **Freshness.** A server that withholds or deletes the newest operations shows the last value it lets through. A device that already holds a newer value keeps it.
- **A device that never held the newer value**: a new device, a device that never synced that field. It accepts whatever authentic value the server shows, within G2: the value must be the winner of the operations the server serves.
- **Forks.** The server can show different subsets of the history to different devices. Detecting that needs signed checkpoints that devices exchange (alternative A4).
- **Ties.** The stamp is the timestamp, not the device. Two writes of the same field in the same millisecond from two devices can be swapped. Both are authentic, concurrent values.
- **Plaintext values** and the mergeable note documents (`notes_doc`, Yjs updates: replaying an older update changes nothing) are outside this change.

## Decisions

### D1. The `v2` envelope

```
"enc:v2:" + base64url(stamp(8) || nonce(12) || AES-256-GCM(utf8(plaintext)) || tag(16))
stamp   = the operation's ts as an unsigned 64-bit big-endian integer, 1 ≤ stamp ≤ 2^53 − 1
aad     = utf8("opentodo/e2ee/v2\0" + entity + "\0" + entityId + "\0" + field + "\0") || stamp(8)
```

- The stamp is in the clear so the server can read it without the key (D3). It is also in the additional data, so changing it fails authentication.
- The label `opentodo/e2ee/v2` separates the two versions: a `v2` body relabelled `v1` puts the stamp's bytes in the nonce and the label is missing from the additional data, so it fails; the other way round the same.
- Same key, same AES-256-GCM, same 96-bit random nonces. The nonce bound (NIST SP 800-38D's 2^32 for random nonces per key) is unchanged.
- 8 more bytes, 11 more characters. `MAX_PLAINTEXT_BYTES` stays 48,000: its `v2` envelope is 64,057 bytes of JSON, still under the 64 KiB value limit. `e2ee.MaxPlaintext` (`fit.go`) and `MAX_DOC_CHARS_ENCRYPTED` (`docfields.ts`) subtract the 8 bytes.
- `isEnvelope` and `e2ee.IsEnvelope` already accept `enc:v[0-9]+:`. They are unchanged, so the server's checks and every placeholder path keep working.

### D2. The invariant: a `v2` value's stamp is its operation's timestamp

Every operation whose value is a `v2` envelope has `ts == stamp`. The device checks it before decrypting. The honest server enforces it on every write path (D3).

So the device needs no new counter. Its per-field clock (`_clock[field]`) is already the high-water mark: an old ciphertext can only arrive with its original timestamp, and last-writer-wins ignores it when the device holds a newer value. The convergence rule is unchanged.

Rejected: binding the device id too. Writers through REST and MCP do not know the device id the server will record (`mcp:<token>` and so on), and swapping a tie gains nothing (see Not goals).

### D3. Writers, and the server's timestamp rule

- **Sync push writers** (web app, Obsidian plugin, `ot vault`) seal at upload with the op's `ts`. The web app already seals at upload from the plaintext outbox, so an op re-stamped after a `clock_skew` refusal is sealed again. `sealValue` and `encryptValue` take the stamp; `vault.Crypter.Seal` gains it.
- **The server never clamps a `v2` op.** A `v2` op more than `MaxFutureSkewMs` ahead is refused `clock_skew`, even for a client that did not declare the feature (it is refused, not changed). A `v2` op whose `ts` differs from its stamp is refused `invalid_op` with detail `stamp_mismatch`.
- **Server-side writes of a client-made envelope** (REST, MCP tools, the relay's encrypt answers, import): the operation takes its timestamp from the stamp; the write's other fields keep the server's clock. Then the server's clock observes the stamp (receive rule), as with any stored op.
  - A stamp that would not win over the field's current operation, so it is not greater than that operation's `ts`, is refused 409 `stale_ciphertext` with `currentTs`. The writer seals again with `max(now, currentTs + 1)` and retries once (`ot`, `ot mcp --decrypt`).
  - A stamp more than `MaxFutureSkewMs` ahead is refused 400 `clock_skew`.
  - The relay's encrypt answers and routine device runs are sealed with the device's own clock (its HLC, past every op it pulled); the server stores them at that stamp like any server-side write. The relay request is unchanged.
  - Import keeps a `v2` value only when its stamp wins in the target account; otherwise the field is skipped and counted.
- **Routine undo** (`rules/routine_undo.go`) puts back the value before the run as a new operation. For a content field of an encrypted account, that value is an older envelope, which devices would refuse (D4). Undo lists those fields under `not_undoable` (`encrypted text`) instead, and restores the rest.
- No other server path writes a stored envelope again as a new operation. `ot vault`'s re-seed and the web app's re-seed after a server restore re-send operations with their original timestamps. A backup restore keeps the op log as it was. Task 4.6 checks this with a test over every `ApplyStrict` caller that writes a content field.

The server reads 8 bytes of base64. It runs no cryptography and still never links `internal/e2ee/crypt` (`TestServerDoesNotLinkCrypt`).

### D4. What a device does on detection

Before an incoming batch is applied (`decryptIncoming`), each content op is classified:

| Incoming value | Device holds | Result |
| --- | --- | --- |
| `v2`, stamp equals `ts`, authentic | anything | applied by last-writer-wins as today |
| `v2`, stamp differs from `ts` | anything | **refused** |
| `v2`, authentication fails | anything | undecryptable placeholder, as today |
| `v1` that would win | the field as `v2` (writer release on) | **refused** |
| `v1` that would win | the field as `v2` (reader release) | applied: honest writers still write `v1` there, for example an older `ot` next to a newer one |
| `v1` that would win | the field as `v1`, plaintext or nothing | applied, as today |
| `v1` or `v2` that would lose | anything | ignored by last-writer-wins, as today |

A refused op is left out of the batch. The field keeps its value and its clock, the pull cursor moves on, and sync continues. The device records it in a local list (`e2ee.olderVersions` in `meta`: entity, id, field, op id, server `seq`, time; at most 200, the oldest dropped), and Settings → Encryption shows one line while the list is not empty: "The server sent older versions of 3 items. This device kept its own." A **Details** button lists the items (title, field, date) with **Clear**. Nothing is re-written automatically: the device cannot tell a hostile server from a buggy one, and a re-write could replace a change someone else made. Editing the item writes the device's value again, as any edit does.

History pages (`displayValue` with the change set's `ts`) show a `v2` value whose stamp differs from its change's timestamp as "[Cannot decrypt]". Readers that have no op (`ot mcp --decrypt`, `ot notes`, a shared page's snapshot, the relay's decrypt requests) check authenticity only. `ot vault` and the Obsidian plugin's vault check the stamp in their store before applying, without the key (`OlderCiphertext`, `olderCiphertext`).

`RowEncryption` (local only) gains `v2?: Record<string, true>`: the fields whose current value arrived or left as `v2`. `markSent` and `decryptIncoming` set and clear it with the wire marks.

Rejected:

- **Apply and warn.** The attacker's value is shown and synced. Detection without protection.
- **Stop syncing**, as for a missing key record. A hostile server can stop sync anyway; a buggy one should not lock every device out over one field.
- **The undecryptable placeholder.** It hides the device's own good value.
- **Re-write the device's value at once.** It heals the server, but a false positive would overwrite someone's change. The user can do it by editing.

### D5. Existing values move to `v2`

- **Reader release (D8, step 1):** every reader opens `v2`. Writers still write `v1`.
- **The switch:** one constant per language turns the writer release on: `WRITE_V2` in `web/src/lib/e2eeEnvelope.ts` (the web app and the Obsidian plugin) and `e2ee.WriterRelease` in Go (`crypt.WriteV2` for `ot`). It turns on the `v2` writers and the refusal of `v1` over a value held as `v2` (D4) together.
- **Writer release (step 2):** every writer writes `v2`. A new value of the re-write job's catch-up, `format: 2` in `e2ee.covered` (`catchUpEncryption`), makes the next unlocked device that completes a sync re-seal every content value in the personal scope whose wire form is `v1`, as when a new kind is added to the job. It is resumable and idempotent: two devices racing write two `v2` ciphertexts of the same text, and one wins. From the writer release, `v1` is refused over a value the device holds as `v2` (D4); once the re-seal finished on a device, over any value it holds.
- **Purge plaintext history** also deletes the superseded `v1` operations afterwards. It is not needed for G1: a `v1` replay is refused once the field is `v2`.
- Fields of entities a device never held stay acceptable as `v1`. A pre-release `ot` creating a task writes those, and nothing is held to compare with. The writer release also refuses `v1` writes for encrypted accounts on the server (`ciphertext_outdated`: "Update the app, ot or the plugin"), so after it only a hostile server can produce them.

### D6. The key record high-water mark

A device keeps `e2ee.recordHighWater` (`createdAt`, `version`) of the newest key record it adopted. It survives turning encryption off (`setEnabled(false)`) and goes at sign-out.

- When `refreshFromServer` gets a record with an older `createdAt`, or the same `createdAt` and a lower `version`, it does not adopt it and never throws: it returns this device's cached record under the served version number, stores the served numbers (`e2ee.olderRecordServed`) and sets `olderRecord` in the snapshot. Sync, the re-send after a server restore, unlocking, a passphrase change and a reset all go on with the device's own record. A server honestly restored from an older backup must never lock a device out.
- Settings shows one line naming the served record's and this device's version and date, with **Upload this device's key record** (`reuploadKeyRecord`) behind a confirmation that says it replaces the server's record, and that a device which missed a passphrase change elsewhere brings its older passphrase back. The cached record goes up as the served version + 1 with its own `createdAt`. It wraps the same account key, so other devices keep decrypting and adopt it on their next refresh. A passphrase change or reset while the older record is served replaces it the same way.
- The server keeps a replaced record's creation time, except when the upload claims a later `createdAt` than the stored one (a device uploading the record of a later enablement over an earlier one): it then sets a fresh one, so every device sees the newest record. The uploading device keeps its key for the record it uploaded (`storeKey` before `setEnabled`, as in `restoreKeyRecord`), and a device whose cached record shares a wrap with a record of a new creation time keeps its key too: the same wrap means the same account key. A record with another account key still locks, as before. `ot` reports its key file as stale (a new version) until `ot encryption unlock` runs again.
- A record the device's own upload returns (enabling, a passphrase change, a reset, `restoreKeyRecord`, `reuploadKeyRecord`) is adopted and moves the mark, whatever its `createdAt`: the device made it.
- `ot encryption unlock` keeps the same mark next to its key file and keeps the stored key when an older record is served.
- **Limit:** `version` and `createdAt` are metadata the server sets; nothing authenticates them. A hostile server can serve an older wrap and salt under current numbers, and the device adopts it. So this notices an older record served unchanged (a restore, a mistake), not an attack. The writer release binds the record's numbers to the account key (a MAC under a key derived from the account key, checked after unwrapping) so that a relabelled record is noticed too.

No format change; it ships in the reader release.

### D7. Shared vectors

`e2ee.vectors.json` gains `contentV2`: the four `v1` cases sealed as `v2` with fixed nonces and stamps (one at 1, one at 2^53 − 1, the rest realistic), plus refusal cases: a stamp changed in the header, an envelope relabelled `v1`, a `v1` relabelled `v2`, a stamp of 0, a stamp above 2^53 − 1, a body too short for a stamp. `internal/e2ee/vectors_test.go` writes them with its independent Go implementation. `crypto.test.ts`, `internal/e2ee/crypt` and the Obsidian plugin's tests read them. `internal/e2ee` gets `Stamp(s string) (int64, bool)`, which the server's checks use, with the same cases.

### D8. Rollout

1. **Reader release.** Every reader opens `v2` and refuses a `v2` value whose stamp is not its op's timestamp, the server enforces D3 for `v2` ops (so a newer `ot` that writes `v2` early works against it), routine undo leaves `v2` fields out, the key record high-water mark (D6) ships as a warning, and writers still write `v1`. Nothing anyone sees changes, except the warning about an older key record.
2. **Writer release**, at least one release later (the owner picks the gap). Writers write `v2`, `MinClientVersion` and `CLIENT_VERSION` become 2, the catch-up re-seals (D5), the server refuses `v1` writes for encrypted accounts, and routine undo skips encrypted fields. The docs move Rollback to "Defended". A web app older than step 1 shows "Update required". An older `ot` or Obsidian plugin shows `v2` values as undecryptable (task 6.3 checks that each marks them undecryptable and never writes the placeholder back) and its `v1` writes are refused with an error that names the update.

## Data model impact

- **Op schema:** none. Content values stay strings and no field is added, renamed or removed. `TestGeneratedOpSchema` is unchanged.
- **Server:** no table or column. New refusals: sync `invalid_op` (`stamp_mismatch`), `clock_skew` for `v2` ops of clients without the feature; REST and MCP 409 `stale_ciphertext` (`currentTs`), 400 `clock_skew`; writer release: 409 `ciphertext_outdated`. The relay protocol is unchanged.
- **Device:** `RowEncryption.v2` (local), `meta` keys `e2ee.olderVersions` and `e2ee.recordHighWater`, and `format: 2` in the catch-up marker (writer release). No IndexedDB version bump: all are optional fields of existing rows. `ot`'s key file gains `record_created_at`.

## Size and performance

- No dependency, no image size change. Client code grows by a few hundred bytes gzip, inside `make bundle-budget`.
- One `subarray` and one comparison per incoming content op; the held form is read from the row the apply step reads anyway.
- The re-seal writes one operation per encrypted value once, like turning encryption on: about 1,500 for 500 tasks (`e2eeMigration.perf.test.ts` covers the job's speed).

## Interface budget

One line in Settings → Encryption, only while refused versions are recorded, with a **Details** button that opens a list in a dialog. No new chrome above any list, no task property, no sidebar destination, no scroll region, no shortcut.

## Alternatives considered

- **A1. A writer-chosen time or counter in the envelope, checked against a per-field high-water mark, with no server change.** The order of stamps and the order of last-writer-wins (`ts`) disagree whenever a writer's clock is off or a REST write is stamped by the server. The device then either refuses legitimate concurrent edits (divergence) or has to allow a tolerance window that is also the attack window. Tying the stamp to `ts` (D2) removes the comparison altogether.
- **A2. A per-field version number (n + 1).** Two offline devices both write n + 1. It needs a sequencer, which is the server.
- **A3. A hash chain per field** (each value authenticates its predecessor). Concurrent edits fork it, and compaction and the purge delete its links.
- **A4. Signed checkpoints over the whole account** (a version vector or a Merkle root, in the style of SUNDR or SPORC fork consistency). It also detects withholding and forks, but needs a total order and every device to sign and exchange checkpoints. That is a much larger design and at odds with offline-first. Possible later, on top of this one.
- **A5. A separate authenticating op field per content field**, which leaves the value readable by old clients. Twice the operations, the same timestamp problem for REST writers, and the server can drop the field and claim an old client wrote the value, until old clients are refused. That is the same compatibility decision with more machinery.
- **A6. The stamp inside the plaintext.** Old readers would show it as text, and the server could not enforce D3.
- **A7. Bind the server's `seq`.** Writers do not know it, and it says nothing about the order of last-writer-wins.

## Risks

- **False refusals.** The invariant holds for every writer listed in Context, and the honest server enforces it, so a refusal means a server that broke it. A bug in a writer would show up as refusals, not as data loss: values are kept (G5), and the tests in tasks 3 and 4 cover every writer.
- **Old clients during the gap.** Step 1 changes no stored value, so the gap only delays the protection.
- **Op volume of the re-seal.** One pass, like turning encryption on. Purge afterwards if the history size matters.

## Owner decisions (2026-11-25)

1. **The breaking format and the two-step rollout (D8): approved.** The reader release comes first; the writer release, which bumps `MinClientVersion` to 2 and refuses `v1` writes, follows after a gap the owner picks.
2. **Server-side writes of a `v2` envelope take their timestamp from it (D3), with 409 `stale_ciphertext`: approved.**
3. **Detection (D4): keep the device's value and report it in Settings → End-to-end encryption: approved.**
4. **Routine undo (D3): encrypted fields are reported as not undoable** (the recommendation).
5. **The re-seal (D5) runs automatically after the writer release, then `v1` is refused** (the recommendation).
