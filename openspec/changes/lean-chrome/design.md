# Design

## Context

See proposal.md for motivation. The four pieces of chrome live in four places today:

- **The help line.** `web/src/app/QuickAdd.tsx` keeps a per-device counter (`quickAddUses`, `countQuickAddUse`, `QUICK_ADD_HELP_USES = 3`) and renders `<HelpLink screen="quick-add">` under the chip preview until the third add. `quickAdd.test.tsx` tests the counter. The page header already renders one Help action per view (`PageHeader help=…`, `HELP_SCREENS` in `TaskListView.tsx`: `inbox`, `today`, … resolved through the `screens` front matter of `docs/built-in-views.md`); the quick-add screen id `quick-add#add-a-task` belongs to `docs/work-from-the-list.md`, which is also the Help landing's "Add a task with a date" page.
- **The demo banner.** `DemoBanner` in `web/src/app/App.tsx` renders the fixed string `DEMO_BANNER` from `web/src/lib/demo.ts` ("… deleted after 2 hours of inactivity …") in a `role="status"` strip above the shell, with the write-limit notice as a second line when `sync.state === 'limited'`. The server already reports `demo.sandboxHours.{idle,max}` and `resetsAt` in `GET /api/v1/auth/status`; `setDemo()` remembers the stable part under `localStorage['opentodo.demo']`, and the sign-in card (`AuthScreen.tsx`) already interpolates `{idle}` and `{max}` from it. `demo.test.tsx` asserts the fixed string; `scripts/docs-screenshots.mjs` and `scripts/screens.mjs` hide `[data-testid="demo-banner"]`.
- **The first-run card.** `web/src/app/FirstRun.tsx` exports `useFirstRun()` (no prefs row or no task yet, not `first_run: 'done'`; sticky once shown) and `FirstRunCard`, which `TaskListView.tsx` renders as a `section` inside `[data-list-page]` before the rows when the route is the Inbox. Step 2 renders `MethodModeChooser` (`writeOnChoose={false}`) and the theme buttons; "Show me around" calls `createSampleProject()`. `firstRun.test.tsx` covers the four scenarios by `data-first-run*` hooks. `useFirstRun` does not wait for the device's first sync, which is why a demo sandbox (seeded through the op log after sign-in) shows the card for a moment or for good; `useWelcome` in `WelcomeDialog.tsx` already waits for `useSyncStatus().lastSyncedAt` and refuses the demo. `HowYouWorkSection.tsx` is the Account section's "How you work" card (`Anchor id="how-you-work"`).
- **Empty states.** `web/src/ui/patterns/EmptyState.tsx` takes `icon`, `title`, `body` and a free `action` node; `ListChrome.tsx` wraps it with a second button line and a `kbd` hint on fine pointers; `MethodListView.tsx` and `TriageView.tsx` pass a body sentence; `TrashView.tsx`, `FilterView.tsx`, `SavedViewView.tsx`, `MonthView.tsx` and `calendar/WeekAgenda.tsx` print a grey paragraph instead. `budget.test.tsx` counts `[data-list-page]` children before the first `[data-task-id]` (`MAX_CHROME_ROWS = 2`) and excludes `[data-overlay-root]` from the scroller count.

Constraints: the overlay primitives (`Dialog`, `Popover`, `Tooltip`, the overlay stack with `trapTab` and `useOverlay`) are the only overlays; `Dialog` is a centred card from 640 px and a full-screen sheet below. Tokens only, icons from the vendored set (`circle-help`, `x`, `info`, `plus`, `rotate-ccw`, `download` exist). Keyboard hints are discoverable, not printed (interface guide rule 5); `Tooltip` takes a `shortcut`. No new shortcut: `q` (`list.quick-add`), `?` (`global.help`), `g ?` (`go.help`) and Escape (overlay stack) are the ones involved, all registered in `web/src/lib/shortcuts.ts`.

## Goals / Non-Goals

**Goals:**
- Two rows of chrome above the first item in every list, on every device, on the first visit and on the demo.
- One empty-state contract enforced by the primitive's types, so a view cannot add a second button or a hint line without changing `web/src/ui`.
- The first run as an overlay that reuses `QuickAdd`, `MethodModeChooser` and `Dialog` unchanged, with the same test hooks (`data-first-run`, `data-first-run-step`, `data-first-run-next`, `data-first-run-skip-all`, `data-first-run-sample`, `data-first-run-mode`).
- The demo line's number from the server, so a change of `SandboxHours` in `internal/demo` needs no client change.

**Non-Goals:**
- No change to what the first run writes (`first_run: 'done'`, the "How you work" preference, the sample project, the starter contexts, the device's start view), to the welcome note, or to the server.
- No new overlay primitive: the bottom sheet is a placement of `Dialog`.
- Settings panels keep `EmptyState`'s `icon` and `body` until `settings-copy`; this change removes them from task views only.

## Decisions

**D1. The help line goes, and nothing replaces it in the list.** `QuickAdd` loses `helpOffered`, `quickAddUses`, `countQuickAddUse`, `QUICK_ADD_HELP_USES` and the `HelpLink` import; the localStorage counter is no longer read or written (an old key is left alone; it is harmless). The page header's Help action keeps the view's target (`inbox`, `today`, …): the view's section in `docs/built-in-views.md` and the project and label guides link `[quick add](quick-add.md)` in their first paragraph, and `web/scripts/docs/check.mjs` gains a rule that every page declaring a list screen (`inbox`, `today`, `upcoming`, `anytime`, `someday`, `assigned`, `completed`, `project`, `label`) links `quick-add.md` in the section the screen points at. Alternative: make the header's Help open the quick-add guide while the field has focus. Rejected: a Help action whose target depends on focus is unpredictable, and opening the panel moves focus anyway. Alternative: keep the line for the first add only. Rejected: it is still a row, and on the demo every visitor is a first add.

**D2. One banner line, text from the device's demo record.** `DEMO_BANNER` becomes a function `demoBannerText(info)` returning `t("Demo: private sandbox, deleted after {idle} h of inactivity. Don't store anything personal.", { idle })` with `idle = info.sandboxHours.idle`; `demoDetailsText(info)` adds the maximum age (`max`) and the nightly reset. `DemoBanner` renders one flex row: the sentence in `truncate min-w-0` with the second sentence in a `hidden sm:inline` span, a "Learn more" text link (`openHelp('demo', el)`; `docs/getting-started.md` declares `screens: [demo#try-the-demo]`), a Details `IconButton` (`circle-help`, `Tooltip` with the full text on fine pointers, a `Dialog` on coarse ones, decided by `useFinePointer()`), and a Dismiss `IconButton` (`x`). Dismissal is `sessionStorage['opentodo.demoBannerDismissed'] = '1'` behind a tiny store in `web/src/lib/demo.ts` (`dismissBanner()`, `useBannerDismissed()`), so a reload in the same tab keeps it hidden and a new session shows it again; nothing is synced or sent. While `sync.state === 'limited'` the row shows `DEMO_LIMIT_NOTICE` in the warning tone, dismissed or not, because that notice is about data the person is typing now. The strip stays `role="status"` with `data-testid="demo-banner"`, so the screenshot scripts keep hiding it. Alternative: a toast for the limit notice. Rejected: a toast leaves after eight seconds and the limit lasts an hour.

**D3. The start guide is a `Dialog` with a new `placement="sheet"`.** `Dialog` gains `placement?: 'center' | 'sheet'` (default `center`, unchanged). With `sheet`, below 640 px the card is anchored to the bottom (`fixed inset-x-0 bottom-0`, `rounded-t-card`, `max-h-[66vh]`, its body scrolling inside the overlay root, `pb-[env(safe-area-inset-bottom)]`), slides up over `--duration-ui` and only fades under reduced motion; from 640 px it is the ordinary centred card. The scrim, focus trap, Escape and the overlay stack are the ones every dialog has. Alternative: a non-modal sheet so the list stays interactive. Rejected: two focus regions on a phone, and the overlay stack has one modal model; the guide's first step has its own quick add, so nothing behind it needs focus. Alternative: `Popover` anchored to the floating add button. Rejected: a popover is dismissed by scrolling and has no title row.

**D4. The guide owns its first step's quick add.** `FirstRunGuide` (the renamed `FirstRunCard`, same file) renders `<QuickAdd autoFocus hideHint placeholder="Call the dentist tomorrow at 3pm" onAdd={createTask with project_id null}>` inside step 1, the way the Loop home and `QuickAddSheet` do; the task appears in the Inbox behind the overlay through the live query and `useTopLevelTaskCount()` moves the guide to step 2, as today. Steps 2 and 3 are unchanged (`MethodModeChooser` with `writeOnChoose={false}` and `offerPreselected`, the theme radio row, Install or How to install). The footer keeps Continue / Skip this step / Show me around / Skip all; the dialog's Close, Escape and the scrim call the same `finish()` as Skip all (`setFirstRunDone()`), so the guide never reappears after any close, matching the welcome note. Alternative: keep the card's "focus the quick add behind" and make the dialog non-modal. Rejected with D3.

**D5. The guide mounts in the Shell and opens after the welcome note.** `Shell.tsx` renders `<FirstRunGuide>` beside `<WelcomeDialog>`; a one-line store `web/src/lib/startGuide.ts` (`openStartGuide()`, `closeStartGuide()`, `useStartGuideRequest()`, the pattern of `helpRequest.ts`) lets Settings reopen it. `useFirstRun()` gains the two conditions `useWelcome` has: not on a demo (`useDemo()`), and only after this device's first sync (`useSyncStatus().lastSyncedAt !== null`), so a seeded sandbox or a second device never shows it before the account's rows arrive; and it yields while `useWelcome()` is true, so the welcome note closes first. The guide opens automatically only while the current route is the Inbox (as the card did), so a start view of Today does not get a guide about the Inbox over it; it opens there on the first visit to the Inbox. `TaskListView.tsx` drops `showFirstRun`, `FirstRunCard` and `useFirstRun`, so the list page is the same on a fresh account as on any other. Reopened from Settings the guide renders over Settings with step 1's quick add creating Inbox tasks like the sheet does; nothing is written until a step writes, and Close writes nothing (`finish()` is only called when `useFirstRun()` opened it).

**D6. "Show the start guide again" in How you work.** `HowYouWorkSection.tsx` adds a ghost `Button` (`rotate-ccw`) under the chooser that calls `openStartGuide()`. Settings → Account is where the preference lives (`settings-navigation`: the You group holds Account), so the open-loops spec names it there. No new settings row pattern: it is the section's last action, as the interface guide puts a primary action of a card.

**D7. `EmptyState` becomes a contract, not a slot.** New props: `title: string` (one sentence), `action?: { label: string; onClick: () => void; shortcut?: string }`, `secondary?: { label: string; onClick: () => void }`, `testId?`; `icon` and `body` stay optional and are documented as settings-only until `settings-copy`. It renders `<section role="region" aria-labelledby>` with an `h2` in `text-body font-medium text-default`, one `Button variant="primary" size="sm"` wrapped in `Tooltip` with the shortcut only when `useFinePointer()` is true, and the secondary as a text link button (`text-meta text-accent underline`). `ListChrome.EmptyState` becomes a thin table lookup (`EMPTY_COPY[view]`) that passes `action.shortcut = keysOf('list.quick-add')` for "Add a task" and the links of the "Empty views" table; `data-empty-state`, `data-empty-action` stay, `data-empty-hint` goes. `MethodListView`, `TriageView`, `TrashView`, `FilterView`, `SavedViewView`, `MonthView` and `WeekAgenda` use the primitive with the table's copy; the Day view's agenda and the week's agenda share one "Nothing planned." with "Add a task" opening quick add with that day as the date (the month's `q` on the focused day already does this). The project's "Show n completed" link turns on the per-device "Show completed tasks" preference the project menu uses. Alternative: keep the hint line on fine pointers, as the first-run spec had it. Rejected: rule 5 of the interface guide, and the tooltip carries the key without a row.

**D8. Stories and baselines.** `Patterns.stories.tsx` gets `EmptyState/Action`, `EmptyState/With link` and `EmptyState/Phone` (375 px); `Overlay.stories.tsx` gets `Dialog/Sheet` at 375 and 1280; `web/src/app/firstRun.stories.tsx` renders the guide's three steps over a seeded Inbox with `withSeed`/`withClock`; a `DemoBanner` story at 360 and 1280 with the limit notice as a variant. Baselines land through the UI baselines workflow under `web/src/ui/__screenshots__/`.

**D9. Tests that pin the budget.** `budget.test.tsx` gains two cases: a fresh account's Inbox (no prefs row, no task, synced) has at most `MAX_CHROME_ROWS` children before its empty view and no `[data-first-run]` inside `[data-list-page]`; and no `[data-help-screen]` exists inside `[data-list-page]` outside the page header. `quickAdd.test.tsx` drops the counter cases. `demo.test.tsx` asserts the line for `idle: 3`, the session dismissal, the limit notice winning over a dismissal, and that Learn more calls `openHelp('demo')`. `firstRun.test.tsx` keeps its four scenarios against the dialog (`[data-overlay="dialog"] [data-first-run]`), adds Escape-closes-for-good, the sync wait, the demo refusal, and the welcome-first order; `howYouWork.test.tsx` adds the reopen case. `patterns.test.tsx` checks the primitive's region, heading, one button and the tooltip shortcut on fine pointers only; `dialog.test.tsx` checks the sheet placement's classes and that Escape and the scrim close it.

## Data model

No change. Reads: the user preferences row (`first_run`, `welcome`, the "How you work" value, `theme_mode`), `DemoInfo` from the device's demo record, the sync snapshot. Writes: only the ones the controls already make (`first_run: 'done'`, the "How you work" preference, `theme_mode`, the sample project's ops, the starter labels, the device's start view). Device-only state: `sessionStorage['opentodo.demoBannerDismissed']`. No op field added, renamed or removed; the op log format is unchanged.

## Size and resources

No dependency. Web bundle about +0.5 KB gzipped: the sheet placement (+0.3 KB), the banner's details and dismissal (+0.4 KB), the primitive's tooltip (+0.1 KB), minus the help line and its counter (−0.3 KB); moving `FirstRun.tsx` behind `lazy()` like the help bundle takes about 2 KB out of the main bundle, which the task list makes optional. Container image, binary and runtime memory unchanged. No request is added: the banner reads the demo record the status already fills.

## Interface budget

Rows of chrome above the first item, before → after:

| View | Before | After |
| --- | --- | --- |
| Inbox, fresh account, first visit | 4 (header, quick add, help line, first-run card) | 2 (header, quick add); the guide is an overlay |
| Inbox, Today, Upcoming, Anytime, Someday, Assigned, a label, before the third add on a device | 3 (header, quick add, help line) | 2 |
| A project, before the third add | 4 (header with the layout switch, quick add, help line, the allowance of 3 the budget test grants) | 3 (within its allowance) |
| Any screen on the demo, phone | the banner above the shell, 3 lines | 1 line |
| Any screen on the demo, desktop | 1 line, 2 with the limit notice | 1 line |

Task properties visible by default: unchanged (rows are out of scope). Primary sidebar destinations: unchanged. Vertical scroll regions: the guide's sheet body scrolls inside `[data-overlay-root]`, which the budget excludes, so every screen stays at 3; the banner does not scroll. Shortcuts: none added; `q`, `?`, `g ?` and Escape keep their registered meanings and the sheet closes on Escape through the overlay stack.

## Risks / Trade-offs

- [A modal guide on the first visit is more interruptive than a card] → one step at a time, Escape and the scrim close it for good, and it opens only once per account; the welcome note already set this precedent.
- [The quick add inside the guide and the quick add behind it look like two fields on a desktop] → the dialog's scrim dims the page and the guide's field is the one with focus; the step's sentence says "Type a line here".
- [Translators have to redo every empty sentence and the banner in six locales] → one table in the spec, one `EMPTY_COPY` map in code, the i18n check fails on a missing key.
- [Truncating the banner on phones hides "Don't store anything personal."] → the sign-in card said it in full one screen earlier, Details repeats it, and the sentence is one tap away.
- [A guide reopened from Settings over Settings creates Inbox tasks the person cannot see] → step 1's sentence names the Inbox, and the task count in the sidebar rises at once.
- [Old devices that stored the quick-add counter] → the key is simply unread; nothing breaks.
- [`budget.test.tsx` renders `TaskListView` without the Shell, so it cannot see the overlay] → the new case checks the list page only, and `firstRun.test.tsx` renders the Shell for the overlay.

## Migration Plan

Pure UI. Ships with the web bundle; no data migration. A device with an unfinished first-run card sees the guide instead on its next load, at step 1 (the step was never stored). Rollback is reverting the commit; the `first_run` preference means the same before and after. Docs screenshots that show the Inbox on a first visit (`your-first-task`) are regenerated with `make docs-screenshots`.

## Implementation notes

- **EmptyState's legacy slot.** The free `action` node became `action: { label, onClick, shortcut? }`. The settings panels, the labels page and the review's project walk still pass a node, so the old slot is kept as `control?: ReactNode`, settings-only next to `icon` and `body`, until `settings-copy`; those callers were renamed mechanically. The primitive renders `section[aria-labelledby]` with the sentence as `h2`, `data-empty-action` on its one button and `data-empty-secondary` on its link, and gained `compact` (less padding, an `h3`) for an empty day inside a list of days headed by `h2` (the week's agenda, the month's day list).
- **"Add a task" on a touch device** opens the Shell's quick-add sheet through `requestQuickAddSheet()` (registered by the Shell with `onQuickAddSheetRequest`, both in `QuickAddSheet.tsx`); with a fine pointer, or when the list renders without a Shell, it focuses the view's own quick add.
- **Calendar day.** The week's agenda (below 640 px) and the month's day list show "Nothing planned." with "Add a task", which opens quick add with that day as the date (`calendar/AddOnDayDialog.tsx`, now shared by the Month's `q` and the agenda). The Day view's time grid shows no empty view: the empty grid is itself the planning surface, and an empty view there would be a row of chrome above the grid; its quick add stays the plan panel and `q` in Month. This is the smallest faithful reading of the "Calendar day" scenario.
- **The `quick-add` help screen** (`quick-add#add-a-task` in `docs/work-from-the-list.md`) is no longer named by any page: the help line was its only user, and the docs check fails on a screen no help link uses. The Help landing's "Add a task with a date" entry opens the page `quick-add` (`docs/quick-add.md`) as before, and every list section links it. The docs check's new rule (`quickAddLinkProblems` in `web/scripts/docs/check.mjs`) requires the link in the section's lead, the text from its heading to the next heading.
- **Banner text.** The line is two catalog messages, "Demo: private sandbox, deleted after {idle} h of inactivity." and "Don't store anything personal.", so the second can be hidden below 640 px. `demoBannerText()` joins them; `demoDetailsText()` adds the maximum age and the nightly reset, with its time on the user's clock when the record has `resetsAt`. The banner lives in `web/src/app/DemoBanner.tsx` (re-exported from `App.tsx`). While the limit applies the line shows the notice in the warning tone with Details (the notice in full) and no Dismiss; once writes are accepted again a banner that was dismissed stays hidden, otherwise the demo line returns. `reloadBannerDismissed()` re-reads the session flag (tests, stories).
- **Start guide.** `FirstRunGuide` (host) and `StartGuide` (the dialog, exported with `initialStep` for the stories) are in `FirstRun.tsx`, which the Shell loads as a lazy chunk (main bundle −3.4 KB gzipped, the chunk 5.9 KB raw). A guide reopened from Settings moves past step one only through its own quick add (the account already has tasks); one that opened itself also moves on when any quick add adds the first task, as the card did. `lib/startGuide.ts` holds the reopen request in memory only. On a demo instance the guide never opens, so How you work does not offer "Show the start guide again" there.
- **Visual baselines** could not be generated here: `make ui-baselines` runs inside the pinned Playwright Docker image and this session has no Docker daemon. The new stories (UI/Patterns `EmptyState/Action`, `EmptyState/With link`, `EmptyState/Phone`; UI/Overlay `Dialog/Sheet`; Screens/Start guide ×3; Screens/Demo banner ×2) have no baselines yet, and the existing baselines of stories that render an empty view (Screens/Task list "Empty") or the quick add's help line change; they are to be taken from the CI run's `ui-check-report` artifact, as earlier changes did.
- **Checked in Chromium instead.** The workbench was built (`npm run build-storybook`) and the new stories rendered with the bundled Chromium at 375 and 1280 px: the start guide's sheet is 528 px of an 800 px viewport on its tallest step (at most two thirds), and the demo banner is one 37 px line at both widths, with or without the limit notice. Below 640 px the banner uses the meta size so more of the sentence fits before the ellipsis.
- **Docs screenshots** were not regenerated: no guide page shows the first visit (the seeded demo never opens the guide), and a `make docs-screenshots` run in this session failed on about thirty unrelated shots (timeouts, a strict-mode locator in the label menu) and rendered with the live date and spell-check marks, so its output was discarded. The quick-add images still show the old Help line under the field until the next regeneration. Tasks 1.3, 3.4, 4.5, 4.6 and 6.2 stay open for the baselines, the screenshots and the manual `make dev` pass.
