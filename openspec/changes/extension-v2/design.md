# Design

## Context

See proposal.md for the motivation. Relevant current state:

- `extension/` is Manifest V3, plain JavaScript, no build step: `background.js` (action, context menu, command), `share-url.js` (pure helpers mirrored from `web/src/lib/share.ts`), `options.html`/`options.js` (server URL, screenshot permission), six `_locales` catalogs, `node --test` units and `locales.test.js`. `make extension` refuses `host_permissions` and `content_scripts`, keeps the optional `http(s)://*/*` host permission that the options page narrows to the server's origin, and zips one package; CI uploads it and attaches it to releases.
- The capture screen (`/share`) parses its title line with the web quick-add parser, closes itself when opened as a popup, and works from the app's offline cache once the app was loaded in that browser.
- `internal/quickadd` is the Go port of `web/src/lib/nlp`, pinned by `web/src/lib/nlp/quickadd.vectors.json`, used by `ot add --natural` (`internal/cli/cmd_tasks.go`: builds a `quickadd.Context` from the account's languages and projects, posts the fields to `POST /api/v1/tasks`, then creates reminders and a closed time entry) and by the importer, so it is already linked into the server binary. `internal/origin` recognises GitHub, GitLab, Jira and Linear links (`Recognize`, `FromURL`) and is pinned by `internal/origin/testdata/origin_vectors.json`.
- `POST /api/v1/tasks` takes `title`, `description`, `project_id`, `priority`, `due`, `labels` (ids of existing labels), `estimate_minutes`, `deadline`, `start`, `evening`, `recurrence`, `origin`; `POST /api/v1/labels`, `/api/v1/reminders` and `/api/v1/time-entries` exist. Token scopes: `read` is refused on every write; `full` and `admin` write; `agent` writes only under the assistant switches.
- `task.origin` is `{kind, provider?, id?, url?, title?}`; `email` needs an `id`, `url` and `provider` are already allowed on every kind by validation; the chip reads the provider for `issue`, the host for `url`, "Email" without a link for `email`. The filter term `origin: value` matches any provider.
- Session cookies are `SameSite=Lax`, so a request from an extension page would not carry them; a bearer token is the only credential that works from the extension, and a cross-origin `fetch` from an extension page needs a host permission for the server's origin, which the screenshot flow already asks for.

## Goals / Non-Goals

**Goals:**
- Capture in two or three keystrokes without a new window, with the same quick-add grammar as the app, and the right project chosen before saving.
- Keep the default install as private as today: no token, no requests, no host permission, until the user turns Quick save on.
- Reuse the server's parsers instead of shipping a second copy of 140 KB of parsing code into a plain-JS extension.
- Two store-ready packages from one source, with texts, disclosure and checklist in the repository.

**Non-Goals:**
- An outbox or retry queue in the extension (the capture screen is the offline path; the app owns offline).
- Reading message bodies, page content or anything beyond the tab's title, the selection and the mail header the user clicked on.
- A framework or bundler for the extension's own code; the popup stays plain HTML, CSS and ES modules.

## Decisions

**D1. Parsing happens on the server, through a new read route.** The popup sends the line to `POST /api/v1/quick-add/parse` and shows the chips it returns; on Save it posts the returned fields. Why: the grammar needs the account's languages, date order, week start, projects and labels, which the extension would have to fetch anyway; the Go port is already in the server and pinned to the web parser by the shared vectors, so the three clients (app, CLI, extension) stay one grammar; the extension stays small and buildless. Alternatives: (a) bundling `web/src/lib/nlp` into the extension with a Vite build: about 40 KB gzipped more in the zip, a build step and a second vocabulary copy to keep in step, and still a request for projects and labels; rejected. (b) Only the capture-screen hand-over (today): no inline chips, no project choice before the window, a new window per capture; kept as the default mode and the fallback, not as the only path. (c) `POST /api/v1/tasks` taking a `natural` line: one request fewer, but no preview while typing and a write route that parses, which the CLI deliberately does not have; rejected. The parse route is pure, accepts `read` tokens, is rate limited (60 a minute per account, counted in `internal/httpapi` like comments), and takes `today`/`now` from the caller so the extension's local date wins over the server's clock.

**D2. Two modes, Capture screen by default.** `storage.sync` keeps `server` and `mode`; `storage.local` keeps `token` (never synchronised by the browser). Quick save needs a `full` or `admin` token (verified on the options page with `GET /api/v1/me`, whose `auth.scope` the page shows) and the optional host permission for the server's origin (the same `permissions.request` the screenshot flow uses, asked from the Save click on the options page). An `agent` token is refused for Quick save with the reason that it writes only under the assistant switches; a `read` token is accepted for parsing but leaves Quick save off. Tokens over plain `http` are refused except for `localhost` and `127.0.0.1`. Alternative: cookies with `credentials: 'include'`: blocked by `SameSite=Lax` and would need the server to relax it; rejected.

**D3. The popup is the one entry point.** `action.default_popup` is `popup.html`, so the toolbar button and `_execute_action` (Alt+Shift+O) open it; the context-menu entries open it too by storing the clicked thing (`{title, text, url, origin_url, image_url}`) in `storage.session` under one key and calling `action.openPopup()` where the browser supports it (Chrome 127+, Firefox), else the old popup window with `/share` as today. The popup reads the pending capture once and clears it. The selection is read in `background.js` as today (`scripting.executeScript` under `activeTab`); the popup never injects scripts itself. Why: one surface to translate, test and screenshot; the existing `/share` window stays the path for screenshots and for signed-out captures.

**D4. Quick save writes exactly what the CLI writes.** `api.js` mirrors `ot add --natural`: create missing labels (`POST /api/v1/labels`), `POST /api/v1/tasks` with the parse's fields plus `origin` and the description (selection, blank line, the page address), then `POST /api/v1/reminders` per reminder and one closed time entry for `spent_minutes`. An idempotency key (`Idempotency-Key`, a random id made when the popup opens) makes a retry after a timeout safe and the popup disables Save while a request is in flight. Why: one documented recipe for "a line becomes a task" across clients, and the reminders and time entries keep their own routes and validation.

**D5. Mail recognition is a pure module with fixtures.** `mail.js` exports `recognizeMail({url, title, header})`: host match (`mail.google.com`, `outlook.office.com`, `outlook.live.com`), subject from the title by cutting the client's suffix (`" - <account> - Gmail"`, `" - Outlook"`, `"Mail - <name> - Outlook"`), the conversation or message id from the address (Gmail `#<folder>/<id>`, Outlook `/id/<id>`), and the sender from a header object that `background.js` fills with one `executeScript` on the click (Gmail: the sender element's `email` and `name` attributes of the open message; Outlook: the sender control in the reading pane; the selectors live in one table in `mail.js` with a note that a failed read means "no From line", never an error). The origin is `{kind: "email", provider, id, url, title}`, valid under the existing rules (`email` carries an `id`; `url` and `provider` are allowed on every kind). The app's chip (`taskOrigin.ts`) reads the provider as "Gmail"/"Outlook" when an `email` origin has a `url`. Alternatives: a content script on the mail hosts (needs host permissions, runs without a click; rejected), server-side recognition of mail permalinks (the server would learn the user's mail host without need; rejected, mail recognition is the one thing the server does not do). Fixtures: `extension/testdata/mail/*.json` with title, address and header captured from both clients in two languages; the test fails loudly when a fixture no longer matches, which is the signal to update the selector table.

**D6. Issue recognition stays on the server.** The parse route answers `origin` for the page address through `internal/origin.FromURL`, so the extension carries no second copy of the recogniser and the shared vectors keep pinning one implementation. In Capture screen mode the app recognises the address in the capture screen as today.

**D7. One source manifest, two packages.** `manifest.src.json` is the manifest; `build.mjs` (Node, no dependencies, run by `make extension`) writes `dist/extension-chrome/manifest.json` (drops `background.scripts` and `browser_specific_settings`) and `dist/extension-firefox/manifest.json` (drops `background.service_worker`), copies the shipped files next to each, and zips both as `opentodo-browser-extension-chrome.zip` and `opentodo-browser-extension-firefox.zip`. The existing manifest check (no host permissions, no content scripts) runs on the source. `npx --yes web-ext@<pinned> lint` runs on the Firefox package and, with `--self-hosted` off, on the Chrome one (the linter is Firefox-oriented; Chrome's own rules are covered by the manifest check and a JSON-schema check of the keys Chrome knows). The version lives in the source manifest and must be the first entry of `extension/CHANGELOG.md`; the extension versions independently of the app. Alternative: two committed manifests; rejected, they drift. Loading unpacked for development uses `dist/extension-chrome/` after `make extension`, or the source folder with `manifest.src.json` copied to `manifest.json` (documented in the README; `manifest.json` is git-ignored).

**D8. Store texts live in the repository.** `extension/store/listing.<lang>.md` (name, summary, description) for the six languages, `extension/store/privacy.md`, `extension/store/screenshots.md` (the five shots to take, at 1280×800 and 640×400), and a release checklist in `extension/README.md` (bump the version, write the changelog entry, `make extension`, upload both packages, paste the listing, answer the permission justifications from `privacy.md`). A test (`store.test.js`) checks that every permission in the source manifest is named in `privacy.md` and that every listing has the three parts. The user guide gets the store links in the pull request that follows the first publication, not before (released facts only).

**D9. Popup size and accessibility.** 360 px wide, at most 480 px tall, system font stack and the extension's own small stylesheet (no tokens shared with the app: the extension has no build and must look right in the browser's popup frame in light and dark through `prefers-color-scheme`). Labels for every control, a live region for the chips and the status line, Enter saves, Escape closes, Tab order: line, project, labels, origin, Save. Why no React or Tailwind: the extension is buildless by decision; the popup is one form.

**D10. Size and footprint.** Extension zip: today about 24 KB; with the popup (about 6 KB HTML and CSS, 9 KB JS), `api.js` (4 KB), `mail.js` (4 KB) and the larger catalogs about 60 KB per package; store texts and fixtures are not shipped. Server: one handler file of about 200 lines; `internal/quickadd` and `internal/origin` are already linked, so the binary grows by a few KB and runtime memory does not change (the parse route allocates per request and keeps nothing). Web app: the chip change in `taskOrigin.ts` is a few lines, no bundle effect worth measuring. No new dependency anywhere; `web-ext` is a pinned development tool fetched by `npx` in CI and `make extension`, never installed into the repository.

**D11. Interface budget (web app).** The only screen change is the origin chip's words and link for a web mail origin: no new chrome, property, destination, scroll region or shortcut. The extension's popup is outside the app and outside the budget.

## Risks / Trade-offs

- [Gmail or Outlook change their page structure] → the subject and permalink come from the tab title and address, which are stable; only the "From:" line depends on selectors, and losing it degrades to a capture without a sender, with a failing fixture test as the signal to update the table.
- [A pasted token in the browser is a new secret to protect] → local storage only, https only, shown once on the options page, `Forget token`, and the recommendation in the docs to create a dedicated `full` token named after the browser so it can be revoked alone; the token is never logged by the server beyond the audit events tokens already produce.
- [`action.openPopup()` is not available in older browsers] → the context-menu entries fall back to the `/share` popup window, exactly today's behaviour; the toolbar button and the shortcut always open the popup.
- [Parse requests while typing add load] → debounce at 150 ms, no request for an empty line, the per-account limit of 60 a minute, and a reply that is cheap (no database read beyond projects and labels, cached for the request).
- [`web-ext lint` warnings differ between versions] → the version is pinned in the Makefile and CI; the lint runs with `--warnings-as-errors` off and fails on errors only.
- [Two packages double the release surface] → one source manifest, one build script, one CI job that produces both, one checklist.
- [The Chrome Web Store review asks why `scripting` and the optional host permission are needed] → `privacy.md` holds the justification for each permission in the words the review form asks for.

## Migration Plan

No data migration and no op-log change. Existing installs keep Capture screen mode: the new `mode` setting defaults to it and the stored `server` keeps working. The server's parse route is additive; an extension built from this change against an older server gets a 404 on parse, shows no chips, and Save still works through `POST /api/v1/tasks` (Quick save) or the capture screen. Rollback: an older extension package ignores the new settings; the route can stay.

## Open Questions

- Whether Fastmail and Proton Mail on the web should join the recognised clients in a follow-up; the module and fixtures are built so that adding a client is one table row and one fixture, and the spec names only Gmail and Outlook now.
- The exact debounce (150 ms) and the parse rate limit (60 a minute) can be tuned after measuring real typing without changing the specs' intent; the spec states the limit, so a change there is a spec edit at archive time.
