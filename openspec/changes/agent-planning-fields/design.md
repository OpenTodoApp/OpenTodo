## Context

See proposal.md for the motivation. Relevant current state, observed in the code:

- The agent tool registry (`internal/agenttools`) is the one place every assistant surface goes through: MCP (`internal/mcp`, transport `internal/httpapi/mcp.go`), the agent REST routes (`internal/httpapi/agent_rest.go`, which translates a body into tool calls and runs them as one write call) and the in-app assistant (`internal/assistant/loop.go`, which only ever calls `Plan`). `ot` with an `agent` token uses the agent REST routes, `ot mcp` the MCP endpoint. So one change to the registry reaches all five surfaces; the REST translator and the CLI flags are the only per-surface work.
- `planCreateTasks` and `planUpdateTasks` (`write_tasks.go`) whitelist their item keys with `it.only(...)`; the four planning fields and `location` are not in the list, which is the whole of issue #198. `checkPatch` already runs the op schema validation (`opsync.Validate`) on every planned field, and `internal/sync/ops.go` already knows `deadline` (`kDate`), `start` (`kStart`), `evening` (`kBool`), `blocked_by` (`kIDList`) and `location` (`kLocation`), so shape validation comes for free; what the planner must add is what `ApplyStrict` checks against state: blockers in scope and acyclic (`internal/sync/dependencies.go`, reasons `not_in_scope` and `cycle`) and a saved location that exists.
- `taskOut` (`data.go`) carries `due`, `overdue`, `recurrence`, `estimate_minutes`, `origin`, `fields`, `tracked_minutes`; nothing of the five fields. `render` is shared by every read, write result and resource, so one addition reaches them all.
- `agentPatchTaskCalls` routes known keys to `update_tasks`, `move_tasks`, `schedule_tasks`, `complete_tasks`/`reopen_tasks` and `trash_tasks`, and refuses the rest with `refusedField` (403 `insufficient_scope`), which is the error the issue reports. `taskCreateFields` is the create whitelist.
- `docs/api.md` "Agent tokens" already lists `deadline`, `start`, `evening`, `blocked_by` as accepted; `docs/mcp.md` lists the real (narrower) tool arguments. The in-app assistant's fixed instructions (`SystemPrompt`) describe dates as "floating calendar dates with an optional time" and know nothing of deadlines or Someday; the skills (`skills.go`) tell plan-week to "call schedule_tasks … for every task you plan", which is exactly the behaviour the issue complains about.
- The CLI (`internal/cli/cmd_tasks.go`) builds REST bodies from flags (`taskFlags.bind`); `--due` takes words and weekdays through `dates.go`. The human table has `ID P DUE PROJECT [ORIGIN] TITLE`, the `ORIGIN` column appearing only when a listed task has one; `schema/task.json` is embedded and checked against the agent skill text by `agent_test.go`.
- REST relative reminders: `ExtraOps` lets the transport add the reminder recomputation a REST `due` write triggers; `docs/api.md` says a `deadline` change recomputes deadline-relative reminders the same way. The agent transport must pass the same hook for `deadline`.
- `location` is a content field on both sides (`internal/e2ee.ContentFields`, `CONTENT_FIELDS`), written as one whole value; `internal/location.CheckValue` validates it; a saved location is the `place` entity, personal scope only. `origin` shows how a content object is handled for encrypted accounts in tool results (`IsCiphertextJSON` → `encrypted: true`, no members) and in schemas (`noCiphertext` for arguments that cannot be sent as an envelope; `location` can, so it is offered as ciphertext only like `title`).
- Per-user agent access is server state in `user_agent_access` (`access.go`), read into `Caller` by `agentCaller`; the per-user switch route is `/api/v1/me/agent-access`. Memberships are server state cached on the device (`db.memberships`, adopted on every sync). The share dialog (`ShareDialog.tsx`) has no Storybook story yet. Project hierarchy: a task belongs to one project; sub-projects are projects with `parent_id`.
- `inbox-means-unplaced` (open, archived before this change applies) already added `internal/inbox` with shared vectors for Inbox membership and reworded `list_tasks`' `inbox` view; the `someday` and `anytime` views follow the same pattern with the app's `web/src/lib` rules.

## Goals / Non-Goals

**Goals:**
- Every field an assistant can read it can also write, through every assistant surface, with the same validation and the same errors everywhere.
- The written word (docs, skill file, tool descriptions, fixed instructions) and the server agree.
- Assistants can follow the Open Loops places instead of forcing due dates.
- A project can be kept away from assistants by the person responsible for it, with no way for an assistant to see or undo that.

**Non-Goals:**
- Reminder tools, new write tools, new quick-add grammar, CalDAV `LOCATION`, per-member exclusions, a relay for encrypted accounts (see proposal).
- Changing what the app's own views list; the server reuses their rules.

## Decisions

**D1. Extend `create_tasks` and `update_tasks` rather than add tools.** The five fields become ordinary item keys of both tools, next to `due` and `priority`. Alternative: dedicated batch tools (`defer_tasks`, `set_deadline`, `block_tasks`) in the style of `schedule_tasks`. Rejected: `update_tasks` already takes up to 50 updates, so the batch case is covered; each new tool is another definition in strict tool schemas, another entry in every skill's tool list, another row in three docs tables, and another thing a model has to choose between; and the issue's own first preference is the fields on the existing tools. `schedule_tasks` stays as it is (due only) because its value is the "keep the time of day" rule, which no other field has.

**D2. Validation lives in the planner, mirrors `ApplyStrict`, and never lets a batch fail late.** The planner already promises that a planned change cannot fail the op schema (`checkPatch`). It gains three state checks so that `ApplyStrict` never refuses a batch the planner accepted:
- `blocked_by`: each id must be a live task visible in the snapshot (plus the call's overlay: a task created earlier in the same `create_tasks` call or the same in-app turn can be a blocker); a missing one is `not_found` listing the ids (same wording as every other missing id, so a foreign task is indistinguishable from a deleted one); each must share the task's scope after the call's own `project_id` (same `scopeKey` as `move_tasks`); the lists the call leaves behind, laid over the scope's current graph read once per call (`scopeBlockedGraph`, as `ApplyStrict` does per batch), must be acyclic. Self-reference, scope and cycle are `-32602` (`ArgError`) naming `items[i].blocked_by` and the id, because they are malformed requests the model can fix, where `not_found` is a state the model should re-read. Alternative: let `ApplyStrict` refuse and translate its reason. Rejected: the in-app assistant never applies on the server (the browser does), so its proposals would carry a change the device then has to refuse; and a refused batch costs a whole call for the MCP caller. The sync rule "accept an id it does not know" stays as it is for devices: an assistant, unlike a device, has no legitimate reason to write a dangling reference.
- `start`: the op schema accepts a date or `someday`; the planner additionally requires a real calendar date, as it does for `due` today, and for `deadline`.
- `location`: `location.CheckValue` for the shape; a `place_id` must name a live saved location of the caller (personal scope), and the planner copies that location's current `name`, `address` and coordinates into the value next to the `place_id`, which is what the app writes when a saved location is chosen (task-locations D2), so the task shows something even if the location is later deleted. A `place_id` with no live saved location is `not_found`. In a shared project a location is a plain value: the planner still copies the members, and other members see the stored members (task-locations D1). Rounding to six decimals as the app does.
- `evening`: `kBool` already refuses anything but a boolean.
- Roles: the five fields are task fields, so `CanWrite(role, "task", f)` applies as for `priority`: editors and admins may write them, viewers may not (`forbidden`, as today).

**D3. Write what is sent.** The tools do not reproduce the app's conveniences (clearing `due` when parking, un-parking on a new `due`): `docs/api.md` already documents REST as writing exactly what is sent, the agent REST routes must keep the documented REST meaning, and the in-app review shows each field as its own line, so an assistant that wants both changes proposes both. The tool descriptions say so in one sentence each ("parking does not clear the do-on date; send `due: null` too if you mean that").

**D4. Reads: the fields plus one derived value.** `taskOut` gains `deadline`, `start`, `evening`, `blocked_by`, `blocked` and `location`. `blocked` is derived in the snapshot (any id in `blocked_by` naming a live open task; completed or deleted blockers do not block, as the app derives it: task-dependencies "Blocked state is derived") because a model should not have to fetch every blocker to know whether a task is actionable. `location`'s `name` and `address` go into `untrusted_text.location` and its coordinates and `place_id` stay on the task, following `origin`. `list_tasks` gains the views `someday` and `anytime` and a `blocked` boolean filter; the resources list gains `opentodo://views/someday` and `opentodo://views/anytime`. The membership rules reuse the app's (`web/src/lib`) definitions ported to Go next to `internal/inbox`, with shared vectors, so the server never drifts from the app. Alternative: only add the fields and let models filter. Rejected: "what am I waiting for" and "what did I park" are two of the five Open Loops places and the issue's stated use; one filter and two views cost little.

**D5. Agent REST routes route the five fields to `update_tasks`.** `taskCreateFields` gains them; `agentPatchTaskCalls` sends `deadline`, `start`, `evening`, `blocked_by` and `location` to `update_tasks` with the other edit fields. The result is that the `docs/api.md` table becomes true as written, plus `location`. The 403 `insufficient_scope` list in that table shrinks accordingly. `ExtraOps` is extended so an agent write of `deadline` recomputes deadline-relative reminders exactly as a REST `deadline` write does (same function; today only `due` is wired).

**D6. CLI flags mirror the API words, resolve ids locally, and refuse early.** `--deadline` and `--start` reuse the `--due` word parser (`dates.go`) plus `someday` for `--start`; `--evening` is a Go bool flag (`--evening=false` clears on edit, the idiom flag users know); `--blocked-by` is a repeatable `stringList` resolved against `GET /api/v1/tasks` by id or unique prefix (the same lookup `ot edit <ref>` uses), ambiguous prefixes exit 1 listing candidates before any write; `--location` takes a saved location by name (case-insensitive, unique) or id, resolved through the places collection (`GET /api/v1/places`; assumption: saved locations are served by the generic collection route under that name, as the export's key list and the `place` entity suggest; if the collection has another path the task names it and nothing else changes), a `lat,lon` pair, or `none`. Edit semantics: `none` clears, `--blocked-by` replaces the list (one flag, no `--add-blocker`), as `--label` replaces. `ot list` gains `--someday`, `--anytime`, `--blocked` evaluated locally like `--inbox` (the CLI already filters on the client with the shared Inbox rule) and a `BY` column appearing only when a listed task has a deadline, as `ORIGIN` does, so existing table consumers see no new column by surprise. `--json` already returns the REST task, which carries the fields; `schema/task.json` is updated so `ot schema` describes them within output version 1 (additive). Alternative: a single `--when` flag with a mini grammar. Rejected: the quick-add grammar already exists for that (`--natural`), and separate flags are what scripts and agents can discover from `ot schema`.

**D7. The assistant learns the vocabulary in three places.** The fixed instructions gain one paragraph (do on = the day you plan to do it; deadline = must be done by, separate; start = do not show before; Someday = parked; evening = after the day's tasks; blocked_by = waits for; location = where). The skills change: plan-week sets `start` for work that begins later and never gives a do-on date just to keep a task visible; weekly-review maps the method's Waiting to `blocked_by` and Later to `start`; triage-inbox may park or defer. The review wording (`web/src/lib/assistant.ts` `describe`) gains cases for the five fields, with dates through the user's date format as `dueWords` does, blockers by title through `names.tasks`, and a location by its name, address or coordinates. The assistant stays off for encrypted accounts (in-app-assistant "Encrypted accounts"), so nothing changes there.

**D8. Encrypted accounts.** `location` is added to `create_tasks`' and `update_tasks`' `ContentFields`, so the existing machinery (`ciphertextOnly`, `plainContent`, `encryptionErr`) offers it as ciphertext only, accepts an envelope and refuses plaintext; the REST translator maps it to 409 `encryption_enabled` as for titles. Reads mirror `origin`: `IsCiphertextJSON` → `encrypted: true`, no members. `ot mcp --decrypt` decrypts and encrypts whole-object content the way it does `origin`'s sibling fields (mcp-projects, local decryption): a task name the bridge must know is `location`; the bridge's content field list comes from the shared vectors, so it is one entry.

**D9. The exclusion is project access state, inherited by sub-projects, hiding the project from assistant surfaces only.** A new table `project_agent_exclusions(project_id PRIMARY KEY, set_by, created_at)`; a row means kept away. It is never an op (like membership), never exported, and lives on the server because its meaning is "what the server lets assistants see", which a device cannot enforce. Who: the project's owner, or an admin of a shared project (the same people who may share it, project-sharing "Sharing in the client"). Scope of effect: the registry's snapshot loader drops excluded projects and their descendants before anything else looks at the data (projects, tasks, sections, field definitions, comments, attachments, time entries, counts, names), so every read, write, resource, prompt and the in-app loop inherit the behaviour with no per-tool code; the agent REST translator calls the same registry, so an excluded task is `not_found` there too; `move_tasks` into an excluded project is `not_found` for the project. Surfaces: every MCP call whatever the token scope (the MCP endpoint exists only for assistants; a `read` or `full` token pasted into one is still an assistant), the agent REST routes (reached only by `agent` tokens), the in-app assistant. Not: ordinary REST with a session, `full` or `admin` token, CalDAV, feeds, webhooks, public links, the export, sync. Alternative A: a per-member switch ("hide from my assistants"). Rejected: the point of the roadmap idea is that one member's assistant cannot see what the others want kept away, which only the people responsible for the project can decide; a per-member switch can be a later addition on the same table. Alternative B: filter in each tool. Rejected: one missed tool is a leak; filtering at the snapshot cannot be missed. Inheritance: a sub-project reads as kept away when any ancestor is; `inherited_from` names the nearest one; the child's own row, if any, is kept so that turning the parent off restores the child's own choice. The device relay (`mcp-device-relay`, planned) runs on the same registry and inherits the exclusion without further work.

**D10. Routes, payloads and the cached copy.** `GET`/`PUT /api/v1/projects/{id}/agent-access` registered with `signedIn.fullTokens()` (sessions, `full`, `admin`; `read` and `agent` get 403 `insufficient_scope` like `/api/v1/me/agent-access`), `PUT` additionally `.demoDenied()` with the matching `demo.go` entry. The membership rules of the project decide `forbidden`; a non-member is `not_found` like the members routes. `/api/v1/me` gains `agent_excluded_projects: [ids]` (every visible project kept away, inherited ones included) so the client caches it in a new Dexie table `agentExclusions` next to `memberships`, adopted on every sync, which is how the share dialog and the palette show the state offline and how the assistant panel knows to show its line. Audit: `project.agent_access` with `project_id`, `from`, `to` in the same transaction, actor the caller; the allow-list of details gains these three keys. Alternative: put the flag on the memberships list. Rejected: personal projects have no membership row.

**D11. Interface budget.** No new row of chrome, no new sidebar destination, no new default-visible task property, no new scroll region, no new shortcut: the switch is a row of the existing share dialog (a `Dialog`, already keyboard-reachable through the share shortcut), two palette commands registered without keys (the registry holds keyed shortcuts only, so nothing can conflict), and one line in the assistant panel where the view hint already is. The review list of the in-app assistant gains lines, not controls. The share dialog gets a story (`Screens/Share dialog`: owner, admin, editor, offline, inherited) with light, dark, 375 and 1280 px baselines, which it lacks today; the assistant review story gains a planning-change case.

**D12. Size.** No new dependency. Server: a few hundred lines of Go across the registry, the REST translator, the CLI and the routes; binary growth under 100 KB. Web: the review wording, the dialog row, the palette commands and the cache table; main bundle growth under 2 KB gzipped (measured in task 7.4). Runtime memory: the exclusion check is one small query per registry load, cached for the request; the blocked-graph read is the one per-batch read `ApplyStrict` already does.

**D13. Spec placement and open changes.** `mcp-server` "Write tools" and "Encrypted accounts and write tools" are modified by `mcp-projects` (archived before this change applies) and the latter also by `mcp-device-relay` (planned, not yet built); this change ADDS requirements ("Planning fields in write tools", "Planning fields in tool results", "Open Loops views and the blocked filter", "Location on encrypted accounts") rather than modifying those two, so the three changes archive in any order. `account-access` "Agent content routes" and `cli-client` "Add and edit tasks" are modified in full; no open change touches them. The exclusion is its own capability (`agent-project-exclusion`) so `project-sharing` and `mcp-server` keep their requirement texts. `task-locations`' requirements are reused, not modified; the location shape and E2EE rule are cited from them. `inbox-means-unplaced`'s `internal/inbox` is the model for the `someday` and `anytime` rules.

## Risks / Trade-offs

- [A model writes `start: "someday"` and expects the due date to go] → the tool description says what parking does and does not do; the review shows both lines; the docs say "write what you send" as for REST.
- [Cycle detection in the planner diverges from `ApplyStrict`] → both use the same graph reader and the same `checkBlockedBy` rule; a test applies every planned `blocked_by` change through `ApplyStrict` and asserts no refusal.
- [An excluded project leaks through a path that bypasses the snapshot] → the exclusion is applied in the one loader every tool uses; a test enumerates every tool and resource against an excluded project and asserts nothing from it appears, and the REST translator test does the same for every agent route.
- [Members are surprised that their own assistant lost a project] → the dialog row shows who set it (the audit event has the actor; the row says "kept away by <name>" from the membership list), and the assistant panel says so when the user looks at the project.
- [CLI `--location` by name is ambiguous] → unique match only, else exit 1 listing the candidates; ids always work.
- [`anytime` and `someday` rules drift from the app] → shared vectors, like the Inbox rule.

## Migration Plan

One additive migration creating `project_agent_exclusions`. No op-schema change, no new environment variable, no change to existing tokens or switches. Old clients ignore the new `/api/v1/me` key. Rollback: an older server ignores the table; agent REST routes go back to refusing the five fields (the documented behaviour of the old version). Upgrade note for the CHANGELOG: assistants can now set deadlines, start dates, Someday, This Evening, dependencies and locations; projects can be kept away from assistants.

## Open Questions

- Whether `inherited_from` should name the nearest or the top-most excluded ancestor when several are set (nearest proposed; it is the one a person would switch off first).
- Whether the demo instance should allow `PUT` on the agent-access route (denied proposed, with the other members and settings routes).
