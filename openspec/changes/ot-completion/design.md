# Design: ot-completion

## Context

`internal/cli/commands.go` holds `cmdSpecs`, the table that `ot help <command>` and `ot schema` print and that `TestSchemaCoversEveryCommandAndFlag` checks against each command's real flag set. The CLI is stdlib only.

## Decisions

### D1. The binary completes, the script only asks

There are two ways to generate completion from the table: (a) write the whole table into each shell's script as case statements, or (b) ship a small per-shell wrapper that calls `ot __complete -- <words>` and let Go answer from `cmdSpecs` at runtime (the approach of cobra, gh and kubectl).

We take (b). The logic (which command is being typed, which flags take values, positional argument kinds, enum values, dynamic names) is written once in Go and unit-tested there, instead of three times in three shell dialects. It cannot drift: an upgraded binary completes its own flags even with a script generated by an older one. Start-up of the static binary takes a few milliseconds; the network is touched only for dynamic values. The test that every schema command and flag is completable runs against the Go engine (`TestCompletionCoversSchema`).

### D2. Protocol of `ot __complete`

`ot __complete -- <word>… <current>`: the words after `ot`; the last is the word under the cursor, possibly empty. Output, always exit 0:

- first line: a directive, `:default` (use the candidates), `:file` (let the shell complete file names) or `:dir` (directories);
- then one candidate per line, `value<TAB>description` (the description may be empty). zsh and fish show descriptions; bash drops them.

`__complete` is hidden: not in `ot help`, not in `ot schema`, not in the dispatcher's command list; the dispatcher checks for it first. Any error, including an unreadable config file, yields `:default` and nothing else.

### D3. Dynamic values: no cache, 2-second limit, silent failure

Names are fetched on each Tab with one GET, under a 2-second deadline. We do not cache: a cache file would put project, label and task titles on disk outside the config file, go stale after renames and need invalidation, and one GET against a self-hosted server is fast enough. Without a profile, a token or a reachable server, completion offers nothing. Global `--profile`, `--server` and `--workspace` typed earlier on the line are honoured, like the `OPENTODO_*` variables.

| Where | Values |
|---|---|
| `--project`, project refs (`project rename/archive/rm/move`) | projects that are not deleted; archived ones only for `project archive` and `project rm` |
| `--label` | labels |
| `--workspace` | workspaces |
| `--profile` | profile names of the config file (no network) |
| task refs (`done`, `edit`, `rm`, `time start`, `time log`, `--task`, `--blocked-by`) | ids of open tasks, the title as description |
| `reopen` | ids of completed tasks |
| `#…` / `@…` in an `ot add` title | `#` + project name with spaces, `_` and `-` removed (how quick add matches), `@` + label names without whitespace |

Values come from every workspace of the account (narrowing to the line's workspace would cost another request per Tab). Values that are end-to-end ciphertext (`e2ee.IsCiphertext`) are skipped; completion does not decrypt. Task titles that are ciphertext leave the id without a description.

Candidates are filtered by the current word's prefix in Go: case-insensitively for names, case-sensitively for commands and flags.

Not completed: rule and issue-connection ids, token names (a credential route) and saved views (no CLI command or REST route reads them).

### D4. Quoting per shell

Go prints raw values. bash: the wrapper quotes each with `printf %q` (and strips an opening quote the user typed before asking). zsh: `compadd` quotes by itself. fish: `complete` quotes by itself. Descriptions are dropped for bash. A value containing a newline or tab is never offered.

### D5. Flags

Only the separate-word form (`--project Home`) is completed in bash, because bash splits `--project=Ho` at `=`. In zsh and fish `--project=Ho` completes to `--project=Home`. Flags already given are not offered again, except repeatable ones. After a literal `--` no flags are offered.

### D6. Release assets

The release job attaches bare `ot-<os>-<arch>` binaries, not archives, so there is nowhere natural to put completion files; the docs tell people to run `ot completion <shell>` once. Package managers can do the same at build time.

## Impact

- Data model: none. Server: none. Binary size: a few KB of Go and three embedded script templates. Memory: none at rest.
- No new dependency or environment variable.
