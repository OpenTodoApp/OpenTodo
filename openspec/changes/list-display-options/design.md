# Design: display options on project and label pages

## Context

Saved views store their grouping and order as view fields and show them in the display panel (`web/src/app/views/DisplayPanel.tsx`, OpenSpec `custom-views` "Display panel"). Project lists are grouped by section in manual order (`lib/listGroups`), label pages by project in manual order. Projects already keep a layout (List/Board/Timeline), collapsed sections, columns and "show completed" per device in the local `meta` table.

## Decisions

- **D1 Synced and personal, in rows that already are.** The choice syncs across the user's devices, as the issue asks for "persist across restarts" and as views do. It stays additive and simple because both targets already have a personal, synced row:
  - a project's options go in `project_prefs` (keyed by the project id, always the author's personal scope, also for a shared project): `group_by`, `sort_by`, `sort_dir`. On a shared project each member keeps their own grouping; writing them on the `project` row would have changed every member's view and needed an editor role.
  - a label's options go on the `label` row itself (`group_by`, `sort_by`, `sort_dir`): labels are personal entities, so the row is already per user.
  All six fields are plain strings (enumerations, like a view's `group_by`): `""` or an unknown value reads as the page's default and is never rewritten, so a newer value from a future client is additive. One op per field: a grouping set on one device and an order set on another both survive (per-field LWW). The fields go into `internal/sync/ops.go` Schema, the schema fixture, `web/src/lib/types.ts` and the row defaults in `ops.ts` (rule 3); none is user-written text, so nothing is added to the encrypted content fields. Per-device storage (as the project layout) was rejected: the issue wants the choice kept per project and label, and a phone and a laptop showing different groupings of the same project after an explicit choice reads as a sync bug.
- **D2 One panel, the parts that apply.** The display panel takes the choices it lists (`groupOptions`, `sortOptions`) and leaves out a part whose value it is not given (layout, completed tasks, row properties). Project and label pages pass grouping and order only: projects keep their own List/Board/Timeline switch and "Show completed tasks" (per device, unchanged), and row properties stay a view feature. The button sits with the header's actions (and in the phone bar's slots), so no row of chrome is added (interface budget: still at most 2 rows above the first task; no new task property; no new shortcut). The panel shows on a project in the List layout only; the board's columns stay its sections and the timeline its dates.
- **D3 Grouping and order apply to top-level tasks.** A project list stays a tree: the top-level tasks are ordered and grouped, and each brings its subtasks in their manual order, so a subtask is never shown away from its parent. Groups reuse the views' `groupTasks` headings and order (Earlier, Today, Tomorrow, dates, No date; Priority 1–4; labels in label order, No label) and the views' `compareTasks` order (undated tasks last for due date and deadline). On a list page a task is selected, dragged and opened by its id, so a task with several labels is listed once, under the first of them in label order (views list it under each). Choices: a project offers Section (default), None, Due date, Priority and Label (a project has no other projects inside it); a label offers Project (default), None, Due date and Priority (its own label would be the only group, and sections belong to one project each). Order: Manual order (default), Priority, Due date, Created, Deadline, Title, with the direction under More options. Later and Completed stay at the end of a project. With grouping by Section, sections keep their headers, collapse, add and drop behaviour; only the order inside them changes.
- **D4 A manual move switches to manual order.** Projects stay manually ordered (drag and Alt+arrows) whatever the display. A drop among rows, or a keyboard move, while another order (or manual descending) is shown first writes `sort_by = position, sort_dir = asc`, then applies the move as before, so the dropped task lands where it was dropped relative to its neighbours in manual order. Grouping is kept. Drops onto a section heading or a sidebar target are not reorders and leave the order alone. Label pages stay non-draggable lists, as before (manual order there is the tasks' stored order).
- **D5 Deadline order for views too.** The panel is shared, so saved views and the New view page also get "Deadline" in Order by. The view field already accepts any string on the sync path; the REST API's list of accepted `sort_by` values gains `deadline`, and an older client reads it as the default order.

## Data model impact

Additive only: `project_prefs.group_by|sort_by|sort_dir`, `label.group_by|sort_by|sort_dir` (strings), and the value `deadline` for `view.sort_by`. No migration (rows are materialized generically), no new route, no dependency; bundle size grows by a few hundred bytes.

## Risks

- An older client ignores the new fields and keeps showing sections in manual order; nothing breaks.
- Grouping by label shows a task under one label only; documented in the user docs.
