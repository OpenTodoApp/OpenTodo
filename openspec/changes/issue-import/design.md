# Design

## Context

See proposal.md for motivation and `specs/issue-connections/spec.md` for the behaviour. What exists and shapes the approach:

- **Calendar subscriptions are the template.** `internal/calfeed` has a per-user store (`calendar_subscriptions` with `etag`, `interval_seconds`, `next_fetch_at`, `last_error`, `stopped_reason`), a `Fetcher` built on `outbound.NewClient(dialer, 20s, FollowRedirects(3))` with the webhooks' `AllowPrivate` switch, a `Worker` with `Run`/`RunOnce`/`Refresh` run by `tenant.StartJobs` on a self-hosted server and by the host scheduler through `KindCalendars` and `Store.NextFetch`, routes in `internal/httpapi/calfeed.go` behind `feedsGate` and `signedIn.demoDenied()`, the hand-triggered limit `handFetchesPerHr = 12`, and `CalendarFeedsPanel.tsx` with a pure view and a loading wrapper. The owner switch is a settings key (`calendar_feeds.enabled`) read on every request.
- **Email to task is the template for server-written tasks.** `internal/email/process.go` builds ops with `ids.NameID` for the task and each op id (so a replay is a no-op), writes through `ApplyStrict` with device `server`, and `parse.go` cuts the body to the longest prefix whose JSON encoding fits `opsync.MaxValueBytes` and that an encrypted account's device could still re-encrypt (`maxEncryptableBytes`, unexported).
- **Secrets** live in `<data>/secrets/<name>.json` through `settings.SecretsFile` (0600 in a 0700 directory, excluded from backups, redacted in logs and JSON). Four features use one file each (`oidc`, `smtp`, `backup`, the assistant's keys). There is no per-user secrets mechanism yet.
- **The op log** accepts task fields from `Schema` in `internal/sync/ops.go`; `task-origin` adds `origin` (an object `{kind, provider, id, url, title}`) there, in `web/src/lib/types.ts` and in the defaults of `web/src/lib/ops.ts`, and decides how rows show it. This change writes that field and adds no field of its own.
- **Audit** is a closed catalogue (`internal/audit/events.go`) with an allow-list of detail keys; `settings.changed` carries `setting`, `from`, `to`.
- **Host mode** runs background work per kind from `computeDue` in `internal/host/scheduler.go`; per-tenant `config.Limits` (ops per hour, ops total, requests per minute, database size) are enforced in `ApplyStrict` through the quota's admit function, which reports refused ops per op.
- **Encrypted accounts.** The digest refuses to enable with 409 `encryption_enabled` (`internal/httpapi/digest.go`) and is turned off when encryption is enabled; email to task instead writes plaintext that the next unlocked device re-encrypts. Both patterns exist; this change must pick one.
- **Interface budget** (docs/interface-guide.md): a settings section is a card with rows; state as a badge beside the label; no header actions.

## Goals / Non-Goals

**Goals:**
- One new Go package, `internal/issues`, that owns the store, the two provider clients, the issue-to-ops mapping and the poller, so the HTTP, CLI, MCP and scheduler layers only call it.
- Idempotent polls: a crash, a retry or two processes cannot create a second task or re-apply a change.
- The user's edits win until the issue changes the same thing again; the poller never fights the user and never deletes.
- Every network request leaves through `internal/outbound` with the host checked, the token bound to that host and no redirect followed.
- Reuse: the fit helper from email, the webhook `AllowPrivate` switch, the calendar panel's structure, the project `Combobox`, `SettingsSection`/`SettingRow`/`Card`/`Badge`.

**Non-Goals:**
- A general "integration framework" for future providers: Jira will add a third client in the same package behind the same interface, nothing more generic is built now.
- Reading or showing issues that are not tasks, comments, milestones, assignees, due dates, estimates.
- Any write to the provider, any provider webhook, any OAuth flow.
- Per-user secrets encryption with a key the server does not hold; the token must be usable by the server, so it is as protected as the SMTP password and the assistant keys are today.

## Decisions

**D1. One package `internal/issues` with a `Provider` interface and two clients.** `Provider` has `Account(ctx) (login, canReadIssues, error)` and `List(ctx, query, cursor) (page, error)`, where `query` is the filter (assigned | repositories, labels) and `cursor` the stored `ETag` plus the updated-since time and the page number of a partial run. `github.go` uses `GET /issues?filter=assigned&state=all&since=…&per_page=100&page=n` for the `assigned` scope and `GET /repos/{owner}/{repo}/issues?assignee=<login>&state=all&since=…` per repository otherwise, with `Accept: application/vnd.github+json`, `Authorization: Bearer`, the API version header, and drops entries carrying `pull_request`. `gitlab.go` uses `GET /api/v4/issues?scope=assigned_to_me&state=all&updated_after=…&per_page=100&page=n` and `GET /api/v4/projects/{path-encoded}/issues?assignee_username=<login>…` with `PRIVATE-TOKEN`. The API address is derived from the host: `https://github.com` → `https://api.github.com`, any other GitHub host → `<host>/api/v3`, GitLab → `<host>/api/v4`. Each client normalises to one `Issue{Key, Title, Body, URL, State, ClosedAt, Labels, UpdatedAt}` with `Key` = `owner/repo#123` or `group/project#45`. Alternative: GraphQL on both providers (fewer requests for labels). Rejected: two query languages, no conditional requests on GraphQL, and REST pages of 100 are enough at the scale of one person's assigned issues.

**D2. Outbound client without redirects.** `outbound.NewClient(dialer, 20s)` with no `FollowRedirects` option, so Go's default redirect would run; the client sets `CheckRedirect` to return `http.ErrUseLastResponse` and the poll fails with `redirect_refused`. Reason: a redirect would carry the `Authorization` header to another host; calendars have no credential, issue polls do. The body is read through `io.LimitReader` at 2 MB plus one byte (`too_large`). The dialer is `&outbound.Dialer{AllowPrivate: hooks.AllowPrivate}`, as `calfeed.NewFetcher` does, so the owner's one toggle governs all three features (webhooks delta).

**D3. Tokens in one secrets file keyed by connection id.** `settings.NewSecretsFile(dataDir, "issues")`, entries `<connection-id>: <token>`, written with `Update` on create, replace and delete; the file never leaves the server (backups exclude `secrets/`, the export never reads it). A poll that finds no entry marks the connection `stopped: token_missing` (the restore case in the spec). On user deletion, `issue_connections` rows cascade and the poller's housekeeping removes entries with no row. Alternatives: a `token` column encrypted with a key in `secrets/` (adds a key-management story for the same trust level); plain column in SQLite (lands in every backup and database dump). Rejected both; the file is the existing mechanism and the design says plainly that it is protected by file permissions and exclusion from backups, not by encryption the server cannot undo.

**D4. Storage.** Migration `0039_issue_connections.sql`:
- `issue_connections(id, user_id → users ON DELETE CASCADE, provider, host, name, project_id, filter TEXT (JSON: scope, repositories[], labels[]), map_labels, enabled, interval_seconds, next_poll_at, last_poll_at, last_success_at, last_error, stopped_reason, etag, since_ms, page, account_login, created_at, updated_at)` with indexes on `user_id` and `next_poll_at`.
- `issue_links(connection_id → issue_connections ON DELETE CASCADE, issue_key, task_id, title, state, closed_at, labels TEXT (JSON of mapped label ids), issue_updated_ms, created_at, PRIMARY KEY (connection_id, issue_key))` with an index on `task_id`.
- A run's counts (`created, completed, reopened, renamed, unlinked, partial`) are stored as JSON in `last_run` on the connection; no run history table (the audit log is for security events, the card shows the last run, the CLI prints it).
Server data, never ops, like `calendar_subscriptions`.

**D5. Deterministic ids and "changed since last seen".** Task id `ids.NameID("issue-task", connectionID+"\x00"+issueKey)`; op ids `ids.NameID("issue-op", connectionID+"\x00"+issueKey+"\x00"+field+"\x00"+<issueUpdatedMs>)`, so re-applying the same issue version is a no-op in the log and a new version produces new ops. The link row records what the poller last saw (`title`, `state`, `closed_at`, `labels`). On each poll, for a linked issue: title op only if `issue.Title != link.title`; `completed_at` op only if the state flipped relative to `link.state` (closed → `completed_at = ClosedAt`, reopened → `completed_at = null`), and only when the task's current `completed_at` disagrees (read from the materialised row on the reader pool); labels op only if the issue's label set differs from `link.labels`, computed as (task's current labels − previously mapped) ∪ newly mapped; description never after creation. A task with `deleted_at` gets no op. Then the link row is updated in the same transaction as the ops are committed (`ApplyStrict` runs in the writer; the store wraps the link update in the same `*sql.Tx` through a small `ApplyWithTx` hook, or, if that is too invasive, writes the link after the apply and relies on the deterministic ids for the restart case in the spec, which it already covers). Alternative: always write the issue's current values. Rejected: it would overwrite the user's rename and completion on every change at the provider, which the spec forbids.

**D6. Timestamps.** Ops carry `TS` from the sync service's clock (`opsync.Service` already issues HLC timestamps for server writes, as email and CalDAV do), so a device edit made later wins by last-writer-wins and a device edit made earlier loses to the poll, exactly like a second device. `completed_at` carries the provider's close time as the value, not the poll time, so Statistics attributes the completion to the day the issue closed.

**D7. Notes and the fit helper.** The issue body is Markdown already (both providers store Markdown), so it goes into `description` as is; the email conversion from HTML is not used. The truncation moves from `internal/email/parse.go` into `internal/e2ee` as `e2ee.FitText(s string, note string) string` and `e2ee.MaxEncryptableBytes` (e2ee imports nothing from sync today, so the constant is passed in from `opsync.MaxValueBytes` by the callers; alternatively a tiny `internal/textfit` package if the import direction turns out awkward). Email keeps its behaviour and its tests; issues cut with the same note. Attachments of issues (images in the body) stay as Markdown links to the provider; nothing is downloaded.

**D8. Labels.** With `map_labels`, each issue label is matched against the user's labels by lower-cased name (materialised `labels` rows on the reader); a missing one is created with id `ids.NameID("issue-label", userID+"\x00"+lowerName)` and ops `name`, `color` (the palette hue derived from the name's hash, as the importer does), `created_at`, device `issues:<id>`. The link stores the mapped ids so a later change replaces only those. Alternative: one fixed label per connection ("GitHub"). Rejected as a default, but `origin` already tells the row where the task came from, so no marker label is needed.

**D9. Poller.** `issues.Worker{Store, Providers, Secrets, Sync, Enabled, Notify, Log}` with `Run(ctx)` (tick every 30 s like calendars), `RunOnce(ctx)` (connections with `next_poll_at <= now`, at most `InFlight = 2`), `Poll(ctx, conn) (*Run, error)` used by the routes for `sync` and by the CLI. A poll: load the token (missing → stop `token_missing`); check the host through the dialer (refused → stop `private_target`); list pages up to `MaxPages = 10`, conditional on the first page with the stored `ETag` (304 → advance `last_poll_at`, done); for each issue decide create/follow per D5; batch the ops per page through `ApplyStrict` (so a refused op stops the run with the limit's reason, and the link rows of applied ops are committed); `NotifyApplied` with the device so open devices refresh; store the `ETag` of the first page and `since_ms = max(issue.UpdatedAt)` of fully processed pages; more pages → `partial: true`, keep `page`, `next_poll_at = now + 1 min`. Failure: `interval = min(interval*2, 6h)`, `last_error`, `next_poll_at`; 401/403-without-reset → stop `unauthorized_provider`; 429 or 403 with `X-RateLimit-Reset`/`RateLimit-Reset`/`Retry-After` → `next_poll_at = reset`, `last_error = provider_rate_limited`, interval unchanged. Success resets the interval to the configured one. Host scheduler: `KindIssues = "issues"` in `computeDue` from `Store.NextPoll(ctx)` when the switch is on, `runDue` calls `RunOnce`.

**D10. Routes and policies.** In `internal/httpapi/issues.go`, registered from `router.go`:
- `GET /api/v1/settings/issues` `signedIn.demoDenied()`; `PUT` `ownerOnly("manage the issue connections setting").demoDenied()`, audit `settings.changed` `integrations.issues`.
- `GET /api/v1/issues/connections` `signedIn.demoDenied()`; `POST` `signedIn.recent().demoDenied()`; `PATCH /{id}` `signedIn.demoDenied()` but the handler requires a fresh session when the body carries `token` (one route, one policy; the handler answers `reauth_required` for that field, as the spec says); `DELETE /{id}`, `POST /{id}/test`, `POST /{id}/sync` `signedIn.demoDenied()`.
- Every write handler refuses `read` and `agent` tokens with `insufficient_scope` through the existing scope check; an `issuesGate` answers 404 while the switch is off, like `feedsGate`.
- `demo.go`: `{"Issue connections", false, prefix("/api/v1/issues")}` and `{"Issue connections", false, exact("/api/v1/settings/issues")}`; `policy_test.go` already checks the deny list against the policies.
- Hand-triggered `test` and `sync` share a per-user window of 12 per hour, the calendar feeds' `handFetchesPerHr` pattern.
Error codes reused: `invalid_input`, `private_target`, `limit_reached`, `rate_limited`, `not_found`, `forbidden`, `reauth_required`, `insufficient_scope`, `encryption_enabled`; new reason strings on the connection (not HTTP codes): `unauthorized_provider`, `token_missing`, `redirect_refused`, `too_large`, `provider_rate_limited`, `encrypted_account`.

**D11. Encrypted accounts: refuse, like the digest.** `POST` and `PATCH {enabled: true}` answer 409 `encryption_enabled` when `e2ee.Store.Enabled(user)`; the encryption-enable handler sets `stopped_reason = encrypted_account` on the user's connections and reports them in its response, as it disables the digest. Alternative: the email pattern (write plaintext, devices encrypt on sight, purge history). Rejected: email writes once per message the user chose to forward, while a poll writes titles and bodies for every change of every issue, forever, leaving a growing plaintext trail in the op log until the user purges; and the poller would have to compare titles it can no longer read. The spec states the degradation; `docs/e2ee.md` lists it under server-side integrations.

**D12. Audit.** New names `issue_connection.created|updated|deleted` with constructors taking `(userID, connectionID, provider)` and, for `updated`, the `setting` key; new allowed detail keys `connection_id` and `provider`; `setting` is reused. Polls write no audit events (the "Task edits are not events" rule).

**D13. Panel.** `web/src/app/IssuesPanel.tsx`: `IssuesView` (pure) plus `IssuesPanel` (loads, acts), mounted in the Integrations section after `CalendarFeedsPanel` inside the same `DemoDisabled`. Each connection is a `Card` whose first row is the state `Badge` (`Off`, `Up to date · 12 min ago`, `Polling`, `Failed`, `Stopped`) with the error or reason as the row's text, then provider and host with the account login, the project (name from Dexie, "Inbox" when none), the filter in words ("Assigned to you", "3 repositories, label bug"), the last run's counts, and a trailing `Menu` with Sync now, Test token, Edit, Disable/Enable, Delete (`ConfirmDialog`). Add/Edit is a `Dialog` with `Select` provider, `Input` host, `Input type=password` token (empty on edit, "Replace token" label), `Select` scope, a textarea-like `Input` list for repositories and labels (comma-separated, validated client-side to the counts), the project `Combobox` from `entity-pickers`, a `Switch` for labels and a `Select` interval (15 min, 30 min, 1 h, 6 h, 24 h). Status strings come from `server-error-codes.json` and the six catalogs. Offline: `useOnline()` false → cards from the last load (kept in `localData` like `cachedCalendarSubscriptions`), actions disabled, a `Notice`. Story `issuesSettings.stories.tsx` with states Off, Members, Healthy, Failed, Stopped (token missing), Encrypted, Offline.

**D14. CLI and MCP.** `internal/cli/cmd_issues.go`: `issues list` (`GET /api/v1/issues/connections`, table columns id, name, provider, host, state, last poll, tasks) and `issues sync [id]` (`POST …/{id}/sync` per connection, `Writes: true, DryRun: true`, output schema `issues_run`), added to `commands.go` so `ot schema` and help agree (`schema` test). `internal/mcp/resources.go`: `opentodo://integrations/issues` read from the store through the same list function the route uses, `enabled` from the switch, no provider call. The `ot` binary grows by the two commands only (about 20 KB).

## Data model

- New server tables `issue_connections` and `issue_links` (D4); server data, never in the op log, never exported.
- One secrets file `<data>/secrets/issues.json` (D3).
- Settings key `integrations.issues` (bool).
- Op log: no new field. Writes use `task.title`, `description`, `project_id`, `priority`, `labels`, `created_at`, `position`, `completed_at`, `origin` (from `task-origin`), and `label.name`, `color`, `created_at`. No field renamed or removed.

## Size and resources

- No dependency. The server binary grows by about 300 KB (two REST clients with their JSON types, the poller, the store, the handlers, the CLI command; comparable to `internal/calfeed` without its recurrence expansion), from about 28 MB. Container image: the same amount. The `ot` binary about +20 KB.
- Web bundle about +6 KB gzipped (the panel and dialog; every primitive is already in the bundle).
- Runtime: nothing while no connection exists. A poll holds one HTTP client and one page of up to 100 issues (bodies capped by the 2 MB body limit) and writes in batches per page; two polls at most in flight per process. Host mode opens a tenant only when a poll is due (multi-tenant-host delta).
- Database: one row per connection, one small row per linked issue.

## Interface budget

- Rows of chrome above a list's first item: unchanged (Settings layout, section list then the section card).
- Task properties visible by default: unchanged; `origin` presentation belongs to `task-origin`.
- Primary sidebar destinations: unchanged. The panel is a section inside Integrations.
- Vertical scroll regions: the settings content column (1 of 3); the Add/Edit dialog scrolls inside itself on phones.
- Shortcuts: none added. `g s` keeps opening Settings; the panel's actions are buttons and a menu, reachable with Tab and Enter.

## Risks / Trade-offs

- [GitHub's `/issues?filter=assigned` lists issues across every organisation the token can see, including private ones the user may not want here] → the `repositories` scope narrows it; the first poll's count is shown on the card before the user leaves the dialog ("Found 212 open issues; they will become tasks in Work") and the dialog offers to switch scope.
- [A first poll of a large backlog floods Today/Next and the op log] → tasks have no due date and priority 4, so they land in the project, not in Today; `MaxPages` bounds a run to 1,000 tasks and the hosted quota still applies; the card says "partial" until done.
- [Fine-grained tokens without `Issues: read` pass the account check but return empty lists] → `test` reports `canReadIssues` by listing one page with `per_page=1`; the card warns when it is false.
- [The provider changes an issue twice between polls] → only the latest state matters for title and state; `since`/`updated_after` is inclusive on both providers, so the cursor is `max(UpdatedAt) − 1 s` and the deterministic op ids make the overlap harmless.
- [Repository or project renamed at the provider] → `Key` changes with the new path and the old link no longer matches; the spec's "no longer matches" rule applies (the task stays, a new task is created for the renamed issue). Documented as a limit; a follow-up could key GitHub issues by their numeric `id`.
- [The token file is readable by anyone with the server's disk] → the same trust level as the SMTP password and assistant keys; documented plainly, and the panel recommends a fine-grained or project-scoped read-only token with an expiry.
- [Two processes polling during a rolling update] → host mode runs the scheduler in one process (multi-tenant-host); on a self-hosted server the jobs leader is one process; deterministic ids make a double run idempotent anyway.
- [Tenant deleted while a poll is in flight] → the poll's context is the tenant's; `ApplyStrict` fails on the closed database and the run is simply lost.
- [Six catalogs need every new string] → the strings are short status words and the dialog's labels; `make ui-check` and the i18n test fail on a missing key.

## Migration Plan

1. Ship the migration (idempotent `CREATE TABLE IF NOT EXISTS`), the package, the routes behind the owner switch (off), the panel, CLI and MCP in one release; nothing happens on any server until an owner turns the switch on.
2. Rolling back the binary leaves two unused tables and an unused secrets file; nothing else references them. Tasks already created are ordinary tasks and keep their `origin`.
3. Docs: `docs/issue-import.md` (set-up for both providers, which token scopes to grant, what follows and what does not, limits, the encryption refusal), one paragraph in `docs/e2ee.md`, the routes in `docs/api.md`, `ot issues` in `docs/cli.md`, the resource in `docs/mcp.md`, the demo deny list in `docs/self-hosting`, the audit events in `docs/api.md`'s audit section.

## Open Questions

- Whether `test` should also report the token's expiry date when the provider returns one (GitHub sends `github-authentication-token-expiration`); harmless to add later and shown only on the card.
- Whether a connection's first poll should offer to import issues closed in the last 30 days as completed tasks for Statistics; the spec says no for now and a later change can add a flag.

## Implementation notes

Recorded while applying the change; the specs state the behaviour, these say where the code differs from the plan above.

- **Migration number.** `0039_issue_connections.sql` was still free (the last migration was `0038_blocked_by_index.sql`). Besides the columns of D4 it has `backoff_seconds` (the current wait, so the configured interval stays as set), `last_error_at`, `repo_index` (the listing a partial run continues with, for the repositories scope), `reconciled_at`, and `etag` holds a JSON object with the first page's ETag of each listing (one per repository). `issue_links` has a `matched` flag for the "no longer matches" rule.
- **Fit helper.** Moved to `internal/e2ee/fit.go` as `e2ee.FitText(body, maxValue, compose)`, `e2ee.FitsValue` and `e2ee.MaxEncryptableBytes(maxValue)`; email passes its own composer (note plus attachment list) and its tests pass unchanged. Issues end a cut body with their own note, "[Issue text truncated: the rest did not fit in the task's notes]", since "Message truncated" would be wrong for an issue.
- **Origin.** `issues.Origin` builds the value with `origin.FromURL(url, key)` (which recognises github.com and gitlab.com addresses and cuts the title) and then sets kind `issue`, the connection's provider and the reference as `id`, so a self-hosted instance's issue is an issue origin too; `Validate` runs before the op is written.
- **Redirects.** `outbound.NewClient` already answers redirects with the 3xx response (no option given), so the client maps any 3xx other than 304 to `redirect_refused`; no request reaches the target (tested).
- **First poll and the cursor.** The first poll (no cursor yet) lists open issues only, so years of closed issues are neither downloaded nor counted against the 10 pages; later polls list `state=all` updated since the cursor (minus one second), oldest change first. The cursor moves only when a run completes; a partial run keeps the listing and page and is due again a minute later.
- **"No longer matches".** An issue the provider stops listing (unassigned) cannot be seen in an updated-since listing, so once a day a poll that has pages left also lists every open matching issue; a linked open issue missing from a complete listing is marked unmatched and counted as `unlinked`. Its task is never touched. An issue listed again later (reassigned) is followed again. An issue still listed but missing a filter label is marked at once.
- **Link written after the apply.** D5's alternative is used: the links of a page are written right after its `ApplyStrict`. A restart in between finds the task by its derived id and links it without writing (tested), and a re-applied version is a duplicate in the log.
- **Device prefix reserved.** `issues:` is added to `sync.ReservedDevice`, so `/api/v1/sync` refuses it from devices like `agent:` and `caldav:`; history labels such changes "issue import".
- **Token check.** The check makes two requests (the account, then a one-issue listing to learn `can_read_issues`, as the risks section planned); the spec's "one request" now says so. A refused token on a check stops the connection with `unauthorized_provider` like a poll, so the panel asks for a new token; a later passing check clears it.
- **Sync of a stopped, disabled or rate-limited connection.** Answers 409 `connection_stopped`, 409 `connection_disabled` (not named by the spec; a disabled connection is never polled) or 409 `provider_rate_limited` before the reset, all before the hourly limit is spent and without a request. A sixth connection answers 409 `limit_reached` as the spec says (calendar subscriptions use 400).
- **Audit in the transaction.** The store's transactions do not take the audit recorder, so events are recorded with `Recorder.Record` right after the change, as calendar feeds do. One `issue_connection.updated` event names every changed setting, comma-separated (`name,labels,interval`).
- **CLI exit code.** The cli-client delta said read-only mode exits 2; every write command exits 5 (`read_only`) under the main spec's exit code contract, so the delta now says 5. `issues_disabled` maps to exit 5 (a switch). A poll that runs and fails exits 1 with `poll_failed`.
- **MCP resource.** `mcp.Options.IssuesResource` is a callback the HTTP layer fills with the same list the route serves, so `internal/mcp` does not import `internal/issues`.
- **Host scheduler clock.** The tenant's `Options.Now` (the host's clock) is also the issue worker's clock, so the scheduler and the store agree on what is due.
- **Settings copy.** The Issues card, its two rows and two notices are in `SETTINGS_COPY.issues` with Learn more to `settings/issues` (the guide `docs/issue-import.md`). The private-network row of Webhooks now reads "Webhooks, calendar subscriptions and issue connections on your LAN. Off on public servers." (the webhooks delta). The guide is in the Integrations section, so the guide-page rules (screenshot first, under 600 words) do not apply, and its `specs` names `webhooks` and `end-to-end-encryption` until this change is archived, when it should name `issue-connections`.
- **Connection reasons in the web app.** The stored reasons are not HTTP error codes, so they are worded in `reasonText()` in `web/src/app/IssuesPanel.tsx` rather than in `server-error-codes.json`; the four new HTTP codes (`issues_disabled`, `connection_stopped`, `connection_disabled`, `provider_rate_limited`) are in the fixture and in `errors.ts`.
- **Keyboard.** Sync now is a button on each card (Tab, then Enter); the other actions are in the card's menu. The happy-dom test focuses the button and clicks it, since happy-dom does not turn Enter into a click.
- **Sizes measured.** Server binary (`-s -w`, same embedded web build) 28,782,752 → 28,991,648 bytes, +204 KB. Web build, gzipped: main chunk +3.6 KB, each translation catalog +2.3 KB, the help bundle +3.1 KB (the new guide).
- **Not regenerated.** UI baselines for the seven `Settings/Integrations/Issues` stories need the Docker-based `make ui-baselines`; the stories were built and rendered once in the bundled Chromium instead (no errors), and baselines come from CI's ui-check-report artefact. No docs screenshot shows this panel, so none went stale.
