# Design

## Context

See proposal.md for the motivation. The pieces this change builds on, as the code stands with `rule-boards` applied:

- A column's rule is `view.on_drop`, a whole-value field of kind `kRule` checked by `internal/sync/rule.go` (`ParseRule`: closed key set, enumerations, at most 32 ids per list) and resolved by REST in `checkView`; the client plans it with `planRule` in `web/src/lib/rules.ts`, which reuses the bulk planners (`planLabels`, `planPriority`, `planDue`, `planComplete`, `planReopen`, `planProjectChange`) so a drop behaves like the single-task actions; the editor is `web/src/app/RuleEditor.tsx`.
- Server-side writers already exist and set the pattern: the issue poller (`internal/issues`, a worker on the jobs leader with `PollInterval`, in-flight slots and per-connection locks, writing through `ApplyStrict` with device `issues:<id>`), the digest scheduler (`internal/digest`, a pass every `TickInterval`, "next due" computed from settings and a stored watermark), the reminder scheduler (`internal/push`, `dueReminders` scans instants that passed since the last pass, the user's zone taken from the offset their devices last reported), and the webhook observer (`internal/webhook`, `sync.Observer` → durable queue rows → one worker). `tenant.StartJobs` starts each under `spawn`, nothing on a demo instance for the outbound ones.
- `sync.Service.SetObserver` accepts one post-commit observer; the tenant wraps the webhook observer and others in one function (`tenant.go` line 247). `sync.Change` carries the author, the scope, the entity, the winning field changes and the origin device. `ApplyResult.Seq` is the op cursor after a batch.
- Materialised rows are read through `sync.Service.List(ctx, userID, entity, includeDeleted)` on the reader pool (as `agenttools.load` does); the server's completion of recurring tasks lives in `internal/sync/recurring.go` and is used by REST and the agent tools, with `StampCompletedBy` on `ApplyStrict`.
- Notifications are server events handed to sinks (`internal/notify`: `Sink`, `MentionSink`, `UnblockedSink`; the in-app sink stores rows for `/api/v1/notifications`). The activity derivation (`internal/activity`, `web/src/lib/activity.ts`) and the history route's `device_label` already special-case `public:`, `agent:` and `assistant:` devices.
- Agent write limits (`internal/agenttools/limits.go`: 50 per call, 30 calls per minute, 1,000 entities per day, in-memory ring) are the precedent for fixed, documented bounds.
- The Inbox rule (`internal/inbox` and `web/src/lib/inbox.ts`) and the time-tracking rules are pinned by shared vector files; the condition matcher follows that pattern.
- Interface budget (docs/interface-guide.md): two rows of chrome above a list's first item, seven task properties, six primary sidebar destinations, three scroll regions, every keyed shortcut registered without conflict; rule 9: every core screen has a story with baselines.
- `quiet-sidebar` and `sidebar-favourites` modify app-shell "Sidebar structure"; `rule-boards` modifies custom-views "Dashboards" and adds "On-drop rule"; several open changes modify end-to-end-encryption "Encrypted and plaintext fields". This change adds requirements beside them instead of modifying them (D12).

## Goals / Non-Goals

**Goals:**
- One rule model for drops and automations: the same action keys, the same planner, the same editor controls, so what a drop does and what a rule does never drift apart.
- Rules work for every account the same way, encrypted ones included, because conditions and actions are structural.
- Mistakes stay small and visible: idempotent runs, no self-firing, a chain limit, fixed rate limits, automatic pause, a run log, undo from history.
- No new dependency, no new mandatory variable, one additive entity.

**Non-Goals:**
- A server-side evaluator for the filter query grammar (D3 explains why conditions are structured instead).
- Rules on shared projects or acting as anyone but their author (D2).
- Creating tasks, sending mail, calling a model, or any outbound request beyond the user's own webhooks.
- Changing the drop behaviour of `rule-boards` or the filter grammar.

## Decisions

**D1. One entity, three whole-value fields.** `rule` joins `Schema` with `name` (`kString`, content), `enabled` (`kBool`), `trigger` (`kRuleTrigger`), `condition` (`kRuleCondition`, nullable), `actions` (`kRuleActions`), `position` (`kNumber`), `created_at`, `deleted_at`. Like a label or a place it resolves to the author's personal scope and never reaches other members. Each structured field is one register: a trigger or an action set is a few choices made together, and whole-value LWW (the `on_drop` precedent, D2 of rule-boards) is simpler to reason about than a map of registers. Alternative: separate fields per action key (`action_priority`, `action_due`, …). Rejected: the key set would be frozen into field names, and a concurrent "set priority" and "clear priority" could interleave into a rule nobody wrote. Alternative: store rules in a server table, not the op log. Rejected: rules are the user's data (they belong in the export, in backups and on every device, and the editor must work offline); only the engine's bookkeeping (queue, watermarks, runs, pauses) is server state.

**D2. Personal scope, acting as the author, personal projects only.** A rule fires only for its author's batches and acts only on tasks its author can edit. The project action refuses a shared project at save time (REST and the editor; sync accepts the shape and the engine refuses at run time with "skipped: shared project"), because moving a task into another scope is the copy-and-tombstone path (`ReasonScopeChange`) that the client performs, and a server-side copy would need the client's attachment and comment handling. Tasks in shared projects are still subject to a user's rules when the user's own batch triggers them (the user completes a shared task → their `task.completed` rule may add a label), which the sharing roles already bound. Alternative: rules on a shared project, editable by admins, acting as a system author. Rejected for this version: there is no system author in the op log, every op has a human author and history reads "Rule (…)" with that author; and two members' rules on one project would need a precedence rule. Recorded as a follow-up.

**D3. Structured conditions, not query text.** The filter grammar resolves `#Work` and `@errand` by name, matches `search:` on titles and compares custom field values; names, titles and text values are ciphertext for an encrypted account, so a server-side evaluator of the grammar would work for some accounts and silently not for others, and it would be a second evaluator of a grammar whose semantics (`this week`, week start, `completed` ranges, quoted names) are owned by the client. A condition is instead a closed set of predicates over ids and plaintext scheduling fields (spec "Conditions"), evaluated by `internal/rules/match.go` and `web/src/lib/rules/match.ts` and pinned by `web/src/lib/rules/match.vectors.json` (the inbox pattern). The editor builds predicates with the same pickers as the rule editor, and "Convert to a rule" compiles the structural subset of a query from the client parser's syntax tree, naming what it drops (custom-views delta). The server validates ids on REST the way `checkView` does; sync checks shape and bounds only. Alternative: accept a query string and have the server reject unsupported terms at save time. Rejected: still two evaluators of one grammar, and a condition saved today could stop evaluating when a later change adds a term.

**D4. Actions are a superset of `on_drop`, planned by one planner.** `kRuleActions` accepts every `on_drop` key with the same values, plus `due: {in_days}`, `deadline`, `assignee`, `comment`, `notify`, `webhook`. `ParseRule` is generalised to take a key set, so `on_drop` keeps its closed set (views are not extended) and `actions` has its own; `rule.go` holds both. On the client, `planRule` takes the extended type and is used by drops and by the editor's dry-run preview; on the server, `internal/rules/plan.go` plans the same field changes from materialised rows in the same order (spec "Actions"), reusing `internal/sync/recurring.go` for completion, the reminder recomputation the REST `PATCH` already performs on a due change, and `StampCompletedBy`. Both planners run the same fixture (`internal/rules/testdata/plan_fixture.json`: task row + actions → expected patches), so a drop on the device and a rule on the server write the same ops. Alternative: run rules through the agent tool registry's planners. Rejected: the registry is gated on tokens, limits and audit built for agents, and its change sets are shaped for review by a person; a thin planner over the sync rows is smaller and shares the fixture with the client.

**D5. Engine shape: observer → queue → worker; scheduler → same worker.** `internal/rules`:
- `Observe(ctx, changes)` (installed in the tenant's combined observer, after the webhook one) derives candidate events only when the batch author has at least one enabled rule of a matching kind (a per-tenant cache of rule kinds per user, invalidated by rule ops) and inserts rows into `rule_events(id, user_id, seq, task_id, kind, label_id, project_id, section_id, origin, depth, created_at)`. Batches with origin `import` and the engine's own `rule:<id>` devices are tagged with their depth (D7); everything else is depth 1.
- `Worker.Run` processes `rule_events` in `(user_id, seq)` order, one user at a time (a per-user lock as the issue worker has per connection), loading the user's enabled rules and the task row through the reader, evaluating trigger and condition, planning, and writing through `ApplyStrict` with device `rule:<rule-id>`, then `NotifyApplied`.
- `Scheduler.Tick` runs every minute on the jobs leader (the digest's pass pattern, `TickInterval = 1 min`): for every enabled `schedule` rule it computes the occurrences since the rule's watermark in the user's zone and enqueues one `schedule` event per occurrence; for `due.reached` and `overdue` rules it scans the author's open tasks whose due instant (09:00 local for date-only, the zoned instant otherwise) or overdue instant (day start of the day after the due date) falls in `(watermark, now]`, like `push.dueReminders`, and enqueues one event per task with the occurrence in its key. Watermarks live in `rule_state(rule_id, watermark_ms, paused_reason, refusals)`; a new or re-enabled rule starts its watermark at now, so enabling a rule never fires for the past.
- The user's zone is `sync.Service`'s last reported device offset (the reminders convention), UTC until a device reported one; day start is `user_prefs.day_start`.
One worker and one scheduler per tenant; the host's shared scheduler calls `Tick` per open tenant as it does for the digest. Alternative: evaluate event triggers synchronously inside the observer. Rejected: the observer runs on the writer's goroutine after commit and must stay quick; a queue also gives idempotency and restart safety for free.

**D6. Idempotency, keys and the run log.** `rule_runs(rule_id, occurrence_key, task_id, at, outcome, reason, changes_json, depth)` with a unique index on `(rule_id, occurrence_key)`; the key is `evt:<seq>:<task_id>` for event triggers, `due:<task_id>:<instant>` for `due.reached`, `overdue:<task_id>:<due date>` for `overdue`, `sched:<minute>` plus `:<task_id>` per task for schedules. The worker inserts the run row (outcome `pending`) in the same transaction that marks the event taken, writes the batch, then updates the outcome; a crash between the two leaves a `pending` run that the next pass finishes by checking whether a batch with device `rule:<id>` and that key's seq exists (the op log is the truth) or re-plans. Titles are never stored (the client resolves task ids from local data; a deleted task shows by id). Pruning: 100 per rule and 30 days, on the hourly prune tick the audit pruner already runs.

**D7. Loops.** Each batch the engine writes is recorded with its depth in `rule_batches(seq, rule_id, depth)` (pruned with the events); the observer looks up the origin seq of a `rule:` batch to set the event's depth to `parent + 1`, and the worker refuses depth ≥ 4 with outcome `stopped`. A rule never fires on a batch whose device is its own id. Alternative: forbid chaining altogether. Rejected: "label x added → section Waiting" followed by "moved to Waiting → priority 3" is a reasonable pair; three links is enough for that and stops any cycle quickly.

**D8. Limits and pauses.** Fixed constants in `internal/rules/limits.go`, documented in `docs/automations.md`: `PerMinute = 60` runs that apply changes per account, `PerDay = 2000` (UTC), `PerRun = 500` tasks, `MaxRules = 50`, `MaxChainDepth = 3`. Counters are in memory per tenant (the agent limiter pattern; a restart resets them, they exist to contain mistakes, not to bill). A rule refused by the per-minute limit three times within an hour is paused: `rule_state.paused_reason = "runaway"`, a `RulePaused` notification through the new `notify.RuleSink`, the Rules page shows the reason and the switch; turning the rule on clears the pause (the `enabled` op is observed; a `PATCH` with `enabled: true` also clears it). The pause is server state, not an op, because it is the server's judgement, not the user's edit.

**D9. Switches.** Owner setting `automations.enabled` (default true) in `internal/settings`, the optional `OPENTODO_AUTOMATIONS=on|off` override validated at startup (the maps pattern: an invalid value exits naming the variable, a set variable makes the setting read-only and `PUT` answers 409 `set_by_environment`). Per-user "pause all" is a row in `rule_state` keyed by user (`user_rules_paused`) set through `PUT /api/v1/me/rules/paused`; the profile exposes `automations: {enabled, paused}` so the Rules page can say what is on. Demo: nothing is wired (`StartJobs` skips the engine like the outbound jobs) and the routes carry `.demoDenied()` plus the "Automations" deny-list entry.

**D10. Routes.** `internal/httpapi/rules.go`: the generic collection handlers for `rule` with a `checkRule` (the `checkView` pattern: shape through `rules.ParseTrigger/ParseCondition/ParseActions`, then ids resolved against the user's live labels, projects, sections and webhooks; the project action refuses a shared project; the comment action refuses an encrypted account with 409 `encryption_enabled`), `GET /api/v1/rules/{id}/runs` (newest first, 100), `POST /api/v1/rules/{id}/test` (the matcher and the planner on one task, nothing written), `PUT /api/v1/me/rules/paused`, `GET|PUT /api/v1/settings/automations` (`ownerOnly`). Policies: `signedIn` for the user routes (so `read` tokens read, `agent` tokens are refused on writes by the existing scope rules), `.demoDenied()` throughout.

**D11. Client.** `web/src/lib/rules/` gains `match.ts` (+ vectors), `summary.ts` (the one-line wording, reusing `describeRule` for the action half), `convert.ts` (query → condition from the parser's tree), and `planRule` moves there from `lib/rules.ts` with the extended keys; `lib/views.ts` keeps `setOnDrop`. A Dexie table `rules` (indexed by `id, position`), `RULE_DEFAULTS` in `ops.ts`, `createRule`, `updateRule`, `reorderRule`, `deleteRule` as ordinary `mutate` calls. The Rules page (`web/src/app/rules/RulesView.tsx`, route `/rules`, `PageBody width="list"`), the editor (`RuleDialog.tsx`, built from `RuleEditor.tsx`'s controls plus a trigger section and condition rows), and the history panel (`RuleHistoryPanel.tsx` through `openPanel`) are one lazy chunk. The More group entry "Rules" sits after "Locations"; the palette commands "Go to Rules" and "New rule" have no keys.

**D12. Spec placement.** New requirements are added beside, not inside, requirements other open changes touch: the More entry is stated in `automation-rules` (not in app-shell "Sidebar structure", which `quiet-sidebar` and `sidebar-favourites` modify); "Convert a column rule" is an added custom-views requirement (rule-boards modifies "Dashboards"); encryption behaviour is an added end-to-end-encryption requirement; the demo refusal is stated in `automation-rules` "Switches" rather than in demo-mode's deny-list requirement. When those changes archive, a follow-up edit lists Rules in the More column of "Sidebar structure" (task 7.5).

## Data model

- Server `Schema["rule"]` as in D1; three kinds `kRuleTrigger`, `kRuleCondition`, `kRuleActions` checked in `internal/rules/values.go` (called from `internal/sync/kinds.go`). No migration for the entity (rows are materialised generically from the op log, as `task-locations` found); one additive migration `NNNN_rules_engine.sql` for `rule_events`, `rule_runs`, `rule_state` and `rule_batches`.
- Content fields: `rule.name`, and the `comment.text` member of `rule.actions` is content but lives inside a structural value; the client encrypts it by refusing to write it on an encrypted account (spec "Rules for encrypted accounts"), so `internal/e2ee.ContentFields["rule"] = ["name"]` and `CONTENT_FIELDS` match. No op field is renamed or removed.
- Client `Rule` type, `RULE_DEFAULTS`, Dexie `rules` table; `RULE_FIELDS` for the export and import; `rules` in the export document and the own-format import's id re-mapping (labels, projects, sections, webhook ids are not re-mapped: a webhook action whose id is unknown after import is kept and skipped at run time).
- Server state (not ops): `rule_events`, `rule_runs`, `rule_state`, `rule_batches`, `user_rules_paused` (a column of `rule_state`'s user row), `automations.enabled` in settings. Backups include them as part of the database; restoring an older backup may replay nothing (watermarks move to now on first tick after restore, D5).

## Size and resources

No dependency. Go binary about +300 KB: the value kinds and matcher (~60 KB), the planner (~40 KB), the queue, worker and scheduler (~120 KB), routes and CLI (~80 KB). Web: the matcher, summary wording, types and the More entry in the main bundle (~4 KB gzipped); the Rules page, editor and history as a lazy chunk (~10 KB gzipped, the editor reuses `RuleEditor`'s controls). Server memory: one goroutine for the worker and the scheduler's tick per open tenant, in-memory counters per account (bounded like the agent limiter), the rule-kind cache per user (a few bytes per user). Database growth: one row per candidate event until processed (processed rows deleted), at most 100 runs per rule, batches pruned with their runs. A scheduler tick over a tenant with no time-triggered rules is one indexed query.

## Interface budget

- **Rules page**: page header (title, New rule, overflow) is the one row of chrome; rows are a list pattern, not task rows; one scroller (the content column). No new primary sidebar destination: Rules is in More in every mode.
- **Rule editor**: a dialog with its own scroller, as every dialog; the live count is one line under the condition rows. Nothing is added to task rows or the panel.
- **Run history**: the panel slot (`openPanel`), the third column's scroller.
- **Board Arrange**: "Make an automation rule" is a button inside the existing Rule dialog, no new row.
- **Shortcuts**: none keyed; "Go to Rules" and "New rule" are palette commands, so the registry's conflict test is unchanged.
- **Stories**: `Screens/Rules` (List, Empty, Paused, Offline), `Rule editor` (Trigger, Condition rows, Encrypted), `Rule history`, in light and dark at 375 and 1280 px, with the axe gate.

## Risks / Trade-offs

- [A rule that completes or moves many tasks is destructive at scale] → `PerRun = 500`, the per-minute limit, every batch undoable from history per task, the dry-run route, and the editor's live count before saving.
- [Server and device planners drift] → one fixture runs on both sides (D4); a planner change without a fixture change fails CI.
- [Two evaluators of conditions drift] → shared vectors (D3), the same discipline as the Inbox rule.
- [Clock and zone surprises (DST, a device in another zone)] → the reminders convention (last reported offset) is reused rather than a new one; occurrences are computed in that zone and keyed by local minute so a DST repeat fires once.
- [A paused rule surprises the user] → one notification, the reason on the page, and the switch resumes it.
- [Host mode: one tenant's rules hog the shared scheduler] → the per-tenant worker takes one event at a time with the same in-flight bound as the issue poller; the host's per-tenant limits apply to the routes.
- [Event rows pile up while the owner has automations off] → the observer queues nothing while off (D9), so turning it on starts fresh.
- [Older clients meet the `rule` entity] → entities a client does not know are ignored by `applyOps` (the view `on_drop` precedent), and the server is upgraded first.

## Migration Plan

Additive. Deploy the server (the migration creates the engine tables; the schema accepts `rule` ops; the engine starts with no rules). Clients ship in the same binary. Rollback: an older binary ignores the engine tables and refuses new `rule` ops; existing rule rows stay in the field store unused. Upgrade note in CHANGELOG: automations are on by default; `OPENTODO_AUTOMATIONS=off` disables them server-wide.

## Open Questions

- The exact fixed bounds (60 per minute, 2,000 per day, 500 per run, 50 rules) can be tuned after a release of real use without changing the specs' shape, only their numbers.
- Whether the Rules page should also list each rule's "next scheduled run" (cheap to compute on the device from the trigger and the zone) is a presentation choice for the implementer.
