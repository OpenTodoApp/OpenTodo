# webhooks Specification

## Purpose
Defines outbound webhooks: how a user registers endpoints for task and project events, how events are derived from the operation log and delivered with signatures and retries, what the delivery log shows, and how the server protects itself and the local network from being used as a request proxy.

## Requirements

### Requirement: Webhook management
A signed-in user SHALL create, list, update, enable or disable and delete their own webhooks through Settings and `GET`/`POST /api/v1/webhooks`, `GET`/`PATCH`/`DELETE /api/v1/webhooks/{id}`. A webhook SHALL have a target URL, a non-empty set of subscribed events, an optional project filter, an enabled flag and a secret generated by the server and shown exactly once. A user SHALL have at most 20 webhooks. No webhook exists until a user creates one, so by default the server sends nothing.

#### Scenario: Create a webhook
- **WHEN** a user POSTs a valid URL and the events `task.completed` and `task.created`
- **THEN** the response is 201 with the webhook, including its secret, and later reads omit the secret

#### Scenario: Routes require authentication
- **WHEN** any `/api/v1/webhooks` route is requested without credentials
- **THEN** the response is a 401 `unauthorized` error

#### Scenario: Invalid webhook
- **WHEN** a user submits a URL with a scheme other than `http` or `https`, an unknown event name, or an empty event list
- **THEN** the response is a 400 `invalid_input` error naming the field and nothing is stored

#### Scenario: Another user's webhook
- **WHEN** a user requests a webhook id that belongs to a different account
- **THEN** the response is a 404 `not_found` error

### Requirement: Events derived from operations
The server SHALL derive events from operations as they are applied, except those written by an import or its undo, coalescing one entity's operations within a batch into one event named `task.created|updated|completed|reopened|deleted` or `project.created|updated|archived|deleted`. Operations that lose under last-writer-wins SHALL produce no event. Edits made offline SHALL produce events when the device syncs them.

#### Scenario: Completion from an offline device
- **WHEN** a user completes a task on a device without network and the device syncs an hour later
- **THEN** one `task.completed` event is emitted at sync time for webhooks subscribed to it

#### Scenario: Stale operation produces no event
- **WHEN** a device syncs a title change that is older than the title already stored
- **THEN** no `task.updated` event is emitted

#### Scenario: Project filter
- **WHEN** a webhook is limited to project P and a task in project Q is created
- **THEN** no delivery is queued for that webhook

#### Scenario: Import writes produce no per-task events
- **WHEN** an import creates 500 tasks for a user whose webhook subscribes to `task.created`
- **THEN** no `task.created` delivery is queued for those tasks

### Requirement: Payload and signature
Each delivery SHALL be an HTTPS or HTTP POST with a JSON body containing a unique delivery id, the event name, the event time, the entity's current state and the list of changed fields with their previous values when known, and SHALL carry headers for the event name, the delivery id, the webhook id, a timestamp and a signature `v1=<hex HMAC-SHA256 of "<timestamp>.<body>">` computed with the webhook's secret. The payload format SHALL be versioned and documented. A task's `origin` SHALL travel in the entity state and in `changes` like every other field, as the ciphertext string for an encrypted account.

#### Scenario: Receiver verifies a delivery
- **WHEN** a receiver recomputes the HMAC over the timestamp header and the raw body with the shared secret
- **THEN** it equals the signature header, and a delivery whose timestamp is older than the receiver's tolerance can be rejected as a replay

#### Scenario: Payload content
- **WHEN** a task's priority changes from 4 to 1 through the API
- **THEN** the `task.updated` body contains the full task with priority 1 and `changes: {"priority": {"from": 4, "to": 1}}`

#### Scenario: Captured task delivered
- **WHEN** a task is created from a shared issue page and the device syncs
- **THEN** the `task.created` body's task carries `origin: {kind: "issue", provider: "github", id: "o/r#7", url: "…"}` and `changes.origin` reads `{"from": null, "to": {…}}`, so a receiver can link the task back to the issue without a second request

### Requirement: Delivery and retries
Deliveries SHALL be queued durably so that a restart loses none, SHALL time out after 10 seconds, SHALL treat any 2xx response as success, and SHALL otherwise retry with exponential backoff and jitter up to 6 attempts over roughly one day. Delivery is at least once and order is not guaranteed; receivers SHALL use the delivery id to de-duplicate. After 20 consecutive failed deliveries a webhook SHALL be disabled automatically with a visible reason.

#### Scenario: Receiver temporarily down
- **WHEN** a receiver answers 503 on the first attempt and 200 on the second
- **THEN** the delivery is marked delivered after the second attempt and the log shows both attempts

#### Scenario: Server restarts mid-queue
- **WHEN** the server stops with pending deliveries and starts again
- **THEN** the pending deliveries are attempted after startup

#### Scenario: Automatic disable
- **WHEN** 20 consecutive deliveries to a webhook fail after all retries
- **THEN** the webhook is disabled, its status shows the reason, and no further deliveries are queued until the user enables it again

### Requirement: Delivery log, test and redelivery
`GET /api/v1/webhooks/{id}/deliveries` SHALL list the most recent 100 deliveries with event, status, attempts, response status code, duration and the first kilobyte of the response body; `POST /api/v1/webhooks/{id}/test` SHALL send a `ping` event immediately and return its result; `POST /api/v1/webhooks/{id}/deliveries/{did}/redeliver` SHALL queue the same payload again with a new delivery id. Log entries older than 30 days SHALL be pruned.

#### Scenario: Test ping
- **WHEN** a user triggers a test on a webhook whose receiver answers 200
- **THEN** the response reports success with the status code and duration, and the delivery appears in the log

#### Scenario: Redeliver a failed delivery
- **WHEN** a user redelivers a failed delivery
- **THEN** a new delivery with the same body and a new id is sent and logged

#### Scenario: Unknown delivery
- **WHEN** a redelivery is requested for a delivery id that does not belong to the webhook
- **THEN** the response is a 404 `not_found` error

### Requirement: Private network protection
The server SHALL refuse webhook targets, at creation and again at every delivery after resolving the host name, whose address is loopback, link-local, unique-local or private, multicast, unspecified, or a cloud metadata address, unless the owner enabled "allow private network targets" in Settings or through the optional `OPENTODO_WEBHOOKS_ALLOW_PRIVATE=true` preset. Connections SHALL be made to the address that was checked, and redirects SHALL not be followed.

#### Scenario: Private target refused by default
- **WHEN** a user creates a webhook pointing at `http://192.168.1.10:8123/...` and the owner has not allowed private targets
- **THEN** the response is a 400 `private_target` error explaining the owner setting

#### Scenario: Owner allows the local network
- **WHEN** the owner enables private targets and the same webhook is created
- **THEN** it is accepted and deliveries reach the LAN receiver

#### Scenario: Host name changes to a private address later
- **WHEN** a public host name of an existing webhook starts resolving to a private address and private targets are not allowed
- **THEN** the delivery is marked failed with reason `private_target` and no connection is made

#### Scenario: Member cannot change the policy
- **WHEN** a member calls `PUT /api/v1/settings/webhooks`
- **THEN** the response is a 403 `forbidden` error

### Requirement: Webhooks screen
Settings SHALL list the user's webhooks with status, let them create one (showing the secret once with a copy action), edit events and filter, enable or disable, test, open the delivery log and redeliver, all reachable with the keyboard. The owner SHALL additionally see the private-network policy toggle. Because delivery happens on the server, the screen SHALL show the last fetched state while offline and disable actions until the connection returns.

#### Scenario: Secret shown once
- **WHEN** a user creates a webhook in Settings
- **THEN** the secret is displayed with a copy action and is not retrievable after the dialog closes

#### Scenario: Offline
- **WHEN** the Webhooks section is opened without a connection
- **THEN** the previously loaded list is visible, actions are disabled and the screen says a connection is required

### Requirement: Import summary events
A finished import job SHALL produce one `import.completed` event and an undo one `import.undone`, delivered at most once per subscribed webhook with the job id, status, counts and touched project ids. Members of a touched shared project SHALL receive it with only their shared projects; a project filter SHALL match when its project is listed. Delivery, signing, retries and private network protection SHALL be as for other events.

#### Scenario: Large import
- **WHEN** a user imports 20,000 tasks and has one webhook subscribed to `import.completed`
- **THEN** exactly one delivery is queued for that webhook, carrying the counts and project ids

#### Scenario: Undo
- **WHEN** the user undoes that import
- **THEN** one `import.undone` delivery is queued and no `task.deleted` deliveries

#### Scenario: Ordinary writes unchanged
- **WHEN** a task is created through the REST API after an import
- **THEN** a `task.created` delivery is queued for every webhook subscribed to it

#### Scenario: Shared project member
- **WHEN** an import writes tasks into a project shared with another member who has a webhook subscribed to `import.completed`
- **THEN** that member's webhook receives one summary listing only that shared project

#### Scenario: Subscribe requires authentication
- **WHEN** a request without credentials creates a webhook subscribed to `import.completed`
- **THEN** the response is a 401 `unauthorized` error

#### Scenario: Unknown event name
- **WHEN** a user creates a webhook subscribed to `import.started`
- **THEN** the response is a 400 `invalid_input` error and nothing is stored

### Requirement: Private network policy shared with calendar subscriptions
The owner's "allow private network targets" setting SHALL also govern the URLs of calendar subscriptions (OpenSpec `calendar-feeds`), with the same address rules, the same check at creation and at every fetch, and the same connection to the checked address. Settings SHALL say next to the toggle that it applies to webhooks and calendar subscriptions.

#### Scenario: One toggle, two features
- **WHEN** the owner enables private network targets
- **THEN** a webhook to `http://192.168.1.10:8123/` and a calendar subscription to `http://192.168.1.5/family.ics` are both accepted, and disabling the toggle makes the next fetch of that subscription fail with `private_target`

#### Scenario: Member reads the policy
- **WHEN** a member opens the Calendar feeds panel while private targets are not allowed
- **THEN** adding a subscription on the local network is refused with a message naming the owner setting
