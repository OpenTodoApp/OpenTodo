# Shared contracts

Some logic runs on the server and in the web app: the server needs it for REST, MCP, the CLI and imports, and the app needs it offline. Each pair is kept in step by one fixture file that a Go test and a TypeScript test both read. Change one side, run both tests; when a fixture is generated, regenerate it with the command in the table, never by hand.

`scripts/contracts.test.mjs` (in `make repo-check`) checks this table: every fixture exists, every file named under *Read in Go* and *Read in TS* exists and names its fixture, and every fixture-like file in the repository (`*.vectors.json`, `*_vectors.json`, `*_fixture.json`, `*.fixture(s).json`) is listed here or below.

## The v1 surface snapshot

Not a shared fixture but the same idea one level up: [`internal/httpapi/testdata/v1_surface.json`](../internal/httpapi/testdata/v1_surface.json) records what every 1.x release keeps ([stability and compatibility](stability.md)): the `/api/v1/` routes with their policy, success statuses, request and response fields (read from the handlers' types), the error codes with their statuses, the op schema with each field's kind, the export's members and version, the MCP tools with their arguments and read results, and the `ot` commands, flags, exit codes and `--json` schemas (from `internal/cli/testdata/schema.golden.json`). `go test ./internal/httpapi -run TestV1SurfaceIsAdditive` fails when an entry is gone or changed and when a new one is not recorded; `-update` adds new entries and never removes or changes one. After `v1.0.0` is tagged, `make repo-check` also compares the file with the one at that tag. `TestGeneratedOpSchema` refuses to regenerate the op schema fixture without a field it had.

## Upgrade fixtures

[`internal/store/testdata/upgrade/`](../internal/store/testdata/upgrade/) holds one fixture per released minor version: `data.tar.gz`, the data directory that version wrote while the fixed scenario of `scripts/release/upgrade-scenario.mjs` ran against it, and `manifest.json`, what the version itself reported (counts read through the API, the op count, a device's cursor, the credentials, the source commit). `scripts/release/upgrade-fixture.sh <version> [ref]` builds the server from the tag (or `ref`) in a temporary checkout and writes both. `go test ./internal/tenant -run TestUpgradeFromEveryRelease` opens each fixture with the current server and compares. A fixture is never regenerated once its version is released; `make release-prepare` refuses a new minor without its own.

## Client recordings

[`internal/sync/testdata/v1_clients/`](../internal/sync/testdata/v1_clients/) holds the calls of the web app's sync client (`web.json`), `ot` (`ot.json`) and the browser extension (`extension.json`) against the server, in order, with sessions and tokens replaced by labels (`session:1`, `<token:1>`) and passwords by `<password>`. They come from the contract tests (`web/src/lib/*.contract.test.ts`) run through the recorder in `web/src/test/recorder.ts`: `make server cli && cd web && npm run test:contract:record`. `go test ./internal/tenant -run TestV1ClientsReplay` replays each file against a fresh current server (mapping the recorded ids and tokens to the replay's own) and fails on another status, a missing field or a field of another type. They are recorded once per major version and never regenerated within it; `make repo-check` checks that they hold no secret.
