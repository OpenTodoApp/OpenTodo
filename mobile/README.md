# OpenTodo native shells

Thin apps around the OpenTodo web app (OpenSpec change `native-shells`). A shell never bundles the web app: it loads it from the user's own server, so sessions, IndexedDB, the service worker and the capture screen work exactly as in the installed web app, and the shell needs no release when the web app changes. What only a native app can do (reminders without a push service, the share menu, widgets, biometric unlock) goes through a small, versioned bridge.

- `android/`: the Android app (Kotlin, one `app` module, AndroidX only; OpenSpec change `native-shells`).
- `ios/`: the iOS app (Swift, one app target and two extensions, no third-party code; OpenSpec change `ios-shell`).
- `app/`: the native app in progress (React Native with Expo, OpenSpec change `native-app-foundation`), which draws its own screens and shares the web app's protocol code instead of loading the web app. [Below](#the-native-app-mobileapp).
- Desktop (`desktop-shell`) is a separate change.

## The native app (`mobile/app`)

The trial of a native app (`native-app-foundation`): React Native 0.88 with Expo SDK 58 (New Architecture, Hermes), iPhone only, installed as **OpenTodo Preview** next to the shell (`app.open-todo.preview` on iOS; `app.opentodo.preview` on Android, where an id cannot hold a hyphen). For now it has one screen, the server's address and its check (`GET /api/v1/health` must answer `"app_sign_in": true`); sign-in, the local database and sync follow.

```sh
make app                                              # Linux is enough: npm ci, type-check, lint, Jest with the shared vectors
cd mobile/app && npx expo prebuild --platform ios     # writes ios/ from app.config.ts (git-ignored, never edited by hand)
cd mobile/app && npx expo run:ios                     # on a Mac with Xcode: build and start on a simulator
```

- **No committed native projects.** `ios/` and `android/` are generated by `expo prebuild` from `app.config.ts` (and, later, config plugins for the widget and the share extension), in CI and on demand.
- **Shared code.** `@shared/*` is `web/src/lib/*`; the boundary and the platform port are in [Work on the native app](../docs/contributing/native-app.md#the-shared-library).
- **Dependencies.** Pinned exactly, each with its reason in `app/DEPENDENCIES.md`.
- **CI.** `app-check` (Linux) for the app and the shared modules it uses; `App builds` (`.github/workflows/app-native.yml`: a Release simulator build on macOS and a debug build with the unit tests on Linux, both unsigned) for changes under `mobile/app/`, release tags and every night.

## Building the Android app

Needs JDK 17 or later and the Android SDK (platform 37.0, build tools 36.0.0) with `ANDROID_HOME` set; the Gradle wrapper downloads Gradle itself (checksum pinned).

The release build is reproducible (OpenSpec change `play-production`): the same tag gives the same APK apart from the signature, whatever the machine, the path, the time or the Gradle cache. That holds for this pinned toolchain, which CI and the F-Droid recipe use:

| Tool | Version | Pinned in |
| --- | --- | --- |
| JDK | Temurin 21.0.13+9 (F-Droid: its build server's default, Debian's OpenJDK 21) | `java-version` in `.github/workflows/ci.yml` and `android-repro.yml` |
| Gradle | 9.8.2 | `distributionUrl` and `distributionSha256Sum` in `android/gradle/wrapper/gradle-wrapper.properties` |
| Android Gradle Plugin | 9.5.1 (Kotlin 2.4.21) | `android/build.gradle.kts` |
| Build tools | 36.0.0 | `buildToolsVersion` in `android/app/build.gradle.kts`; the SDK step in CI |

The APK carries no build-time, machine or checkout metadata: no dependency block (`dependenciesInfo`, which F-Droid refuses) and no commit file (`vcsInfo`); the version comes only from `OPENTODO_VERSION`. `scripts/repo-checks.test.mjs` fails when one of the pins goes missing or this table stops naming it.

```sh
scripts/android-repro.sh v0.20.0                                  # build the tag twice, compare
scripts/android-repro.sh v0.20.0 opentodo-android-0.20.0.apk      # compare a release APK with a build of its tag
```

The second form needs `apksigcopier` (`python3 -m pip install --require-hashes -r scripts/release/requirements-repro.txt`): it copies the release APK's signature onto the local build and checks that the result verifies, which is exactly F-Droid's check. A mismatch names the files inside the APK that differ. CI runs the comparison on every release tag (a mismatch fails the release before anything is published), and **Actions → Android reproducible build** runs it on any tag or commit.

```sh
make android          # unit tests, lint, the checks below, debug APK and the instrumented-test APK
cd mobile/android && ./gradlew :app:assembleDebug
adb install app/build/outputs/apk/debug/app-debug.apk
```

Without a local SDK, the image CI's tooling is closest to works too:

```sh
docker run --rm -v "$PWD:/r" -w /r ghcr.io/cirruslabs/android-sdk:35 make android
```

Checks that `make android` runs besides the unit tests and lint:

| Task | Fails when |
| --- | --- |
| `:app:checkDependencies` | the release runtime classpath holds anything but AndroidX and Kotlin (no third-party SDK, design D8) |
| `:app:checkTranslations` | a language (`values-de`, `-es`, `-fr`, `-it`, `-pt`) misses a key of `values/strings.xml` |
| `:app:checkStoreMetadata` | the manifest's permissions differ from `store/permissions.txt`, a listing language is missing in `fastlane/metadata/android/`, or `data-safety.md` or `play-review.md` is missing |

The version comes from `OPENTODO_VERSION` (CI sets it from the tag; local builds are `0.0.0-dev`), the version code is `major·10000 + minor·100 + patch`.

## Building the iOS app

The official build is signed and uploaded to TestFlight in CI ([below](#the-ios-app-testflight-from-ci)). To build it yourself you need a Mac with Xcode 16 or newer and an installed iOS simulator runtime. The Xcode project is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from `ios/project.yml` and committed, so Xcode alone is enough; after editing `project.yml`, run `xcodegen generate` in `mobile/ios` and commit the result.

```sh
make ios                                   # unit tests on a simulator, unsigned device build, dependency check
make ios-archive                           # the TestFlight job's unsigned archive, signed ad hoc
SIM="iPhone 16" make ios                   # a specific simulator
cd mobile/ios && open OpenTodo.xcodeproj   # Run, with your team selected for signing
```

`make ios` is not part of `make check` (it needs macOS). CI's `ios` job runs it on a macOS runner, only when `mobile/ios` or the workflow changes. `WalkthroughTests` is skipped there; it needs a server and runs in the on-demand iPhone walkthrough workflow (`docs/ios-app.md`).

### Signing for a device

Pick a team for the three targets and Run. A free Apple ID can sign the app but not the App Groups capability the two extensions share data through, so an app-only build means removing `OpenTodoWidget.appex` and `OpenTodoShare.appex` from the app target's embedded content, deleting the two targets and dropping **App Groups** from `OpenTodo` — locally, never committed. Everything except the widget and the share sheet then works, and the app needs renewing from Xcode after seven days. The widget and the share sheet need a paid membership with one App Group on all three targets. `docs/ios-app.md` has the steps for both.

Two build settings matter:

| Setting | Effect |
| --- | --- |
| `OPENTODO_APP_BOUND_HOST` | empty (the default): a portable build that opens any server, without a service worker, so it needs the network; its Info.plist has no `WKAppBoundDomains` at all, since the key alone, even with a placeholder, denies the bridge on every other server (`ios-bridge-portable`). Set to a host name (`todo.example.com`, at most ten, comma separated): the "App-bound domains" build phase writes them as `WKAppBoundDomains`, and only for those origins `limitsNavigationsToAppBoundDomains` is switched on at runtime, which is what gives the web app its service worker, its precache and an offline start (design D2) |
| `OPENTODO_VERSION` | the version the shell reports to the web app and the app's `CFBundleShortVersionString`; `CFBundleVersion` is `major·10000 + minor·100 + patch` |

A build without `OPENTODO_VERSION` reports `0.0.0-dev`, which is older than `MIN_SHELL_APP` (`0.10.0`) in `web/src/lib/shell.ts`, so the web app's About screen calls that build outdated. `make ios` and CI pass the version from `git describe`, so this only affects a plain Run from Xcode.

Measured on iOS 27 in the simulator (design D2): without a matching app-bound domain, `'serviceWorker' in navigator` is `false` — iOS only exposes the service worker API to app-bound origins or the default browser. With the domain listed and the flag on, the service worker registers, precaches 126 files and the app starts offline from them. An app-bound domain is *not* a licence to skip the bridge's origin check: App-Bound Domains also gate message handlers and injected scripts, which is the second reason the list is opt-in.

## How it fits together

| File | What it does |
| --- | --- |
| `SetupActivity`, `ServerAddress`, `HealthCheck` | first-run screen: https, or http only for local addresses after a warning; `GET /api/v1/health`, then `/healthz` for older servers, names the failure (no network, not OpenTodo, untrusted certificate, refused) |
| `MainActivity` | the full-screen `WebView` on the configured origin; other origins open in the browser; file chooser; back; shares; "Change server" (long-press the app icon) |
| `Bridge` | the bridge, injected with `WebViewCompat.addWebMessageListener` and `addDocumentStartJavaScript`, both restricted to the configured origin |
| `ReminderSchedule`, `Reminders.kt` | the handed-over schedule, exact alarms (inexact when refused), notifications with Snooze 10 min and Dismiss, re-arming after a reboot |
| `GeofenceSchedule`, `Geofences.kt` | location reminders: the handed-over regions, at most 19 registered as platform proximity alerts (`LocationManager`, no Play services), the nearest to the last known position, re-ranked on leaving a 1 km region around it; a notification with Done and Dismiss on a crossing in the reminder's direction, at most once an hour per reminder; registered again after a reboot or an update |
| `HiddenRun` | the hourly refresh and notification actions: the web app in a hidden `WebView` for at most 30 seconds |
| `WidgetModel`, `Widgets.kt` | the Today and quick-add widgets (`RemoteViews`), drawn from the last publication only |
| `BiometricKeyStore` | the account key under a Keystore AES-GCM key that needs a strong biometric for every use and is invalidated by an enrolment change |

Certificates: `res/xml/network_security_config.xml` trusts the system and the user-installed authorities, nothing else; an untrusted certificate is refused, never bypassed. Android backup and device transfer exclude everything the app stores.

## The bridge, version 1

`window.opentodoShell` exists only on pages of the configured server's origin. The web side is `web/src/lib/shell.ts`; a method the shell does not list in `capabilities` is never called, and without the bridge the web app behaves as in a browser.

The iOS shell reports `platform: "ios"` and the same members; `scheduleReminders` answers `"granted"` or `"denied"` (iOS has no exact-alarm permission, so never `"exact-denied"`), `widgets`, `share`, `links` and — with Face ID or Touch ID enrolled — `biometric`.

| Member | Capability | Shape | Notes |
| --- | --- | --- | --- |
| `bridge` | | `1` | changes only when a method's shape changes |
| `platform` | | `"android"` | |
| `app` | | `"0.10.0"` | the shell's version; Settings → About warns below the web app's `MIN_SHELL_APP` |
| `capabilities` | | `string[]` | `reminders`, `widgets`, `geofences` (Android), and in the visible app `share`, `links`, `obsidian-links`, `biometric` (when a strong biometric is enrolled) |
| `scheduleReminders(json)` | `reminders` | `→ Promise<"granted" \| "denied" \| "exact-denied">` | `[{id, taskId, fireAt, title?}]`, the next 7 days; replaces the stored schedule; asks for the notification permission once, opens the exact-alarm setting once |
| `scheduleGeofences(json)` | `geofences` | `→ Promise<"granted" \| "foreground-only" \| "denied" \| "unavailable">` | `{version: 1, ask?, regions: [{id, taskId, lat, lon, radius, on: "arrive"\|"leave", title?}]}`, at most 100; replaces the stored regions, registered only with background location; asks for fine, then background location only with `ask` in the visible app; the position never reaches the web view |
| `testNotification()` | `reminders` | `→ Promise<boolean>` | shows a notification now |
| `publishWidget(json)` | `widgets` | `void` | `{updatedAt, locked, count, overdue, tasks: [{id, title?, time?, priority, overdue}]}`, at most 50 tasks; `locked` means counts only |
| `biometricStore(keyB64)` | `biometric` | `→ Promise<boolean>` | 32-byte raw account key; shows the biometric prompt |
| `biometricRead()` | `biometric` | `→ Promise<string \| null>` | the key after the prompt; `null` when cancelled, never stored or invalidated |
| `biometricForget()` | `biometric` | `void` | deletes the stored key |
| `openExternal(url)` | `links` | `void` | http(s), `mailto:` and `tel:` in the system browser or app; with `obsidian-links` also an Obsidian note link of exactly the form `obsidian://open?vault=…&file=…` (no other Obsidian action, no other custom scheme) |

The iOS shell reports `platform: "ios"` and the same members; `scheduleReminders` answers `"granted"` or `"denied"` (iOS has no exact-alarm permission, so never `"exact-denied"`), `widgets`, `share`, `links` and — with Face ID or Touch ID enrolled — `biometric`.

Addresses the shell opens in the web app: `/?task=<id>` (a notification tap or the widget's row), `/?reminder=<id>&action=snooze|dismiss` (a notification action; `done|dismiss` for a location reminder), `/?add=<text>`, `/today` and `/share?title=…&text=…&url=…[&files=1]` (shares; files follow as the `opentodo-files` message, the same one the browser extension posts — the extension's own per-file check is `ShareMap`, at most 10 files, 20 MB each, 25 MB in all). The same addresses arrive as links: `opentodo://task/<id>`, `opentodo://reminder/<id>?action=snooze|dismiss`, `opentodo://add?text=…` and `opentodo://share`. Every value is percent-encoded when it goes into the path, and only `snooze` and `dismiss` survive as actions (and, from an Android location reminder's notification, `done`).

## Release signing

Release builds are signed only in CI, on a `v*` tag, from four repository secrets: `ANDROID_KEYSTORE_BASE64` (the keystore file, base64), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`. The job writes `keystore.properties` and the keystore to the runner's temporary directory, builds `opentodo-android-<version>.apk` and `.aab` (the AAB with `-Popentodo.play=true`, the Google Play build without location permissions until Play approves background location; `scripts/android-store-check.sh` checks both on every CI run), deletes both files, and the release job attaches the two files with build provenance. Without the secrets the tag build skips signing with a warning. Never commit a keystore or `keystore.properties` (both are ignored).

**One certificate everywhere** (`play-production` D1). The release key signs the GitHub APK, F-Droid publishes that same signed APK (`AllowedAPKSigningKeys` in the F-Droid metadata), and Google Play signs with the same key through Play App Signing ("use my own key"). Its certificate's SHA-256 is

`ff2eacdf7e79712e44fdd9d2e3110891e712c170ea516bd3fbbecc291072befa`

(`CN=Raffaele Pizzari, O=OpenTodo, C=DE`). The signing step prints it to the job summary with `apksigner verify --print-certs` and fails when it differs from the one in `android/store/fdroid/app.opentodo.yml`; `docs/android-app.md` publishes it for users.

**Google Play upload.** After the release, the `play` job of a final tag (no suffix) takes the AAB, replaces the release key's signature with the **upload key**'s, and `scripts/release/play-upload.mjs` puts it on Play's internal testing track with the CHANGELOG notes (Play Developer API, a service account, no dependency). The secrets are in the `release` environment: `PLAY_UPLOAD_KEYSTORE_BASE64`, `PLAY_UPLOAD_KEYSTORE_PASSWORD`, `PLAY_UPLOAD_KEY_ALIAS`, `PLAY_UPLOAD_KEY_PASSWORD` and `PLAY_SERVICE_ACCOUNT_JSON` (a service account with "Release apps to testing tracks" only, so CI can never promote to production). Without them the job warns and succeeds. A leaked upload key is reset by Google without changing the app's identity; the release key never goes to Play again after the one-time enrolment.

The store listing (name, summary, description, icon, feature graphic, phone screenshots and each release's notes, six languages) is the Fastlane folder at the repository root, `fastlane/metadata/android/`: F-Droid reads it from the commit it builds (it never looks under the recipe's `subdir`), and the Play listing is copied from it; [`fastlane/README.md`](../fastlane/README.md) says what makes each file. The other store files live in `android/store/`: `data-safety.md` (the Play form: no data collected, no third-party SDK), `play-review.md` (App access with the demo instance, the exact-alarm declaration, the content rating answers), `fdroid/app.opentodo.yml` (fdroiddata metadata without texts, the source of truth for F-Droid's copy) and `permissions.txt`.

### The iOS app: TestFlight from CI

The official iOS build comes from TestFlight and the App Store. As the copyright holder, the author of OpenTodo allows distributing its iOS app through Apple's App Store and TestFlight; anyone can still build it from source as above. It is signed and uploaded in CI with no Mac and nothing stored: no certificate, profile or password lives in this repository or in a secret (OpenSpec change `ios-distribution`, D9).

**The secrets**, in the `release` environment: `APPLE_TEAM_ID` (the ten-character team id), `ASC_KEY_ID` and `ASC_ISSUER_ID` (App Store Connect → Users and Access → Integrations → App Store Connect API, a team key), and `ASC_KEY_P8` (the content of the key's `.p8` file, pasted whole). The key's role is App Manager; if the signing step answers 403 on `certificates`, Apple wants an Admin key for creating a distribution certificate, and replacing `ASC_KEY_ID` and `ASC_KEY_P8` is enough.

**What a run does** (`.github/workflows/ios-testflight.yml`):

1. `scripts/release/appstore.mjs register`: registers `app.open-todo.ios`, `app.open-todo.ios.widget` and `app.open-todo.ios.share` with App Groups when missing; safe to repeat.
2. The version from the last tag (`1.2.0`) and the build number `major·10000 + minor·100 + patch` (`10200`); a later upload of the same version takes the next free `10200.1`, `10200.2`, …, which TestFlight requires.
3. `scripts/release/ios-testflight.sh archive` with the newest Xcode on the runner: built with signing off, then signed ad hoc with each target's entitlements. The `ios` job runs this step (`make ios-archive`) on every iOS change.
4. A new key and CSR on the runner; `appstore.mjs sign` creates an Apple Distribution certificate and three App Store profiles through the API, checks they carry the App Group and writes `ExportOptions.plist`; they go into a keychain made for the run.
5. `xcodebuild -exportArchive`, then `xcrun altool --upload-package` with the API key.
6. "What to test" from the version's CHANGELOG section, once Apple has the build.
7. Always, even after a failure: the keychain and the key file are deleted. The certificate and the profiles of a build that was uploaded stay: Apple checks the signature again when the build is submitted for TestFlight or App Store review, and a revoked certificate makes it fail with ITMS-90035 "Invalid Signature". Their private key never left the runner, so nobody can sign with them. A run that uploaded nothing revokes its certificate and deletes its profiles.
8. When Apple refuses a new certificate because the team is at its limit, `sign` revokes the oldest certificate this workflow made (the one named by the oldest "OpenTodo CI" profiles), deletes its profiles and tries again. Builds signed with it can no longer be submitted for review, which with one release a week only affects older builds. A certificate made by hand is never touched. Apple emails the account holder about each certificate created and revoked.

**When it runs:** after the GitHub release of a final tag (never a release candidate), and by hand: **Actions → iOS TestFlight → Run workflow**, with a tag, branch or commit and, rarely, a build number. Without the secrets it warns and succeeds. A failed upload never touches the release. Nothing is submitted for review; that is a step in [RELEASING.md](../RELEASING.md).

**Bundle IDs:** the iOS app is `app.open-todo.ios` (widget `.widget`, share extension `.share`, App Group `group.app.open-todo`), built on the project's domain open-todo.app, while Android stays `app.opentodo`: Apple refused `app.opentodo` because another developer team already holds it. **Actions → iOS register IDs → Run workflow** only registers and reports: each identifier (already there, or registered now), whether the App Store Connect app record exists, and what the API cannot do. If `app.open-todo.ios` belongs to another team, it fails and says so: change the prefix in `ios/project.yml` (and regenerate the Xcode project), the App Group and `scripts/release/appstore.mjs`. Two things are done once by hand, on the web: register the App Group `group.app.open-todo` (developer.apple.com → Certificates, Identifiers & Profiles → Identifiers → App Groups) and tick it on the three identifiers, and create the app record (App Store Connect → Apps → + → New App, bundle ID `app.open-todo.ios`). The TestFlight job stops and says which while either is missing.

**Store material** for App Store Connect is in `ios/store/`: the listing text, the App Privacy answers ("Data Not Collected"), the export compliance reasoning (`ITSAppUsesNonExemptEncryption` is `NO`) and the notes for App Review.
