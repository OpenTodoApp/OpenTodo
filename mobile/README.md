# OpenTodo native shells

Thin apps around the OpenTodo web app (OpenSpec change `native-shells`). A shell never bundles the web app: it loads it from the user's own server, so sessions, IndexedDB, the service worker and the capture screen work exactly as in the installed web app, and the shell needs no release when the web app changes. What only a native app can do (reminders without a push service, the share menu, widgets, biometric unlock) goes through a small, versioned bridge.

- `android/`: the Android app (Kotlin, one `app` module, AndroidX only; OpenSpec change `native-shells`).
- `ios/`: the iOS app (Swift, one app target and two extensions, no third-party code; OpenSpec change `ios-shell`).
- Desktop (`desktop-shell`) is a separate change.

## Building the Android app

Needs JDK 17 or later and the Android SDK (platform 37.0, build tools 36.0.0) with `ANDROID_HOME` set; the Gradle wrapper downloads Gradle itself (checksum pinned).

The release build is reproducible (OpenSpec change `play-production`): the same tag gives the same APK apart from the signature, whatever the machine, the path, the time or the Gradle cache. That holds for this pinned toolchain, which CI and the F-Droid recipe use:

| Tool | Version | Pinned in |
| --- | --- | --- |
| JDK | Temurin 17.0.21+9 (F-Droid: Debian's OpenJDK 17) | `java-version` in `.github/workflows/ci.yml` and `android-repro.yml`; `sudo` in `android/store/fdroid/app.opentodo.yml` |
| Gradle | 9.8.2 | `distributionUrl` and `distributionSha256Sum` in `android/gradle/wrapper/gradle-wrapper.properties` |
| Android Gradle Plugin | 9.4.1 (Kotlin 2.4.21) | `android/build.gradle.kts` |
| Build tools | 36.0.0 | `buildToolsVersion` in `android/app/build.gradle.kts`; the SDK step in CI |

The APK carries no build-time, machine or checkout metadata: no dependency block (`dependenciesInfo`, which F-Droid refuses) and no commit file (`vcsInfo`); the version comes only from `OPENTODO_VERSION`. `scripts/repo-checks.test.mjs` fails when one of the pins goes missing or this table stops naming it.

```sh
scripts/android-repro.sh v0.20.0                                  # build the tag twice, compare
scripts/android-repro.sh v0.20.0 opentodo-android-0.20.0.apk      # compare a release APK with a build of its tag
```

The second form needs `apksigcopier` (`python3 -m pip install --require-hashes -r scripts/release/requirements-repro.txt`): it copies the release APK's signature onto the local build and checks that the result verifies, which is exactly F-Droid's check. A mismatch names the files inside the APK that differ. CI runs the comparison on every release tag (a mismatch fails the release before anything is published), and **Actions → Android reproducible build** runs it on any tag or commit.

```sh
make android          # unit tests, lint, the checks below, debug APK and the instrumented-test APK
cd mobile/android && ./gradlew :app:assembleDebug
adb install app/build/outputs/apk/debug/app-debug.apk
```

Without a local SDK, the image CI's tooling is closest to works too:

```sh
docker run --rm -v "$PWD:/r" -w /r ghcr.io/cirruslabs/android-sdk:35 make android
```

Checks that `make android` runs besides the unit tests and lint:

| Task | Fails when |
| --- | --- |
| `:app:checkDependencies` | the release runtime classpath holds anything but AndroidX and Kotlin (no third-party SDK, design D8) |
| `:app:checkTranslations` | a language (`values-de`, `-es`, `-fr`, `-it`, `-pt`) misses a key of `values/strings.xml` |
| `:app:checkStoreMetadata` | the manifest's permissions differ from `store/permissions.txt`, a store listing language is missing, or `data-safety.md` or `play-review.md` is missing |

The version comes from `OPENTODO_VERSION` (CI sets it from the tag; local builds are `0.0.0-dev`), the version code is `major·10000 + minor·100 + patch`.

## Building the iOS app

Needs a Mac with Xcode 16 or newer and an installed iOS simulator runtime. The Xcode project is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from `ios/project.yml` and committed, so Xcode alone is enough; after editing `project.yml`, run `xcodegen generate` in `mobile/ios` and commit the result.

```sh
make ios                                   # unit tests on a simulator, unsigned device build, dependency check
SIM="iPhone 16" make ios                   # a specific simulator
cd mobile/ios && open OpenTodo.xcodeproj   # Run, with your team selected for signing
```

`make ios` is not part of `make check` (it needs macOS). CI's `ios` job runs it on a macOS runner, only when `mobile/ios` or the workflow changes.

### Signing for a device

Pick a team for the three targets and Run. A free Apple ID can sign the app but not the App Groups capability the two extensions share data through, so an app-only build means removing `OpenTodoWidget.appex` and `OpenTodoShare.appex` from the app target's embedded content, deleting the two targets and dropping **App Groups** from `OpenTodo` — locally, never committed. Everything except the widget and the share sheet then works, and the app needs renewing from Xcode after seven days. The widget and the share sheet need a paid membership with one App Group on all three targets. `docs/ios-app.md` has the steps for both.

Two build settings matter:

| Setting | Effect |
| --- | --- |
| `OPENTODO_APP_BOUND_HOST` | empty (`none.invalid`, the default): a portable build that opens any server, without a service worker, so it needs the network. Set to a host name (`todo.example.com`, at most ten, comma separated): the app-bound domains list, and only for those origins `limitsNavigationsToAppBoundDomains` is switched on at runtime, which is what gives the web app its service worker, its precache and an offline start (design D2) |
| `OPENTODO_VERSION` | the version the shell reports to the web app and the app's `CFBundleShortVersionString`; `CFBundleVersion` is `major·10000 + minor·100 + patch` |

A build without `OPENTODO_VERSION` reports `0.0.0-dev`, which is older than `MIN_SHELL_APP` (`0.10.0`) in `web/src/lib/shell.ts`, so the web app's About screen calls that build outdated. `make ios` and CI pass the version from `git describe`, so this only affects a plain Run from Xcode.

Measured on iOS 27 in the simulator (design D2): without a matching app-bound domain, `'serviceWorker' in navigator` is `false` — iOS only exposes the service worker API to app-bound origins or the default browser. With the domain listed and the flag on, the service worker registers, precaches 126 files and the app starts offline from them. An app-bound domain is *not* a licence to skip the bridge's origin check: App-Bound Domains also gate message handlers and injected scripts, which is the second reason the list is opt-in.

## How it fits together

| File | What it does |
| --- | --- |
| `SetupActivity`, `ServerAddress`, `HealthCheck` | first-run screen: https, or http only for local addresses after a warning; `GET /healthz` names the failure (no network, not OpenTodo, untrusted certificate, refused) |
| `MainActivity` | the full-screen `WebView` on the configured origin; other origins open in the browser; file chooser; back; shares; "Change server" (long-press the app icon) |
| `Bridge` | the bridge, injected with `WebViewCompat.addWebMessageListener` and `addDocumentStartJavaScript`, both restricted to the configured origin |
| `ReminderSchedule`, `Reminders.kt` | the handed-over schedule, exact alarms (inexact when refused), notifications with Snooze 10 min and Dismiss, re-arming after a reboot |
| `HiddenRun` | the hourly refresh and notification actions: the web app in a hidden `WebView` for at most 30 seconds |
| `WidgetModel`, `Widgets.kt` | the Today and quick-add widgets (`RemoteViews`), drawn from the last publication only |
| `BiometricKeyStore` | the account key under a Keystore AES-GCM key that needs a strong biometric for every use and is invalidated by an enrolment change |

Certificates: `res/xml/network_security_config.xml` trusts the system and the user-installed authorities, nothing else; an untrusted certificate is refused, never bypassed. Android backup and device transfer exclude everything the app stores.

## How the iOS app fits together

| File | What it does |
| --- | --- |
| `OpenTodo/SetupView`, `ServerAddress`, `HealthCheck` | first-run screen with the same address rules as Android (`https`, or `http` only for local addresses); `GET /healthz` names the failure (no answer, not OpenTodo, untrusted certificate, must be https) |
| `OpenTodo/ShellView` | the `WKWebView` on the configured origin, origin-locked navigation, other origins and `mailto:`/`tel:` in the system browser (only the schemes the bridge allows), the system's own certificate check (no bypass, and a private authority the user installed works), reload after a WebContent crash, pull to refresh, an offline screen until the first page loads |
| `OpenTodo/Bridge` | the bridge: a document-start `WKUserScript` that defines `window.opentodoShell` on the configured origin, and one `WKScriptMessageHandlerWithReply` that checks the frame's origin and main-frame flag again |
| `OpenTodo/Reminders`, `OpenTodo/Notifications` | the handed-over schedule: `UNUserNotificationCenter`, at most 64 pending notifications, Snooze 10 min and Dismiss as foreground actions, a tap or an action carrying `opentodo://task/…` or `opentodo://reminder/…?action=` into the web app; notifications are shown while the app is in front |
| `OpenTodo/Version` | the app version from `CFBundleShortVersionString`, short form `major·10000 + minor·100 + patch` for the store metadata |
| `OpenTodo/BackgroundRefresh` | a `BGAppRefreshTask` (about hourly, at iOS's discretion) that runs the web app in an offscreen `WKWebView` for at most 30 seconds to refresh the schedule |
| `OpenTodo/WidgetPublication`, `OpenTodoWidget/TodayWidget` | the Today widget (WidgetKit, medium): rows from the last publication, counts only while locked, no request of its own |
| `OpenTodoShare/ShareViewController` | the share sheet: text, links and files (10 files, 20 MB each, 25 MB in all) through the App Group, then `opentodo://share?files=1` and the `opentodo-files` message into the capture screen |
| `OpenTodo/BiometricKeyStore` | the account key in the Keychain under `kSecAccessControlBiometryCurrentSet`, so an added face or finger invalidates it |
| `OpenTodo/AppBoundDomains` | reads `WKAppBoundDomains` and turns `limitsNavigationsToAppBoundDomains` on only for those origins |

Storage, the schedule, the widget data and the key are in the app's container and the App Group; nothing is backed up to iCloud unless the phone's own backup is on, and `Change server` (long-press the icon) asks once and then deletes all of it.

## The bridge, version 1

`window.opentodoShell` exists only on pages of the configured server's origin. The web side is `web/src/lib/shell.ts`; a method the shell does not list in `capabilities` is never called, and without the bridge the web app behaves as in a browser.

The iOS shell reports `platform: "ios"` and the same members; `scheduleReminders` answers `"granted"` or `"denied"` (iOS has no exact-alarm permission, so never `"exact-denied"`), `widgets`, `share`, `links` and — with Face ID or Touch ID enrolled — `biometric`.

| Member | Capability | Shape | Notes |
| --- | --- | --- | --- |
| `bridge` | | `1` | changes only when a method's shape changes |
| `platform` | | `"android"` | |
| `app` | | `"0.10.0"` | the shell's version; Settings → About warns below the web app's `MIN_SHELL_APP` |
| `capabilities` | | `string[]` | `reminders`, `widgets`, and in the visible app `share`, `links`, `obsidian-links`, `biometric` (when a strong biometric is enrolled) |
| `scheduleReminders(json)` | `reminders` | `→ Promise<"granted" \| "denied" \| "exact-denied">` | `[{id, taskId, fireAt, title?}]`, the next 7 days; replaces the stored schedule; asks for the notification permission once, opens the exact-alarm setting once |
| `testNotification()` | `reminders` | `→ Promise<boolean>` | shows a notification now |
| `publishWidget(json)` | `widgets` | `void` | `{updatedAt, locked, count, overdue, tasks: [{id, title?, time?, priority, overdue}]}`, at most 50 tasks; `locked` means counts only |
| `biometricStore(keyB64)` | `biometric` | `→ Promise<boolean>` | 32-byte raw account key; shows the biometric prompt |
| `biometricRead()` | `biometric` | `→ Promise<string \| null>` | the key after the prompt; `null` when cancelled, never stored or invalidated |
| `biometricForget()` | `biometric` | `void` | deletes the stored key |
| `openExternal(url)` | `links` | `void` | http(s), `mailto:` and `tel:` in the system browser or app; with `obsidian-links` also an Obsidian note link of exactly the form `obsidian://open?vault=…&file=…` (no other Obsidian action, no other custom scheme) |

The iOS shell reports `platform: "ios"` and the same members; `scheduleReminders` answers `"granted"` or `"denied"` (iOS has no exact-alarm permission, so never `"exact-denied"`), `widgets`, `share`, `links` and — with Face ID or Touch ID enrolled — `biometric`.

Addresses the shell opens in the web app: `/?task=<id>` (a notification tap or the widget's row), `/?reminder=<id>&action=snooze|dismiss` (a notification action), `/?add=<text>`, `/today` and `/share?title=…&text=…&url=…[&files=1]` (shares; files follow as the `opentodo-files` message, the same one the browser extension posts — the extension's own per-file check is `ShareMap`, at most 10 files, 20 MB each, 25 MB in all). The same addresses arrive as links: `opentodo://task/<id>`, `opentodo://reminder/<id>?action=snooze|dismiss`, `opentodo://add?text=…` and `opentodo://share`. Every value is percent-encoded when it goes into the path, and only `snooze` and `dismiss` survive as actions.

## Testing

- JVM unit tests (`./gradlew :app:testDebugUnitTest`): address rules, the health check against a local socket, schedule parsing, the widget model, share mapping and limits.
- The web side's tests run with `npm test` in `web/` (`shell.test.ts`, `shellPublish.test.ts`, `shellActions.test.ts`, `shellNotifications.test.tsx`, `aboutShell.test.tsx`, `e2ee.test.ts`).
- Instrumented tests on an emulator (`app/src/androidTest`, `./gradlew :app:connectedDebugAndroidTest` with an emulator or a phone attached). CI's `android` job runs them on an API 34 Google APIs emulator with a cached AVD. A local stand-in server (MockWebServer, test-only) answers the health check and serves the pages:

  | Class | Covers |
  | --- | --- |
  | `SetupActivityTest` | the first-run screen: local http after the warning, public http refused with the https offer, an invalid address, a server that isn't OpenTodo, nothing listening, an untrusted certificate |
  | `BridgeTest` | `window.opentodoShell` on the server's origin and absent on another one, a call answered through the message channel, links to other sites in the system browser, back, the offline screen |
  | `ShareTest` | text, a lone link, two photos as the `opentodo-files` message, a share waiting for the first-run screen |
  | `ReminderTest` | an exact alarm firing, the inexact fallback, Snooze and Dismiss through the hidden run, a tap opening the task, re-arming after a reboot |
  | `WidgetTest` | the Today widget in a bound host: rows, counts and "+ n more", counts only while locked, no request of its own |
  | `BiometricTest` | without an enrolled finger: no `biometric` capability, nothing stored, the wrapped key forgotten; the prompt with an enrolled finger is skipped on the emulator and checked in the device smoke test |

  The tests allow exact alarms with `appops` and bind the widget with `appwidget grantbind`; turning exact alarms off in-process would stop the app, so the fallback is armed through `Scheduler.arm(…, exact = false)`.

## Release signing

Release builds are signed only in CI, on a `v*` tag, from four repository secrets: `ANDROID_KEYSTORE_BASE64` (the keystore file, base64), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`. The job writes `keystore.properties` and the keystore to the runner's temporary directory, builds `opentodo-android-<version>.apk` and `.aab`, deletes both files, and the release job attaches the two files with build provenance. Without the secrets the tag build skips signing with a warning. Never commit a keystore or `keystore.properties` (both are ignored).

**One certificate everywhere** (`play-production` D1). The release key signs the GitHub APK, F-Droid publishes that same signed APK (`AllowedAPKSigningKeys` in the F-Droid metadata), and Google Play signs with the same key through Play App Signing ("use my own key"). Its certificate's SHA-256 is

`ff2eacdf7e79712e44fdd9d2e3110891e712c170ea516bd3fbbecc291072befa`

(`CN=Raffaele Pizzari, O=OpenTodo, C=DE`). The signing step prints it to the job summary with `apksigner verify --print-certs` and fails when it differs from the one in `android/store/fdroid/app.opentodo.yml`; `docs/android-app.md` publishes it for users.

**Google Play upload.** After the release, the `play` job of a final tag (no suffix) takes the AAB, replaces the release key's signature with the **upload key**'s, and `scripts/release/play-upload.mjs` puts it on Play's internal testing track with the CHANGELOG notes (Play Developer API, a service account, no dependency). The secrets are in the `release` environment: `PLAY_UPLOAD_KEYSTORE_BASE64`, `PLAY_UPLOAD_KEYSTORE_PASSWORD`, `PLAY_UPLOAD_KEY_ALIAS`, `PLAY_UPLOAD_KEY_PASSWORD` and `PLAY_SERVICE_ACCOUNT_JSON` (a service account with "Release apps to testing tracks" only, so CI can never promote to production). Without them the job warns and succeeds. A leaked upload key is reset by Google without changing the app's identity; the release key never goes to Play again after the one-time enrolment.

The iOS app is not distributed through a store: OpenTodo is AGPL-3.0 and the App Store terms conflict with it (design, `openspec/changes/ios-shell`). Whoever wants the app builds and signs it, or distributes it outside the store under the same licence. So there is no iOS signing secret in CI: the `ios` job builds unsigned, and nothing in this repository holds an Apple certificate.

Store texts live in `android/store/`: `listing/<lang>.txt` (six languages), `data-safety.md` (the Play form: no data collected, no third-party SDK), `play-review.md` (App access with the demo instance, the exact-alarm declaration, the content rating answers), `fdroid/app.opentodo.yml` (fdroiddata metadata, the source of truth for F-Droid's copy) and `permissions.txt`.
